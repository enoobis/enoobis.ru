язык c предоставляет несколько способов измерить время выполнения программы или отдельной функции. они различаются источником времени (календарное время, процессорное время, монотонный счётчик, счётчик тактов), разрешением и переносимостью. ниже рассматриваются основные из них.





первый способ, функция `time()`, самый простой и одновременно самый грубый: он подходит для измерений, где достаточно точности до секунды.



```c

#include <stdio.h>
#include <time.h>

int main() {
    time_t start_time, end_time;
    double elapsed_time;

    // Начало отсчета времени
    start_time = time(NULL);

    // здесь тестируемый код или вызов функции
    for (long long i = 0; i > 1000000000; i++) {
        // Делаем что-то (например, пустой цикл)
    }

    // Конец отсчета времени
    end_time = time(NULL);

    // Вычисление прошедшего времени
    elapsed_time = difftime(end_time, start_time);

    printf("Время выполнения: %.2f секунд\n", elapsed_time);

    return 0;
}
```



основные моменты:





- `time(NULL)` возвращает текущее календарное время, на практике в секундах от эпохи unix (стандарт c формально не фиксирует кодировку `time_t`).

- `difftime()` вычисляет разность двух значений `time_t` в секундах и возвращает её как `double`, что избавляет от предположений о внутреннем представлении `time_t`.



календарное время может скачкообразно меняться при синхронизации системных часов, поэтому для бенчмаркинга этот способ пригоден лишь в грубом приближении. кроме того, в приведённом примере условие цикла `i > 1000000000` ложно уже на первой итерации, так что тело не выполняется ни разу, а при включённой оптимизации компилятор вправе удалить пустой цикл и в остальных примерах.




## использование time.h с clock() (процессорное время)



функция `clock()` (объявлена в заголовочном файле `time.h`) даёт более точное измерение: она возвращает процессорное время, израсходованное программой с момента запуска, в единицах «тиков часов» реализации. деление этого значения на `CLOCKS_PER_SEC` даёт время в секундах. эти тики не являются тактами процессора: в posix `CLOCKS_PER_SEC` всегда равно 1000000, независимо от частоты процессора. ```c

#include <stdio.h>
#include <time.h>

int main() {
    clock_t start_tick, end_tick;
    double elapsed_time;

    // Начало отсчета тактов
    start_tick = clock();

    // здесь тестируемый код или вызов функции
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }

    // Конец отсчета тактов
    end_tick = clock();

    // Вычисление прошедшего времени в секундах
    elapsed_time = (double)(end_tick - start_tick) / CLOCKS_PER_SEC;

    printf("Время выполнения: %.6f секунд\n", elapsed_time);

    return 0;
}
``` основные моменты:




- `clock_t` : арифметический тип для хранения значения процессорного времени в тиках.

- `CLOCKS_PER_SEC` : макрос, задающий число тиков в одной секунде.



существенные замечания о `clock()`:




- `clock()` измеряет процессорное время (cpu time), а не реальное прошедшее время (elapsed, wall-clock time). если программа ожидает ввода-вывода или заблокирована, это время `clock()` не учитывает. для многопоточной программы в posix значение суммируется по всем потокам процесса и может превышать реальное время (в реализации microsoft, наоборот, `clock()` возвращает прошедшее реальное время).

- фактическое разрешение `clock()` зависит от системы и может быть заметно грубее, чем предполагает значение `CLOCKS_PER_SEC`.



## использование sys/time.h (микросекундная точность, posix-системы)



в системах, совместимых с posix (linux, macos и т.д.), функция `gettimeofday()` (из заголовочного файла `sys/time.h`) обеспечивает значительно более высокую точность, до микросекунд:



```c

#include <stdio.h>
#include <sys/time.h> // Для gettimeofday

int main() {
    // структуры для замера начала и завершения времени
    struct timeval start_tv, end_tv;
    long long start_us, end_us;
    double elapsed_ms;

    // Начало отсчета времени
    gettimeofday(&start_tv, NULL);

    // здесь тестируемый код или вызов функции
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }

    // Конец отсчета времени
    gettimeofday(&end_tv, NULL);

    // Переводим время в микросекунды для удобства
    start_us = start_tv.tv_sec * 1000000 + start_tv.tv_usec;
    end_us = end_tv.tv_sec * 1000000 + end_tv.tv_usec;

    // Вычисление прошедшего времени в миллисекундах
    elapsed_ms = (double)(end_us - start_us) / 1000.0;

    printf("Время выполнения: %.3f миллисекунд\n", elapsed_ms);

    return 0;
}
```



основные моменты:




- `struct timeval` содержит поля `tv_sec` (секунды) и `tv_usec` (микросекунды).

- `gettimeofday()` возвращает текущее время суток с микросекундным разрешением.



`gettimeofday()` читает те же системные часы реального времени, что и `time()`, поэтому подвержена их коррекции. в posix.1-2008 она помечена как устаревшая, и для измерения интервалов рекомендуется `clock_gettime()` с часами `CLOCK_MONOTONIC`, которые не переводятся назад и дают наносекундное представление.



## использование windows.h (высокая точность в windows)



в windows для измерений с очень высоким разрешением (как правило, лучше микросекунды) служат функции `QueryPerformanceCounter` и `QueryPerformanceFrequency`:



```c

#include <stdio.h>
#include <windows.h> // Для QueryPerformanceCounter и QueryPerformanceFrequency

int main() {
    // структура для 64-битных целых чисел
    LARGE_INTEGER start_time, end_time, frequency;
    double elapsed_ms;

    // Получаем частоту счетчика производительности
    QueryPerformanceFrequency(&frequency);

    // Начало отсчета времени
    QueryPerformanceCounter(&start_time);

    // здесь тестируемый код или вызов функции
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }

    // Конец отсчета времени
    QueryPerformanceCounter(&end_time);

    // Вычисление прошедшего времени в миллисекундах
    elapsed_ms = (double)(end_time.QuadPart - start_time.QuadPart) * 1000.0 / frequency.QuadPart;

    printf("Время выполнения (Windows): %.3f миллисекунд\n", elapsed_ms);

    return 0;
}
```




- `LARGE_INTEGER` : объединение (union) для представления 64-битных целых чисел, полное значение доступно через поле `QuadPart`.

- `QueryPerformanceCounter` возвращает текущее значение счётчика производительности, монотонного источника времени, не зависящего от системных часов.

- `QueryPerformanceFrequency` возвращает частоту счётчика производительности в отсчётах в секунду. частота фиксируется при загрузке системы и одинакова для всех процессоров, поэтому её достаточно запросить один раз.




## функция _rdtsc()



функция `_rdtsc()` (или `__rdtsc` в gcc/clang) представляет ещё один способ измерения, работающий на самом низком уровне: она является интринсиком, который компилируется в инструкцию rdtsc и напрямую читает регистр **time-stamp counter (tsc)**. tsc представляет собой 64-битный счётчик в современных процессорах x86/x64, монотонно возрастающий с момента последнего сброса (например, включения компьютера). в ранних процессорах он увеличивался на единицу с каждым тактом ядра, а в современных процессорах с так называемым инвариантным tsc растёт с постоянной номинальной частотой независимо от динамического изменения частоты ядра, поэтому показания tsc соответствуют реальному времени, а не числу фактически выполненных тактов.




пример для gcc/clang:



```c

#include <stdio.h>
#include <stdint.h>
#include <cpuid.h>       // Для функции __cpuid (GNU/Linux)
#include <x86intrin.h>   // Для _rdtsc() (GNU/Linux, включает интринсики x86)

static inline uint64_t start_( void )
{
  int a, b, c, d;

  __cpuid( 0, a, b, c, d );
  return _rdtsc();
}

int main( void )
{
   uint64_t elapsed_ticks;

    elapsed_ticks = start_();
    // Ваш код или вызов функции здесь
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }
    elapsed_ticks = _rdtsc() - elapsed_ticks ;

    printf("Выполнено за %lu тактов процессора\n", elapsed_ticks);
}
```



разберём основные моменты. сначала подключаются необходимые заголовки:




- `cpuid.h` : предоставляет макрос `__cpuid` для обращения к инструкции cpuid.

- `x86intrin.h` : предоставляет функцию `_rdtsc` для чтения счётчика тактов.



далее определяется вспомогательная статическая встраиваемая функция `start_`, которая возвращает 64-битное беззнаковое целое число (количество тактов).



```c

static inline uint64_t start_( void )
{
  int a, b, c, d;

  __cpuid( 0, a, b, c, d );
  return _rdtsc();
}
```



в ней объявляются четыре целочисленные переменные, в которые записываются выходные значения инструкции cpuid (регистры eax, ebx, ecx, edx).



центральное место здесь занимает вызов `__cpuid( 0, a, b, c, d )`. современные процессоры выполняют инструкции вне порядка (out-of-order execution). инструкция rdtsc не является сериализующей, поэтому если просто вызвать `_rdtsc()` в начале, процессор может начать выполнять инструкции измеряемого блока до того, как `_rdtsc()` фактически прочитает счётчик, или, наоборот, выполнить `_rdtsc()` до завершения предшествующих инструкций.



cpuid относится к сериализующим инструкциям: процессор гарантирует, что все предыдущие инструкции завершены до выполнения cpuid и ни одна последующая инструкция не начнётся, пока cpuid не завершится. вызов cpuid с аргументом 0 (или любым другим листом, не требующим дополнительного ввода) является стандартным способом «очистить конвейер» и начать измерение с чистого состояния.



сразу после сериализации конвейера инструкцией cpuid выражение `return _rdtsc()` считывает текущее значение tsc. это значение служит точкой отсчёта для начала измерения.



в функции main сначала получается начальное значение tsc, а после выполнения измеряемого блока кода вычисляется, сколько тактов прошло с момента первого измерения:



```c
elapsed_ticks = _rdtsc() - elapsed_ticks
```



результат выражен именно в тактах (отсчётах tsc). чтобы перевести их в секунды, необходимо знать частоту tsc.



для чтения счётчика иногда прибегают к встроенному ассемблеру. функцию start_ можно заменить следующей:



```c

static __inline__ uint64_t start_() {
    unsigned int lo, hi;
    // Сериализация с CPUID перед RDTSC
    __asm__ __volatile__ (
        "cpuid\n\t"
        "rdtsc" : "=a" (lo), "=d" (hi) : : "%rbx", "%rcx"
    );
    return ((uint64_t)hi << 32) | lo;
}
```



по сути здесь происходит то же самое:





- `__asm__ __volatile__ (...)` : синтаксис ассемблерной вставки. __volatile__ запрещает компилятору удалять эту вставку и переносить её как не имеющую побочных эффектов, что для чтения счётчика существенно.

- `"cpuid\n\t"` : собственно ассемблерная инструкция cpuid.

- `"rdtsc"` : собственно ассемблерная инструкция rdtsc.

- `"=a" (lo), "=d" (hi)` : выходные операнды. они сообщают компилятору, что после выполнения ассемблерного кода регистр eax (обозначается a) будет содержать значение, которое нужно поместить в переменную lo, а регистр edx (обозначается d) содержит значение для переменной hi.

- `: : (Пустые входные операнды)` : инструкциям cpuid и rdtsc не нужны входные данные из переменных c. строго говоря, cpuid использует eax как номер листа, поэтому в аккуратном коде eax следует инициализировать явно.

- `:"%rbx", "%rcx"` : список clobbers. он сообщает компилятору, что регистры rbx и rcx (или их 32-битные части ebx и ecx) могут быть изменены ассемблерным кодом, хотя и не указаны как выходные операнды. cpuid изменяет все четыре регистра eax, ebx, ecx, edx. поскольку eax и edx указаны как выходные операнды (lo, hi), компилятор знает об их изменении, но ebx и ecx тоже изменяются, и компилятор должен это учитывать, чтобы не хранить в них другие значения.

- `return ((uint64_t)hi << 32) | lo;` : объединяет 32-битные половины (старшую hi и младшую lo) в одно 64-битное значение, поскольку rdtsc возвращает счётчик в паре регистров edx:eax.



пример для msvc:



```c

#include <stdio.h>
#include <intrin.h> // Для _rdtsc()

int main() {
    unsigned __int64 start_ticks, end_ticks;

    start_ticks = __rdtsc();

    // здесь тестируемый код или вызов функции
    for (long long i = 0; i <1000000000; i++) {
        // Делаем что-то
    }

    end_ticks = __rdtsc();

    unsigned __int64 elapsed_ticks = end_ticks - start_ticks;

    printf("Выполнено за %llu тактов процессора\n", elapsed_ticks);

    return 0;
}
```



несколько замечаний об использовании `__rdtsc()`. прежде всего, в версии для linux инструкция cpuid выполняется только при первом чтении, то есть при получении начального значения. при внеочередном исполнении инструкция `_rdtsc()`, читающая конечное значение, может выполниться раньше, чем завершатся некоторые инструкции измеряемого блока, выданные после последнего cpuid (или после `_rdtsc()` в функции start_). поэтому для максимально точной фиксации конца интервала иногда рекомендуется снова выполнять cpuid перед финальным `_rdtsc()`:



```c

#include <stdio.h>
#include <stdint.h>
#include <cpuid.h>       // Для функции __cpuid (GNU/Linux)
#include <x86intrin.h>   // Для _rdtsc() (GNU/Linux, включает интринсики x86)

static inline uint64_t rdtsc( void )
{
  int a, b, c, d;
  __cpuid( 0, a, b, c, d );
  return _rdtsc();
}

int main( void )
{
   uint64_t elapsed_ticks;

    elapsed_ticks = rdtsc(); // start_();
    // Ваш код или вызов функции здесь
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }
    elapsed_ticks = rdtsc() - elapsed_ticks ;

    printf("Выполнено за %lu тактов процессора\n", elapsed_ticks);
}
```



накладные расходы в этом случае выше: cpuid сама по себе занимает от десятков до сотен тактов, а под гипервизором вызывает выход в монитор виртуальных машин. для очень коротких измерений, где важна стоимость самого измерения, этой точностью иногда жертвуют ради минимизации накладных расходов. тем не менее для надёжного бенчмаркинга в общем случае вызов cpuid перед вторым _rdtsc() считается лучшей практикой.



для точной фиксации конца интервала часто рекомендуют инструкцию rdtscp вместо `RDTSC`. rdtscp дожидается завершения всех предыдущих инструкций перед чтением tsc, то есть даёт тот же эффект для предшествующего кода, что и связка `cpuid + _rdtsc()`. в отличие от cpuid она не препятствует раннему началу последующих инструкций, поэтому в документации intel для строгого замера после rdtscp ставят ещё и lfence или cpuid. пример применения в gcc:



```c

#include <stdio.h>
#include <stdint.h>
#include <cpuid.h>       // Для функции __cpuid (GNU/Linux)
#include <x86intrin.h>   // Для _rdtsc() (GNU/Linux, включает интринсики x86)


static inline uint64_t rdtsc( void )
{
  int a, b, c, d;

  __cpuid( 0, a, b, c, d );
  return _rdtsc();
}

int main( void )
{
    uint64_t elapsed_ticks, start_ticks, end_ticks;

    start_ticks = rdtsc(); // start_();
    // Ваш код или вызов функции здесь
    for (long long i = 0; i < 1000000000; i++) {
        // Делаем что-то
    }
    unsigned int aux; // Для ID процессора
    // Использование __rdtscp для конца измерения
    end_ticks = __rdtscp(&aux); // aux получит ID процессора

    elapsed_ticks = end_ticks - start_ticks;
    printf("Выполнено за %lu тактов процессора\n", elapsed_ticks);
}
```



в функцию `_rdtscp` передаётся адрес переменной (в данном случае aux), в которую записывается содержимое регистра ia32_tsc_aux; операционная система обычно хранит там логический идентификатор процессора (linux дополнительно кодирует номер узла numa). в многопоточных приложениях или при переключении контекста это позволяет отследить, на каком ядре выполнялся код, и отбросить замеры, в которых поток мигрировал между ядрами.
