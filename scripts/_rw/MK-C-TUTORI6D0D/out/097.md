если есть несколько файлов с исходным кодом, их можно вместе скомпилировать в один бинарный файл. например, есть два файла с исходным кодом **hello.c** и **app.c**. для компиляции обоих файлов в одно приложение все эти файлы передают компилятору:

```bash
gcc app.c hello.c -o app
```

либо по отдельности компилируют объектные файлы для обоих исходников и компонуют их в один исполняемый файл:

```bash


gcc -c hello.c -o hello.o

gcc -c app.c -o app.o

gcc app.o hello.o -o app
```

для компиляции в объектный файл применяется флаг **-c**. он останавливает цепочку на этапе трансляции в машинный код и не вызывает компоновщик. можно сократить, без явной компиляции основного файла в объектный файл:

```bash


gcc -c hello.c -o hello.o

gcc app.c hello.o -o app
```

во втором варианте gcc сам прогоняет app.c через компиляцию и сразу передаёт результат компоновщику вместе с уже готовым hello.o. в любом случае в результате компиляции создаётся один исполняемый файл, в который добавляется код из всех объектных файлов, участвующих в компиляции. это статическая схема: все определённые символы оказываются внутри одного образа.

на linux компилятор gcc также позволяет использовать другой подход: **dynamic linking** (динамическое связывание или динамическая компоновка). при динамическом связывании код библиотек не включается в приложение, библиотеки остаются отдельными файлами, а код приложения просто ссылается на них. они объединяются только во время (или иногда после) запуска программы. это более гибкий подход, поскольку если код находится в библиотеках, библиотеки можно обновлять отдельно от приложений. если в библиотеке возникла проблема с безопасностью, достаточно изменить саму библиотеку. это также экономит дисковое пространство, поскольку отдельные функции не копируются в каждую программу, а существуют только в одном месте файловой системы. эти библиотеки ещё называются **shared libraries** (общие или разделяемые библиотеки). на уровне формата elf зависимость записывается в динамическую секцию (теги вроде dt_needed), а адреса символов подставляет загрузчик.

в системе linux общие библиотеки также называются **shared objects** (общими объектами) и имеют расширение **.so**. аналогичные библиотеки есть в других системах: на windows это динамические библиотеки с расширением **.dll**, на mac: библиотеки с расширением **.dylib** (хотя также используется расширение **.so**).

по умолчанию внешние зависимости подключаются как разделяемые библиотеки динамически. простейшая программа в файле **app.c**:

```c


#include <stdio.h>



int main(void) 

{

    printf("Hello World\n");

    return 0;

}
```

здесь применяется библиотечная функция **printf**, которую программа не определяет и которая берётся извне. скомпилируем эту программу стандартным образом:

```bash
gcc app.c -o app
```

скомпилированный файл имеет небольшой размер (около 16 кб). теперь зависимости этого файла смотрит команда

```bash
ldd app
```

эта команда перечисляет все используемые библиотеки и места их загрузки в память (которые могут меняться при каждом вызове). результат выглядит так:

```bash


root@Eugene:~/asm# ldd app

        linux-vdso.so.1 (0x00007ffe643f7000)

        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fa9113e1000)

        /lib64/ld-linux-x86-64.so.2 (0x00007fa911615000)

root@Eugene:~/asm#
```

адреса в скобках: результат aslr, при следующем запуске они будут другими. самая последняя запись в этом списке представляет **загрузчик**

```bash
/lib64/ld-linux-x86-64.so.2
```

загрузчик: программа, которая читает файл программы и загружает его в память, а также любые связанные библиотеки. загрузчик обычно имеет имя **ld.so**. это библиотека, которая фактически сама загружает. фактически это сам исполняемый файл. его даже можно вручную запустить как самостоятельную программу: `/lib64/ld-linux-x86-64.so.2`. в elf путь к интерпретатору записан в сегменте pt_interp; ядро начинает выполнение именно с него, а не с `_start` приложения.

когда запускается исполняемый файл, фактически начинается выполнение загрузчика, которому в качестве параметра передаётся имя программы. например, команда

```bash
/lib64/ld-linux-x86-64.so.2 ./app
```

аналогично запустит и выполнит выше скомпилированное приложение.

следующая запись:

```bash
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fa9113e1000)
```

представляет библиотеку c версии 6. стрелка (`=>`) после имени библиотеки указывает, где в системе можно найти библиотеку. это позволяет исполняемому файлу узнать, на какую библиотеку ссылаться, а загрузчику динамической компоновки: где её найти. слева soname, справа реальный путь после поиска по правилам ld.so.cache и стандартных каталогов.

первая запись:

```bash
linux-vdso.so.1 (0x00007ffe643f7000)
```

представляет библиотеку "linux-vdso.so.1". это специальная библиотека, называемая библиотекой vdso и предоставляемая самим ядром linux. эта библиотека позволяет быстро выполнять определённые функции ядра, такие как функции времени, для доступа к которым не требуется какой-либо особый уровень привилегий. вызов этих функций позволяет получить общедоступную системную информацию без фактического вызова системного вызова. vdso отображается в адресное пространство процесса ядром, отдельного файла на диске у неё нет, поэтому у записи ldd нет стрелки с путём.

весь используемый приложением функционал можно поместить непосредственно в исполняемый файл. для этого при компоновке применяется флаг **-static**:

```bash


root@Eugene:~/asm# gcc -static app.c -o app

root@Eugene:~/asm# ldd app

        not a dynamic executable

root@Eugene:~/asm#
```

в этом случае исполняемый файл будет занимать гораздо больше места, 800-900 кб, но не будет иметь внешних зависимостей, на что укажет результат команды **ldd**. это именно то, что происходит, когда несколько файлов при компиляции определяются в один. соответственно можно использовать статическую линковку, при которой файл не имеет зависимостей, но имеет большой объём. или динамическую линковку, когда файл имеет зависимости, которые нужно учитывать, но его размер гораздо меньше. если есть приложения, которые используют одни и те же разделяемые библиотеки, выгода в плане экономии памяти ещё больше: страницы libc разделяются между процессами на уровне виртуальной памяти.

### определение своей библиотеки

ниже: как создать свою разделяемую библиотеку. файл **hello.c** будет представлять код разделяемой библиотеки

```c


#include <stdio.h>



extern char* message;



void print_data(int value) 

{

    printf("value: %d\n", value );

    printf("message: %s\n", message);

}
```

здесь объявлена внешняя переменная message, которая определена где-то во внешнем коде. также для теста определена функция print_data, которая выводит на консоль значение параметра и переменной message. разделяемая библиотека может предоставлять некоторый функционал, но при этом сама может использовать какие-то внешние данные или функции. символ `message` останется неопределённым в .so и будет разрешён загрузчиком из объекта приложения (или другой библиотеки) в момент запуска.

скомпилируем этот файл в разделяемую библиотеку. сначала команда

```bash


gcc -c -fPIC  hello.c -o hello.o
```

для создания приложения, в котором код не зависит от позиции (position independent code), применяется флаг **-fPIC**. при работе с разделяемыми библиотеками загрузчик может загружать их в любое место адресного пространства. это одна из мер безопасности, которые обычно принимают дистрибутивы linux: рандомизация адресных пространств (aslr, address space layout randomization), чтобы библиотеки и части приложения можно было загружать в любое место в памяти. это уменьшает вероятность того, что злоумышленник узнает точное расположение частей приложения в памяти. но это означает, что библиотеки и приложение должны быть написаны специально, чтобы загрузка их в память не приводила к ошибкам. данный тип кода приложения известен как позиционно-независимый код или pic (position-independent code). поэтому для компиляции библиотек применяется флаг **-fPIC**. практически pic обращается к глобальным данным через таблицу got и к внешним функциям через plt, а не через абсолютные адреса.

в итоге будет сгенерирован объектный файл **hello.o**. далее для создания собственно разделяемой библиотеки выполняется команда:

```bash


root@Eugene:~/asm# gcc -shared hello.o -o hello.so
```

при компиляции разделяемой библиотеки линковщику передаётся флаг **-shared**. в итоге будет создан файл **hello.so**, который можно динамически подключать к приложению при компиляции.

для тестирования библиотеки определяется главный файл приложения **app.c** со следующим кодом:

```c


extern void print_data(int);



char* message = "Hello";



int main(void) 

{

    print_data(22);

    return 0;

}
```

здесь объявляется внешняя функция print_data и определяется глобальная переменная message, которую будет использовать разделяемая библиотека. в функции main вызывается функция print_data из библиотеки. компиляция программы:

```bash


gcc -c app.c -o app.o

gcc app.o hello.so -o app
```

вторая команда передаёт линковщику объектный файл app.o и файл библиотеки hello.so и создаёт исполняемый файл приложения: файл **app**. в бинарнике появится зависимость от hello.so; сам код print_data в app не копируется. запуск этого файла:

```bash


root@Eugene:~/asm# ./app

./app: error while loading shared libraries: hello.so: cannot open shared object file: No such file or directory
```

загрузчик не может найти библиотеку "hello.so". по умолчанию поиск библиотек выполняется в некоторых стандартных каталогах операционной системы, в частности в каталоге /lib, либо в каталогах, которые установлены в переменной окружения **LD_LIBRARY_PATH**. наша библиотека располагается не в этих каталогах, а в текущем каталоге, где также находится исполняемый файл **app**. поэтому переменной LD_LIBRARY_PATH передаётся путь к текущему каталогу, и приложение запускается повторно:

```bash


root@Eugene:~/asm#  export LD_LIBRARY_PATH=.

root@Eugene:~/asm# ./app

value: 22

message: Hello

root@Eugene:~/asm#
```

поиск начинается с каталогов, определённых в LD_LIBRARY_PATH, и продолжается до стандартных каталогов. точка означает текущий рабочий каталог на момент запуска, не каталог самого исполняемого файла.

полный консольный вывод:

```bash


root@Eugene:~/asm# gcc -c -fPIC  hello.c -o hello.o

root@Eugene:~/asm# gcc -shared hello.o -o hello.so

root@Eugene:~/asm# gcc -c app.c -o app.o

root@Eugene:~/asm# gcc app.o hello.so -o app

root@Eugene:~/asm# ./app

./app: error while loading shared libraries: hello.so: cannot open shared object file: No such file or directory

root@Eugene:~/asm#  export LD_LIBRARY_PATH=.

root@Eugene:~/asm# ./app

value: 22

message: Hello

root@Eugene:~/asm#
```

если посмотреть на применяемые приложением зависимости, в списке окажется библиотека hello.so:

```c


root@Eugene:~/asm# ldd app

        linux-vdso.so.1 (0x00007fff3193e000)

        hello.so => ./hello.so (0x00007fd953be2000)

        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007fd9539b5000)

        /lib64/ld-linux-x86-64.so.2 (0x00007fd953bee000)

root@Eugene:~/asm#
```
