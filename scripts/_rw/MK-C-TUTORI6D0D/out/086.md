для создания многопоточных приложений, выполняющих действия параллельно, в языке c обычно используются потоки `pthreads`, но параллелизм этим api не исчерпывается. для той же цели применяется библиотека openmp. openmp относится к модели fork-join: компилятор по директивам порождает команду потоков, они выполняют общую область, затем снова сходятся. в отличие от явного api pthread программист описывает намерение (какие циклы и области параллельны), а отображение на потоки берёт на себя среда выполнения.

для применения openmp не нужно включать какие-либо файлы заголовков, если сами функции openmp не используются. вместо этого применяются прагмы (директивы `pragma`). небольшой пример:

```c


#include <unistd.h<

#include <stdio.h>



int main(void)

{

  static const char str[] = "Hello enoobis.ru\n";



  // Используются все доступные процессоры

  #pragma omp parallel

  write(STDOUT_FILENO, str, sizeof str - 1);

}
```

разбор кода. сначала определяется строка, которую для примера выводят на консоль:

```c
static const char str[] = "Hello enoobis.ru\n";
```

далее используется прагма:

```c
#pragma omp parallel
```

эта директива создаёт параллельную область: каждый поток исполняет одну и ту же инструкцию, расположенную сразу после директивы. число потоков по умолчанию совпадает с числом логических процессоров либо берётся из переменной окружения `OMP_NUM_THREADS`.

далее идёт низкоуровневый системный вызов для вывода ранее определённой строки в стандартный вывод (stdout).

```c
write(STDOUT_FILENO, str, sizeof str - 1)
```

запуск кода, например, компилятором gcc (предполагается, что код расположен в файле app.c):

```bash


eugene@Eugene:/workspace/c$ gcc -fopenmp app.c -o app && ./app

Hello enoobis.ru

Hello enoobis.ru

Hello enoobis.ru

Hello enoobis.ru

..................

Hello enoobis.ru

eugene@Eugene:/workspace/c$
```

при использовании компиляторов gcc или clang нужно явно указать флаг -fopenmp. без этого флага директивы `#pragma omp` игнорируются, программа остаётся однопоточной, диагностика при этом может отсутствовать.

при выполнении создаётся несколько потоков, обычно столько, сколько ядер у процессора. каждый поток одновременно вызывает функцию `write` и выводит строку "Hello enoobis.ru\n" на консоль. в результате на экране появляется несколько строк, выведенных параллельно.

для вывода на консоль здесь применяется не стандартный `printf`, а прямой вызов в системный буфер вывода через `write`. поскольку write небуферизованный, он работает атомарно на уровне системных вызовов (в отличие от printf), поэтому каждая строка скорее всего будет выведена полностью, без перемешивания символов. если бы использовался `printf`, вывод мог бы перемешиваться, потому что `printf` использует буферизацию и не является потокобезопасным. стандарт iso c не требует потокобезопасности stdio; реализация может сериализовать вызовы, но рассчитывать на это нельзя.

### директивы openmp

при работе с openmp применяется ряд директив. некоторые из них:

```c


#pragma omp parallel

#pragma omp simd

#pragma omp for
```

при использовании директив openmp после `#pragma` сначала идёт omp, затем указывается директива openmp:

- `#pragma omp parallel` эта директива создаёт параллельную область: несколько потоков начинают выполнение кода внутри этой области. каждый поток исполняет одну и ту же копию кода.

- `#pragma omp simd` эта директива указывает компилятору векторизовать (simd: single instruction, multiple data) следующий цикл: выполнять одну инструкцию одновременно над множеством данных, используя векторные инструкции cpu (например, sse/avx).

- `#pragma omp for` обозначает, что итерации следующего за директивой цикла должны быть распределены между потоками. обычно используется внутри parallel.

директивы можно сочетать, например, `parallel` и `for`:

```c
#pragma omp parallel for
```

комбинированная форма создаёт параллельную область и сразу распределяет итерации цикла, без отдельного вложенного `#pragma omp for`. ниже: некоторые сценарии применения директив openmp.

### параллельная обработка циклов

директива for предназначена для использования с `parallel` и служит для разветвления текущего потока на дополнительные n-1 потоков, где n: количество итераций цикла. если n больше количества логических процессоров, n будет соответствовать этому значению, и тогда получится m групп по n потоков в последовательности, где m: количество итераций, делённое на максимальное количество потоков. иначе говоря, среда ограничивает фактическое число рабочих потоков аппаратной шириной, а итерации планировщик раздаёт этим потокам. пример:

```c


#include <stdio.h>



int main( void )

{

  int i;



  // Используем 8 процессоров (создаст 7 новых потоков + основной)

  #pragma omp parallel for

  for ( i = 0; i < 8; i++ )

    printf( "%d\n", i );

}
```

директива openmp `parallel for` делит итерации цикла for между несколькими потоками. каждый поток получает своё значение счётчика i в диапазоне от 0 до 7. openmp по умолчанию использует число потоков, равное количеству логических ядер, либо значение, заданное в omp_num_threads. переменная цикла при такой директиве становится private: у каждого потока своя копия i. пример консольного вывода:

```bash


eugene@Eugene:/workspace/c$ gcc -fopenmp app.c -o app && ./app

1

3

2

4

7

5

0

6

eugene@Eugene:/workspace/c$
```

порядок, в котором потоки выполняются, не гарантируется. если нужен правильный порядок, необходимо использовать директиву ordered:

```c


#include <stdio.h>



int main( void )

{

  int i;



  // упорядоченный вывод

  #pragma omp parallel for ordered

  for (i = 0; i < 8; i++ )

    #pragma omp ordered

    printf( "%d\n", i );

}
```

первой директивой `#pragma` openmp сообщается, что цикл for распараллелен и внутри блока цикла есть выражения (здесь вызов функции `printf()`), которые должны быть выполнены по порядку. чтобы указать, какие выражения должны быть упорядочены, к ним применяется вторая директива `#pragma`: `#pragma omp ordered`. внутри цикла вполне могут быть выражения, которые выполняются не по порядку, и другие, которые выполняются по порядку. область `ordered` сериализует только помеченный фрагмент и только в порядке итераций; остальной код итерации может идти параллельно.

```bash


eugene@Eugene:/workspace/c$ gcc -fopenmp app.c -o app && ./app

0

1

2

3

4

5

6

7
```

### векторизация и simd

директива `#pragma omp simd` применяется для векторизации цикла. она указывает компилятору векторизовать цикл, используя simd-инструкции процессора (например, avx, sse). она **не создаёт потоки**, как `#pragma omp parallel`, а применяет одну инструкцию к множеству данных одновременно. это уровень внутри одного потока: данные укладываются в векторные регистры cpu. пример: операция сложения массивов.

```c


#include <stdio.h>

#include <omp.h>



int main(void)

{

    const int N = 8;

    float a[N], b[N], c[N];



    // Инициализация

    for (int i = 0; i < N; i++) {

        a[i] = i;

        b[i] = i * 2;

    }



    // Векторизуемый цикл сложения

    #pragma omp simd

    for (int i = 0; i < N; i++) {

        c[i] = a[i] + b[i];

    }



    // Вывод результата

    for (int i = 0; i < N; i++) {

        printf("c[%d] = %.1f\n", i, c[i]);

    }



    return 0;

}
```

для компиляции применяется флаг -O2 или выше, чтобы компилятор действительно применил векторизацию:

```bash


eugene@Eugene:/workspace/c$ gcc -O2 -fopenmp app.c -o app && ./app

c[0] = 0.0

c[1] = 3.0

c[2] = 6.0

c[3] = 9.0

c[4] = 12.0

c[5] = 15.0

c[6] = 18.0

c[7] = 21.0

eugene@Eugene:/workspace/c$
```

директива `omp simd` применяется, когда есть простые циклы над массивами (арифметика, копирование и т.п.), либо когда надо ускорить код за счёт векторизации, без параллельных потоков. цикл должен быть канонической формы без зависимостей между итерациями, иначе векторизация может быть отвергнута компилятором.

### функции openmp

если нужно использовать специфические функции openmp, необходимо подключить заголовочный файл omp.h. пример: встроенная функция omp_get_thread_num(), которая возвращает номер текущего потока. идентификатор лежит в диапазоне от 0 до `omp_get_num_threads() - 1`; нулевой поток: master исходного потока, вошедшего в параллельную область.

```c


#include <stdio.h>

#include <omp.h>



int main( void )

{

  #pragma omp parallel

    {

        int tid = omp_get_thread_num();

        printf("Thread %d: Hello\n", tid);

    }

}
```

### критическая секция

при параллельном выполнении следует помнить, что некоторые стандартные функции, как, например, функции вывода `printf()` или `puts()`, **не потокобезопасны**. `printf/puts` используют буферизацию, и их вызовы не синхронизируются между потоками по умолчанию. это может привести к перемешиванию вывода, повреждённым строкам (например, "HeHlellollo") или даже потере части вывода в редких случаях.

чтобы решить эту проблему, применяется ещё одна директива: `#pragma omp critical`. она используется для **синхронизации потоков** и гарантирует, что **только один поток заходит в критическую секцию в каждый момент времени**:

```c


#pragma omp critical

{

    // Этот блок выполняется ОДНИМ потоком за раз

}
```

использование этой директивы позволяет **предотвратить одновременный доступ** к общим ресурсам, таким как файлы, переменные, буферы вывода (printf, puts) и т.п. unnamed critical секция в программе одна: все такие блоки взаимно исключают друг друга. именованные секции (`critical(name)`) независимы.

пример: конкурентный доступ к `puts`:

```c


#include <stdio.h>



int main(void)

{

    const char str[] = "Hello";

    #pragma omp parallel for

    for (int i = 0; i < 8; i++) {

        #pragma omp critical

        {

            puts(str);

        }

    }

    return 0;

}
```

без директивы `critical` вызовы `puts()` из разных потоков могут перемешиваться, т.к. stdout не потокобезопасен.

с `critical` потоки выводят по очереди. `puts()` выполняется атомарно (одним потоком за раз).

при всех плюсах есть и минусы: это замедляет производительность, если использовать слишком часто, потоки начинают ждать друг друга. поэтому критическую секцию сужают до минимально необходимого кода. для счётчиков с ассоциативной операцией openmp даёт отдельную конструкцию reduction, которая дешевле глобальной критической секции.
