большая часть объектов в программе на c# относится к управляемому коду, managed-коду. временем их жизни распоряжается clr, а недоступные экземпляры забирает сборщик мусора. рядом встречаются объекты, которые держат неуправляемые ресурсы: открытые файлы, соединения с базами данных, сетевые подключения. такие ресурсы получены через api операционной системы. сборщик умеет освободить управляемую оболочку, но не знает, каким вызовом закрывается конкретный ресурс операционной системы. освобождение приходится описывать в самом коде.

для этого у класса есть два механизма:

- деструктор

- реализация интерфейса `System.IDisposable`

### создание деструкторов

деструктор знаком по c++. его имя совпадает с именем класса, как у конструктора, и перед именем стоит тильда (`~`).

деструктор объявляется только в классе. в отличие от конструктора у него не бывает модификатора доступа и параметров. в одном классе допускается только один деструктор.

простейший деструктор в классе `Person`:

```c#


class Person

{

    public string Name { get;}

    public Person(string name) => Name = name;



    ~Person()

    {

        Console.WriteLine($"{Name} has deleted");

    }

}
```

в этом деструкторе на консоль выводится строка о том, что объект удалён. так сделано для наблюдения за моментом финализации. в рабочей программе в деструктор помещают освобождение неуправляемых ресурсов.

при сборке мусора clr вызывает не деструктор как отдельный метод исходного текста, а метод **Finalize**. компилятор c# превращает деструктор в конструкцию, эквивалентную следующей:

```c#


protected override void Finalize()

{

    try

    {

        // здесь идут инструкции деструктора

    }

	finally

	{

		base.Finalize();

	}

}
```

тело деструктора попадает в блок `try`. в `finally` вызывается `base.Finalize()`, поэтому финализация базового класса выполняется даже тогда, когда в теле деструктора возникло исключение. метод `Finalize` объявлен в `Object`, общем базовом классе всех типов, но переопределить его обычным синтаксисом `override` нельзя. единственная предусмотренная форма реализации проходит через объявление деструктора.

программа с классом `Person` после завершения может напечатать сообщение об удалении объекта `tom`:

```c#


Test();        

GC.Collect();   // очистка памяти под объект tom

Console.Read(); // ставим задержку



void Test()

{

    Person tom = new Person("Tom");

}



public class Person

{

    public string Name { get;}

    public Person(string name) => Name = name;



    ~Person()

    {

        Console.WriteLine($"{Name} has been deleted");

    }

}
```

выход из `Test` удаляет из стека ссылку на объект `Person` в куче, но деструктор из-за этого не вызывается сразу. момент финализации определяет сборщик. полная очистка памяти процесса гарантировалась при завершении программы в прежних версиях среды. начиная с .net 5 деструкторы при завершении процесса уже не вызываются. поэтому в примере память просят собрать явно, методом `GC.Collect`, а вызов деструктора удерживают задержкой `Console.Read()`: метод ждёт ввода и не даёт процессу завершиться раньше финализации.

на уровне структур сборщика это устроено так. при размещении объекта в куче clr проверяет, есть ли у типа метод `Finalize`. если метод есть, указатель на объект заносится в очередь финализации. когда сборщик признаёт объект мусором и видит у него `Finalize`, объект переносится во вторую таблицу, очередь объектов, ожидающих финализации, и остаётся достижимым для потока финализации. окончательно память освобождается лишь на следующем проходе сборщика, после того как `Finalize` уже отработал. из-за этого объект с деструктором переживает как минимум одну лишнюю сборку.

точное время вызова деструктора не определено. для двух связанных объектов порядок финализации тоже не гарантируется. если объект `A` хранит ссылку на объект `B` и у обоих есть деструкторы, деструктор `B` может уже завершиться к тому моменту, когда деструктор `A` только начнёт работу. опираться в деструкторе `A` на поля `B` нельзя.

отсюда возникает практическое ограничение. деструктор не подходит, когда неуправляемые ресурсы нужно отдать в определённый момент, а не когда-нибудь на потоке финализации. для детерминированного освобождения применяется второй механизм, интерфейс `IDisposable`.

### интерфейс idisposable

интерфейс `IDisposable` объявляет один метод, **Dispose**. в реализации класса этот метод освобождает неуправляемые ресурсы. вызов выглядит так:

```c#


Test();



void Test()

{

    Person? tom = null;

    try

    {

        tom = new Person("Tom");

    }

    finally

    {

        tom?.Dispose();

    }

}



public class Person : IDisposable

{

    public string Name { get;}

    public Person(string name) => Name = name;



    public void Dispose()

    {

        Console.WriteLine($"{Name} has been disposed");

    }

}
```

здесь использована конструкция `try...finally`. по основному сценарию она делает то же, что и две следующие строки:

```c#


Person tom = new Person("Tom");

tom.Dispose();
```

для вызова `Dispose` предпочтительна именно `try...finally`. если между созданием объекта и вызовом `Dispose` возникнет исключение, блок `finally` всё равно выполнится, и ресурсы будут освобождены. линейная пара вызовов до `Dispose` в этом случае не дойдёт.

### комбинирование подходов

у двух механизмов разные свойства. `Dispose` освобождает ресурсы в тот момент, когда это делает вызывающий код. вызывающий код при этом может забыть про вызов. деструктор срабатывает без участия вызывающего кода, но момент неизвестен, а сам объект дольше занимает память. оба свойства соединяет шаблон, который описывает microsoft. формализованная запись такая:

```c#


public class SomeClass: IDisposable

{

    private bool disposed = false;



    // реализация интерфейса IDisposable.

    public void Dispose()

    {

        // освобождаем неуправляемые ресурсы

        Dispose(true);

		// подавляем финализацию

        GC.SuppressFinalize(this);

    }



    protected virtual void Dispose(bool disposing)

    {

        if (disposed) return;

        if (disposing)

        {

            // Освобождаем управляемые ресурсы

        }

        // освобождаем неуправляемые объекты

        disposed = true;

    }



    // Деструктор

    ~SomeClass()

    {

        Dispose (false);

    }

}
```

логика очистки собрана в перегрузке `Dispose(bool disposing)`. значение `true` означает, что метод вызван из открытого `Dispose`. значение `false` означает, что метод вызван из деструктора.

деструктор передаёт `false`, чтобы не трогать управляемые ресурсы. к моменту финализации их состояние уже не гарантировано: они сами могут быть финализированы или ещё нет. за их освобождение отвечают их собственные деструкторы. неуправляемые ресурсы освобождаются при обоих значениях `disposing`, потому что кроме этого кода их некому закрыть.

флаг `disposed` не даёт выполнить очистку второй раз. повторный `Dispose` и поздний вызов из деструктора видят, что работа уже сделана, и выходят.

в открытом `Dispose` после очистки вызывается `GC.SuppressFinalize(this)`. метод вычёркивает объект из очереди финализации, и среда уже не вызывает для него `Finalize`. если деструктор в классе не объявлен, у объекта нет записи в этой очереди, и вызов `SuppressFinalize` ничего не меняет.

при таком шаблоне ресурсы освобождаются и тогда, когда автор вызывающего кода не вызвал `Dispose`: остаётся путь через деструктор. этот путь дороже и не привязан к моменту, когда ресурс перестал быть нужен.

#### общие рекомендации по использованию finalize и dispose

- деструктор стоит реализовывать только у тех объектов, которым он действительно нужен. метод `Finalize` удлиняет жизнь объекта минимум на одну сборку и загружает отдельный поток финализации, что заметно сказывается на производительности

- после `Dispose` вызов `Finalize` для этого объекта нужно подавить через `GC.SuppressFinalize`

- в производном классе, если базовый реализует `IDisposable`, переопределение обязано вызвать `Dispose` базового класса:

```c#


public class Derived: Base

{

    private bool IsDisposed = false;



    protected override void Dispose(bool disposing)

    {

        if (IsDisposed) return;

        if (disposing)

        {

			// Освобождение управляемых ресурсов

		}

        IsDisposed = true;

		// Обращение к методу Dispose базового класса

        base.Dispose(disposing);

    }

}
```

- предпочтителен комбинированный шаблон, в котором есть и открытый `Dispose`, и деструктор

открытый `Dispose` в шаблоне не является виртуальным. точка расширения для наследника называется `Dispose(bool)` и объявлена как `protected virtual`. наследник переопределяет именно её, освобождает свои ресурсы и передаёт вызов базовому методу. для необработанных дескрипторов операционной системы в современном .net ту же роль обычно играет `SafeHandle`: у него есть критический финализатор, и рукописный деструктор для самого дескриптора уже не нужен. шаблон выше остаётся общей схемой, когда класс владеет и управляемыми, и неуправляемыми ресурсами сразу.
