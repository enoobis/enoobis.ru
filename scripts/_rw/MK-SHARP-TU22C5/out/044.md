помимо обычных значений чисел и строк в c# есть особое значение `null`. оно обозначает отсутствие значения как такового, отсутствие данных. до введения более строгой модели ссылок `null` выступал значением по умолчанию для ссылочных типов: переменная ссылочного типа могла не указывать ни на какой объект.

до версии c# 8.0 любому ссылочному типу разрешалось присваивать `null` без дополнительной пометки:

```c#


string name = null;

Console.WriteLine(name);
```

начиная с c# 8.0 в язык введены ссылочные nullable-типы (nullable reference types) и nullable-контекст (nullable aware context), в котором эти типы используются. контекст разделяет на уровне статической проверки ссылки, которым по контракту разрешён `null`, и ссылки, которые `null` содержать не должны. во время выполнения отдельного представления у nullable-ссылки нет: `string` и `string?` являются одним типом clr. знак `?` остаётся аннотацией компилятора и записывается в метаданные сборки, чтобы анализ был виден и в других сборках.

чтобы переменная или параметр ссылочного типа допускали присваивание `null`, после имени типа ставится знак `?`:

```c#


string? name = null;

Console.WriteLine(name);	// ничего не выведет
```

встроенный метод `Console.ReadLine()`, который считывает с консоли строку, возвращает именно `string?`. отсутствие введённой строки он выражает значением `null`, поэтому тип `string` без `?` для результата этого метода не обещается:

```c#
string? name = Console.ReadLine();
```

значение `null` нужно в тех ситуациях, где объект может быть не задан. стандартный пример даёт база данных, в которой допустимо отсутствие значения. заранее неизвестно, что вернёт запрос: определённое значение или `null`.

подобные ссылочные типы, допускающие `null`, доступны только в nullable-контексте. для него характерны следующие правила:

- переменную ссылочного типа без `?` следует инициализировать конкретным значением, присваивать ей `null` не следует

- переменной ссылочного nullable-типа можно присвоить `null`, но перед использованием значение необходимо проверить на `null`

начиная с .net 6 и c# 10 nullable-контекст по умолчанию распространяется на все файлы кода проекта. сам механизм появился в c# 8.0, а в шаблонах проектов с .net 6 элемент `<Nullable>` со значением `enable` включён изначально. если набрать в visual studio 2022 для проекта .net 6 прежний пример с присваиванием `null` переменной типа `string`, компилятор покажет предупреждение:

nullable-контекст остаётся параметром, которым управляют на уровне проекта. файл проекта открывается двойным щелчком левой кнопки мыши по проекту либо правым щелчком и пунктом **Edit Project File** в появившемся меню:

![nullable enable в c# в visual studio](/uploads/course-lectures/38f4e04bfa812770fff94079542bf4f1bbfafdc3.png)

visual studio открывает файл проекта, который выглядит примерно так:

```xml


<Project Sdk="Microsoft.NET.Sdk">



  <PropertyGroup>

    <OutputType>Exe</OutputType>

    <TargetFramework>net6.0</TargetFramework>

    <ImplicitUsings>enable</ImplicitUsings>

    <Nullable>enable</Nullable>

  </PropertyGroup>



</Project>
```

здесь строка

```xml
<Nullable>enable</Nullable>
```

точнее элемент `<Nullable>` со значением `enable`, указывает, что nullable-контекст распространяется на весь проект.

опасность `null` в том, что значение означает отсутствие данных, а обращение к члену по такой ссылке не имеет получателя. пусть извне получена строка и у неё вызывается операция. в примере ниже у строки вызывается метод `ToUpper()`, который переводит все символы строки в верхний регистр:

```c#


string name = null;

PrintUpper(name);  // ! NullReferenceException



void PrintUpper(string text)

{

    Console.WriteLine(text.ToUpper());

}
```

при выполнении вызова `PrintUpper(name)` возникает исключение `NullReferenceException`, и программа аварийно завершает работу. ситуация выглядит искусственной, потому что в функцию явно передаётся `null`. в реальном коде данные приходят извне: из базы данных, из сети и из других модулей. есть ли значение фактически, вызывающему коду может быть неизвестно. ссылочные nullable-типы частично закрывают эту ситуацию. именно частично: предупреждение не мешает скомпилировать и запустить программу выше. nullable-контекст при этом включает статический анализ, и по нему видны участки, на которых возможно `NullReferenceException`.

есть вероятность, что microsoft изменит отношение к `null` и `NullReferenceException` и в будущих версиях превратит подобные предупреждения в ошибки компиляции. код, уже согласованный с анализатором, к такому изменению готов.

предыдущий пример записывается так:

```c#


string? name = null;

PrintUpper(name);  // 



void PrintUpper(string? text)

{

    Console.WriteLine(text.ToUpper());

}
```

статический анализ указывает, что в методе `PrintUpper` ситуация потенциально опасна: параметр `text` может быть равен `null`, а метод `ToUpper()` вызывается без предшествующей проверки.

#### отключение nullable-контекста

для отключения nullable-контекста в файле конфигурации проекта достаточно изменить значение параметра `Nullable`, например на `disable`:

```xml


<Project Sdk="Microsoft.NET.Sdk">



  <PropertyGroup>

    <OutputType>Exe</OutputType>

    <TargetFramework>net6.0</TargetFramework>

    <ImplicitUsings>enable</ImplicitUsings>

    <Nullable>disable</Nullable>

  </PropertyGroup>



</Project>
```

после отключения в файлах кода проекта ссылочные nullable-типы больше не используются как контракт анализатора, и встроенный статический анализ потенциально опасных ситуаций с `NullReferenceException` недоступен. присваивание `null` обычной ссылке снова проходит без предупреждения.

#### nullable-контекст на уровне участка кода

nullable-контекст включается и на уровне отдельных участков кода директивой `#nullable enable`. пусть глобально, на уровне проекта, контекст отключён:

```xml
<Nullable>disable</Nullable>
```

в файле `Program.cs` тогда записывается следующий код:

```c#


#nullable enable // включаем nullable-контекст на уровне файла



string? name = null;



PrintUpper(name);



void PrintUpper(string? text)

{

    Console.WriteLine(text.ToUpper());

}
```

первая строка включает nullable-контекст на уровне всего файла. директива действует на последующий текст, пока другая директива не сменит режим.

### оператор ! (null-forgiving operator)

оператор `!` (null-forgiving operator) указывает статическому анализу, что переменная ссылочного типа не равна `null`:

```c#


string? name = null;



PrintUpper(name!);



void PrintUpper(string text)

{

    if(text == null) Console.WriteLine("null");

    else Console.WriteLine(text.ToUpper());

}
```

если записать `PrintUpper(name)` без оператора `!`, компилятор выдаст предупреждение: аргумент имеет тип `string?`, параметр ожидает `string`. в самом методе значение проверяется на `null`, поэтому передача `null` к сбою не приводит. оператор убирает предупреждение, которое в этой точке не соответствует уже выполненной проверке. на время выполнения он не влияет и никакой проверки не вставляет. выражение `name!` во время выполнения совпадает со значением `name`. если проверку в методе убрать и передать действительный `null`, `NullReferenceException` возникнет так же, как без этого оператора.

### исключение кода из nullable-контекста

директивой `#nullable disable` из nullable-контекста исключается отдельный фрагмент кода:

```c#


#nullable disable

	string text = null;	// здесь nullable-контекст не действует

#nullable restore



string? name = null;   // здесь nullable-контекст снова действует
```

любой код между директивами `#nullable disable` и `#nullable restore` исключён из nullable-контекста и статическому анализу не подлежит. `#nullable restore` возвращает контекст к значению, заданному в проекте. в примере проектный контекст включён, поэтому после `restore` проверка снова действует.
