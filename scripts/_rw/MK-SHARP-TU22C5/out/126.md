начиная с .net 9 во фреймворк добавлен api синхронизации: класс `System.Threading.Lock`. он защищает критическую секцию от гонки потоков за общий ресурс. в отличие от `Monitor`, `Lock` не занимает служебный блок синхронизации произвольного объекта. это отдельный примитив со своими методами входа и выхода. ниже несколько форм применения.

### с оператором lock

самая короткая запись использует `Lock` вместе с оператором `lock`. для выражения типа `Lock` компилятор c# раскрывает `lock` в `EnterScope` и освобождение области при выходе из блока, а не в `Monitor.Enter`.

```c#


int x = 0;  // некоторый общий ресурс

Lock _lockObj = new(); // объект-заглушка для синхронизации доступа

// запускаем пять потоков

for (int i = 1; i < 6; i++)

{

    Thread myThread = new(Print);

    myThread.Name = $"Поток {i}";

    myThread.Start();

}



void Print()

{

    lock(_lockObj)  // начало критической секции

    {

        x = 1;

        for (int i = 1; i < 5; i++)

        {

            Console.WriteLine($"{Thread.CurrentThread.Name}: {x}");

            x++;

            Thread.Sleep(100);

        }

    }  // завершение критической секции

}
```

пример устроен так же, как синхронизация оператором `lock` с произвольным объектом-заглушкой. сначала задаётся общий ресурс, доступ к которому нужно упорядочить, переменная `x`, и объект синхронизации типа `Lock`. для демонстрации запускаются пять потоков. каждый входит в общую секцию метода `Print`, где `x` читается и изменяется. поток, захвативший `_lockObj`, находится в критической секции один. остальные ждут освобождения `_lockObj`. при выходе из секции поток отпускает `_lockObj`, и в неё входит следующий. доступ поэтому сериализован:

```bash


Поток 1: 1

Поток 1: 2

Поток 1: 3

Поток 1: 4

Поток 1: 5

Поток 2: 1

Поток 2: 2

Поток 2: 3

Поток 2: 4

Поток 2: 5

Поток 4: 1

Поток 4: 2

Поток 4: 3

Поток 4: 4

Поток 4: 5

Поток 5: 1

Поток 5: 2

Поток 5: 3

Поток 5: 4

Поток 5: 5

Поток 3: 1

Поток 3: 2

Поток 3: 3

Поток 3: 4

Поток 3: 5
```

по консольному выводу виден синхронизированный доступ к переменной `x`: поток, вошедший в секцию, доводит свою печать до конца, и только потом блокировку получает другой поток. какой поток окажется первым, по-прежнему решает планировщик.

### метод enter()

вызов `Enter()` у объекта `Lock` обозначает начало критической секции. войти в неё может один поток. остальные ждут, пока этот поток не выйдет. выход выполняется методом `Exit()`:

```c#


int x = 0;  // некоторый общий ресурс

Lock _lockObj = new(); // объект-заглушка для синхронизации доступа

// запускаем пять потоков

for (int i = 1; i < 6; i++)

{

    Thread myThread = new(Print);

    myThread.Name = $"Поток {i}";

    myThread.Start();

}



void Print()

{

    _lockObj.Enter();;  // начало критической секции

    try

    {

        x = 1;

        for (int i = 1; i < 6; i++)

        {

            Console.WriteLine($"{Thread.CurrentThread.Name}: {x}");

            x++;

            Thread.Sleep(100);

        }

    }  

    finally { _lockObj.Exit(); } // завершение критической секции

}
```

выход из секции стоит в блоке `finally`. исключение внутри секции всё равно приводит к `Exit`, и блокировка не остаётся у потока, который уже не выполняет секцию. пара `Enter`/`Exit` обязана быть согласованной: каждый успешный `Enter` закрывается своим `Exit`. в примере `Enter` стоит до `try`, поэтому `finally` относится к телу секции после успешного входа.

### tryenter()

`TryEnter()` тоже пытается войти в критическую секцию и возвращает логическое значение, `true` или `false`. значение `true` означает, что текущий поток единственный держит блокировку и может выполнять секцию. значение `false` означает, что блокировка занята: поток не ждёт её освобождения и секцию не выполняет.

```c#


int x = 0;  // некоторый общий ресурс

Lock _lockObj = new(); // объект-заглушка для синхронизации доступа

// запускаем пять потоков

for (int i = 1; i < 6; i++)

{

    Thread myThread = new(Print);

    myThread.Name = $"Поток {i}";

    myThread.Start();

}





void Print()

{

    if (_lockObj.TryEnter())  // начало критической секции

    {

        try

        {

            x = 1;

            for (int i = 1; i < 6; i++)

            {

                Console.WriteLine($"{Thread.CurrentThread.Name}: {x}");

                x++;

                Thread.Sleep(100);

            }

        }  

        finally { _lockObj.Exit(); } // завершение критической секции

    }

}
```

консольный вывод:

```bash


Поток 1: 1

Поток 1: 2

Поток 1: 3

Поток 1: 4

Поток 1: 5
```

тело секции в этом запуске выполнил один поток. потоки стартуют вместе. первый, кому `TryEnter` вернул `true`, выполняет секцию. для остальных `_lockObj.TryEnter()` возвращает `false`: блокировка уже занята, они не входят в секцию и не встают в очередь. поэтому в выводе нет последовательностей остальных потоков. какой именно поток успеет первым, зависит от планировщика. исходный вывод показывает поток 1.

### enterscope()

метод `EnterScope()` входит в критическую секцию и является рекомендуемым способом с точки зрения microsoft. если блокировка уже захвачена, другие потоки ждут её освобождения, как при `Enter`. метод рассчитан на конструкцию `using`: возвращённая область освобождает блокировку в `Dispose`, а `using` вызывает `Dispose` при любом выходе из блока, включая исключение.

```c#


int x = 0;  // некоторый общий ресурс

Lock _lockObj = new(); // объект-заглушка для синхронизации доступа

// запускаем пять потоков

for (int i = 1; i < 6; i++)

{

    Thread myThread = new(Print);

    myThread.Name = $"Поток {i}";

    myThread.Start();

}





void Print()

{

    using (_lockObj.EnterScope())  // начало критической секции

    {

        x = 1;

        for (int i = 1; i < 6; i++)

        {

            Console.WriteLine($"{Thread.CurrentThread.Name}: {x}");

            x++;

            Thread.Sleep(100);

        }

    }  // завершение критической секции

}
```

вызывать `Exit()` здесь не нужно. выход из критической секции и снятие блокировки выполняет область, полученная из `EnterScope`, в конце `using`. консольный вывод снова показывает пять потоков по очереди, каждый со своей непрерывной последовательностью:
