при выполнении программы возникают ошибки, которые трудно предусмотреть, а иногда и вовсе невозможно предвидеть. при передаче файла по сети сетевое подключение может неожиданно оборваться. такие ситуации называются **исключениями**. язык c# предоставляет средства для обработки таких ситуаций. для этого предназначена конструкция **try...catch...finally**.

```c#


try

{

	

}

catch

{

	

}

finally

{

	

}
```

при использовании блока **try...catch..finally** вначале выполняются все инструкции в блоке **try**. если в этом блоке исключения не возникло, после его выполнения выполняется блок **finally**. затем конструкция try..catch..finally завершает работу.

если в блоке `try` возникает исключение, обычный порядок выполнения останавливается, и среда clr начинает искать блок **catch**, который может обработать данное исключение. если нужный блок `catch` найден, он выполняется, и после его завершения выполняется блок `finally`.

если нужный блок `catch` не найден, при возникновении исключения программа аварийно завершает своё выполнение.

поиск обработчика в clr табличный. у метода есть таблица защищённых областей: какие диапазоны инструкций покрыты `try`, какой `catch` их обрабатывает, какой `finally` обязан выполниться. при исключении среда сначала ищет подходящий обработчик по этой таблице, затем при раскрутке стека выполняет `finally` и только после этого входит в найденный `catch`.

следующий пример порождает такое исключение:

```c#


int x = 5;

int y = x / 0;

Console.WriteLine($"Результат: {y}");

Console.WriteLine("Конец программы");
```

здесь происходит деление числа на 0, что приводит к генерации исключения. при запуске приложения в режиме отладки visual studio показывает окно, которое информирует об исключении:

![исключения в c#](/uploads/course-lectures/b10bfe52a30713cd7f75d6078d04d715658e4cd8.png)

в этом окне видно, что возникло исключение типа `System.DivideByZeroException`, то есть попытка деления на ноль. пунктом `View Details` открывается более детальная информация об исключении.

для целочисленного деления это именно исключение: операция `/` над `int` при нулевом делителе завершается `DivideByZeroException`. деление `float` и `double` по ieee 754 исключения не генерирует, результат есть бесконечность или `NaN`. деление `decimal` на ноль по-прежнему порождает `DivideByZeroException`. в примере типы целочисленные, поэтому срабатывает исключительная ситуация, а не арифметика ieee.

дальше остаётся только завершить выполнение программы.

чтобы избежать подобного аварийного завершения, для обработки исключений используется конструкция **try...catch...finally**. пример переписывается так:

```c#


try

{

	int x = 5;

	int y = x / 0;

	Console.WriteLine($"Результат: {y}");

}

catch

{

	Console.WriteLine("Возникло исключение!");

}

finally

{

	Console.WriteLine("Блок finally");

}

Console.WriteLine("Конец программы");
```

исключение снова возникает в блоке `try`, потому что выполняется деление на ноль. выполнение доходит до строки

```c#
int y = x / 0;
```

и останавливается. clr находит блок **catch** и передаёт управление этому блоку.

после блока `catch` выполняется блок `finally`.

```consoletext


Возникло исключение!

Блок finally

Конец программы
```

программа по-прежнему не выполняет деление на ноль и не выводит результат этого деления, но уже не завершается аварийно: исключение обрабатывается в блоке `catch`, а код после всей конструкции продолжает работу. блок `finally` выполняется в обоих исходах, и когда `try` прошёл без исключения, и когда управление ушло в `catch`.

в этой конструкции обязателен блок **try**. при наличии блока `catch` блок `finally` можно опустить:

```c#


try

{

	int x = 5;

	int y = x / 0;

	Console.WriteLine($"Результат: {y}");

}

catch

{

	Console.WriteLine("Возникло исключение!");

}
```

и наоборот, при наличии блока `finally` можно опустить блок `catch` и не обрабатывать исключение:

```c#


try

{

	int x = 5;

	int y = x / 0;

	Console.WriteLine($"Результат: {y}");

}

finally

{

	Console.WriteLine("Блок finally");

}
```

с точки зрения синтаксиса c# такая конструкция корректна. отдельный `try` без `catch` и без `finally` языком запрещён: у защищённой области должен быть хотя бы один из этих блоков. но если `catch` опущен, clr не находит обработчик, исключение не обрабатывается, и программа аварийно завершается. `finally` при этой раскрутке всё равно выполняется, однако остановить само исключение он не может.

### обработка исключений и условные конструкции

ряд исключительных ситуаций разработчик может предвидеть заранее. пусть в программе есть метод, который принимает строку, конвертирует её в число и вычисляет квадрат этого числа:

```c#


Square("12"); // Квадрат числа 12: 144

Square("ab"); // !Исключение



void Square(string data)

{

    int x = int.Parse(data);

    Console.WriteLine($"Квадрат числа {x}: {x * x}");

}
```

если в метод передать не число, а строку, которая содержит нецифровые символы, программа завершится с ошибкой. для этой ошибки подходит блок `try..catch`. дешевле проверить допустимость преобразования до того, как исключение будет создано:

```c#


Square("12"); // Квадрат числа 12: 144

Square("ab"); // Некорректный ввод



void Square(string data)

{

    if (int.TryParse(data, out var x))

    {

        Console.WriteLine($"Квадрат числа {x}: {x * x}");

    }

    else

    {

        Console.WriteLine("Некорректный ввод");

    }

}
```

метод `int.TryParse()` возвращает `true`, если преобразование можно осуществить, и `false`, если нельзя. при допустимости преобразования переменная `x` содержит введённое число. возможная исключительная ситуация обрабатывается без `try...catch`.

с точки зрения производительности блоки `try..catch` дороже условных конструкций. само присутствие обработчика заставляет jit учитывать таблицу исключений, а создание и поиск исключения заметно тяжелее обычной ветки. поэтому там, где отказ можно распознать заранее, как при разборе строки, вместо `try..catch` используется условная конструкция. исключение остаётся для ситуаций, которые в этой точке программы не проверяются локальным условием, вроде обрыва соединения из первого примера.
