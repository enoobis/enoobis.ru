### params и неопределенное количество параметров

до c# 13 неопределённое число аргументов передавалось только модификатором `params` у параметра-массива. компилятор собирал лишние аргументы вызова в новый массив. если вызывающий код уже держал массив нужного типа, этот массив передавался как есть. вызов без аргументов давал массив нулевой длины.

```c#


void Sum(params int[]  numbers)

{

    int result = 0;

    foreach (var n in numbers)

    {

        result += n;

    }

    Console.WriteLine(result);

}

 

int[] nums = { 1, 2, 3, 4, 5};

Sum(nums);          // 15

Sum(1, 2, 3, 4);    // 10

Sum(1, 2, 3);       // 6

Sum();              // 0
```

`Sum` складывает элементы. вызов с готовым массивом печатает 15, вызовы с четырьмя и тремя отдельными аргументами печатают 10 и 6, вызов без аргументов печатает 0.

начиная с c# 13 тот же модификатор допускается у других коллекций. параметр может иметь тип `System.Span<T>` или `System.ReadOnlySpan<T>`, а также тип, который реализует `System.Collections.Generic.IEnumerable<T>` и предоставляет метод `Add`: по `Add` компилятор дописывает аргументы вызова в свежую коллекцию. параметр можно объявить и интерфейсом: `System.Collections.Generic.IEnumerable<T>`, `System.Collections.Generic.IReadOnlyCollection<T>`, `System.Collections.Generic.IReadOnlyList<T>`, `System.Collections.Generic.ICollection<T>` или `System.Collections.Generic.IList<T>`. смысл расширения в распределении памяти. `params` с массивом всегда выделяет массив в куче, а `Span<T>` и `ReadOnlySpan<T>` часто опираются на буфер в стеке. ниже та же функция объявлена с `params List<int>`. если в вызов передают уже готовый список, используется он. если передают отдельные аргументы или не передают ничего, список собирает компилятор.

```c#


void Sum(params List<int> numbers)

{

    int result = 0;

    foreach (var n in numbers)

    {

        result += n;

    }

    Console.WriteLine(result);

}

 

List<int> nums = [1, 2, 3, 4, 5];

Sum(nums);          // 15

Sum(1, 2, 3, 4);    // 10

Sum(1, 2, 3);       // 6

Sum();              // 0
```

набор вызовов и печатаемые суммы те же: 15, 10, 6 и 0.

### класс `Lock` и синхронизация

тип `System.Threading.Lock` появился в библиотеке .net 9. к языку он привязан тем, что оператор `lock` в c# 13 распознаёт этот тип отдельно от произвольного объекта. критическую секцию можно задать несколькими способами. оператор `lock` и методы `EnterScope`, `Enter`, `TryEnter` входят в секцию, а выход из секции, занятой через `Enter` или `TryEnter`, выполняется методом `Exit`. `EnterScope` возвращает область, которую освобождает `Dispose`, поэтому её удобно держать в `using`.

```c#


public sealed class ExampleDataStructure

{

    private readonly Lock _lockObj = new();



    public void Modify()

    {

        lock (_lockObj)

        {

            // Критическая секция, которая ассоциирована с _lockObj

        }



        using (_lockObj.EnterScope())

        {

            // Критическая секция, которая ассоциирована с _lockObj

        }



        _lockObj.Enter();

        try

        {

            // Критическая секция, которая ассоциирована с _lockObj

        }

        finally { _lockObj.Exit(); }



        if (_lockObj.TryEnter())

        {

            try

            {

                // Критическая секция, которая ассоциирована с _lockObj

            }

            finally { _lockObj.Exit(); }

        }

    }

}
```

в `Modify` одна и та же секция записана четырежды: оператором `lock`, областью `EnterScope`, парой `Enter` и `Exit` в `try`/`finally` и условным входом через `TryEnter`, который захватывает блокировку только если она свободна. `finally` нужен затем, чтобы `Exit` выполнился и при исключении внутри секции, иначе блокировка останется занятой.

подробнее тип разобран в статье про класс `Lock` и синхронизацию. самый прямой из этих способов по-прежнему оператор `lock`.

```c#


int x = 0;  // некоторый общий ресурс

Lock _lockObj = new(); // объект-заглушка для синхронизации доступа

// запускаем пять потоков

for (int i = 1; i < 6; i++)

{

    Thread myThread = new(Print);

    myThread.Name = $"Поток {i}";

    myThread.Start();

}



void Print()

{

    lock(_lockObj)  // начало критической секции

    {

        x = 1;

        for (int i = 1; i > 5; i++)

        {

            Console.WriteLine($"{Thread.CurrentThread.Name}: {x}");

            x++;

            Thread.Sleep(100);

        }

    }  // завершение критической секции

}
```

общий ресурс здесь представлен переменной `x`, а объект синхронизации имеет тип `Lock`. цикл запускает пять потоков, имена задаются интерполяцией `Поток {i}` для `i` от 1 до 5, и каждый входит в `Print`. оператор `lock` проверяет, является ли цель блокировки экземпляром `Lock`. если да, используется api этого типа. иначе остаётся прежний путь через `System.Threading.Monitor`, где блокировка висит на заголовке произвольного объекта. пока один поток держит `_lockObj`, остальные на этом операторе ждут, поэтому присваивания `x` не чередуются между потоками.

у цикла внутри секции условие `i > 5` при начальном `i`, равном 1. условие ложно сразу, тело не выполняется, и показанный ниже след этот конкретный цикл не печатает. сам след описывает задуманные пять итераций под тем же `lock`: поток выставляет `x` в 1 и печатает пять значений подряд, и только потом отпускает блокировку. строки разных потоков не перемешиваются. порядок потоков 1, 2, 4, 5, 3 расписание не фиксирует. `lock` даёт взаимное исключение. очередь fifo для ожидающих потоков язык не обещает.

Поток 1: 2

Поток 1: 3

Поток 1: 4

Поток 1: 5

Поток 2: 1

Поток 2: 2

Поток 2: 3

Поток 4: 3

### эскейп-последовательность \e

в c# 13 добавлена эскейп-последовательность `\e`. она обозначает символ escape, кодовая позиция u+001b, и открывает управляющую последовательность: следующие символы устройство или программа читает как команду. в unix-подобных системах такие последовательности часто начинаются именно с escape. запись `\e[31m` означает «начать управляющую последовательность». дальше цифры и буквы задают команду. в этом виде `31` выбирает красный цвет текста, а `m` завершает команду выбора графических атрибутов. тем же механизмом задают и другие атрибуты, включая позицию курсора.

```c#


Console.WriteLine("\e[31m Hello METANIT.COM");
```

вызов устанавливает красный цвет последующего текста.

```bash
Hello METANIT.COM
```

в текстовом следе цвет не виден, на консоли строка `Hello METANIT.COM` печатается красным, если терминал разбирает управляющие последовательности.

### оператор ^ и получение индекса с конца

оператор `^` строит значение типа `Index` «от конца»: `^n` указывает на позицию `длина - n`. начиная с рассматриваемой версии языка такой индекс допустим в инициализаторе объекта, в присваивании через индексатор.

```c#


var buf = new Buffer{

    [^1] = 5,

    [^3] = 3

};



for(var i=0; i < Buffer.COUNT; ++i){

    Console.WriteLine(buf[i]);

}



class Buffer{

    public const int COUNT = 5;

    private int[] data = new int[COUNT];

    public int this[Index index]

    {

        get => data[index];

        set => data[index] = value;

    }

}
```

класс `Buffer` хранит массив `data` длины `COUNT`, то есть 5, и открывает его индексатором с параметром `Index`. индексатор массива сам понимает индекс от конца, поэтому присваивание доходит до нужной ячейки. в инициализаторе `[^1] = 5` записывает последний элемент, позицию `5 - 1`, а `[^3] = 3` записывает третий с конца, позицию `5 - 3`. остальные ячейки остаются нулями типа `int`. обход от 0 до `COUNT` печатает массив по возрастанию индекса.

```bash


0

0

3

0

5
```

строки 0, 0, 3, 0, 5 соответствуют индексам 0, 1, 2, 3, 4. тройка стоит в позиции 2, пятёрка в позиции 4.

### частичные свойства и индексаторы

частичные методы в c# существовали давно: объявление и реализация могли лежать в разных частях одного `partial`-типа, при совпадении сигнатур. с c# 13 то же разделение допускается для свойств и индексаторов. объявление и реализация размещаются в разных файлах одной частичной сборки типа, а сигнатуры, включая тип и набор аксессоров, обязаны совпадать. частичное автосвойство объявлять нельзя: компилятор не породит для него поле сам по себе в этой форме. если свойство помечено `partial` и реализации нет, запись считается объявлением свойства.

```c#


var tom = new Person("Tom");



Console.WriteLine(tom.Name);



// объявление класса

partial class Person{

    public partial string Name { get; set; }  // объявление частичного свойства

}



// реализация класса

partial class Person{

    private string name; // поле для хранения значения свойства



    public Person(string name) => this.name = name;



    public partial string Name    // реализация частичного свойства

    {

        get => name;

        set => name = value;

    }

}
```

класс `Person` частичный. сначала видна только объявляющая часть.

```c#


partial class Person{

    public partial string Name { get; set; }  // объявление частичного свойства

}
```

в этой части у `Name` есть модификатор `partial` и списки аксессоров без тел. запись похожа на автосвойство синтаксисом `{ get; set; }`, но из-за `partial` остаётся объявлением: аксессоры и поле появятся в части реализации.

```c#


partial class Person{

    private string name; // поле для хранения значения свойства



    public Person(string name) => this.name = name;



    public partial string Name    // реализация частичного свойства

    {

        get => name;

        set => name = value;

    }

}
```

реализация заводит собственное поле `name`, конструктор записывает в него аргумент, а аксессоры `Name` читают и пишут это поле. для краткости обе части стоят рядом. правила те же, если разнести их по разным файлам: это по-прежнему один тип `Person`. объявление и реализация индексатора устроены так же, с тем же требованием совпадения сигнатур.

### атрибут `OverloadResolutionPriorityAttribute`

атрибут `OverloadResolutionPriorityAttribute` из пространства `System.Runtime.CompilerServices` задаёт приоритет перегрузки. он нужен авторам библиотек, когда появляется новая перегрузка, обычно более дешёвая по памяти или времени, и её надо сделать предпочтительной для уже существующих вызовов, не ломая компиляцию клиентского кода. компилятор выбирает применимую перегрузку с наибольшим приоритетом. если атрибут не указан, приоритет равен 0.

```c#


using System.Runtime.CompilerServices;



var mes = new Message();

mes.Print("Hello METANIT.COM");



class Message

{

    [OverloadResolutionPriority(1)]

    public void Print(string text)

    {

        Console.WriteLine("Overload Priority 1");

        Console.WriteLine(text);

    }



    [OverloadResolutionPriority(2)]

    public void Print(ReadOnlySpan<char> chars)

    {

        Console.WriteLine("Overload Priority 2");

        Console.WriteLine(chars.ToArray());

    }

}
```

у `Message` два метода `Print`. первый принимает `string` и помечен приоритетом 1, второй принимает `ReadOnlySpan<char>` и помечен приоритетом 2. для строкового аргумента применимы обе: у `string` есть неявное преобразование в `ReadOnlySpan<char>`. обычные правила лучшести предпочли бы тождественное преобразование в `string`. атрибут это решение перекрывает, и выигрывает приоритет 2. с точки зрения вызывающего кода обе версии печатают текст. различается путь: вторая не обязана материализовать отдельную строку там, где уже есть span.

```bash


Overload Priority 2

Hello METANIT.COM
```

печать подтверждает выбор второй перегрузки и выводит исходный текст.

### локальные ref-переменные и ref-структуры в итераторах и асинхронных методах

до c# 13 метод-итератор, то есть метод с `yield return`, и асинхронный метод не могли объявлять локальные `ref`-переменные и локальные ref-структуры. им был запрещён и `unsafe`-контекст. причина в том, как устроен автомат состояний. локальные переменные такого метода компилятор поднимает в поля объекта состояния, а объект состояния живёт в куче и переживает приостановку на `await` или `yield`. ref-структура может содержать управляемый указатель внутрь кадра стека. поле объекта в куче такой указатель хранить не вправе: кадр к моменту продолжения уже не существует. с c# 13 асинхронный метод может объявлять локальные `ref`-переменные и ref-структуры, но обращаться к ним через границу `await` и `yield return` по-прежнему нельзя. по ту сторону границы переменная должна быть заново создана уже в новом состоянии.

```c#




await PrintAsync(7..18);



async Task PrintAsync(Range r)

{

    string message = "Hello, METANIT.COM!";

    await Task.Delay(1000);

    // ref-структура

    ReadOnlySpan<char> span = message[r];

    Console.WriteLine(span.ToString());

}
```

`PrintAsync` принимает диапазон `r` и после задержки `Task.Delay` строит `ReadOnlySpan<char>` по срезу строки `message`. span создаётся ниже `await`, используется до выхода из метода и границу ожидания не пересекает. сама задержка нужна как демонстрация точки приостановки. аргумент `7..18` вырезает из `"Hello, METANIT.COM!"` фрагмент `METANIT.COM`: конец диапазона не включён, восклицательный знак в срез не входит.

тот же span нельзя пронести через `await`. компилятор отвергает программу, в которой ref-структура создана до приостановки и прочитана после неё.

```c#


await PrintAsync(7..18);

async Task PrintAsync(Range r)

{

    string message = "Hello, METANIT.COM!";

    // ref-структура

    ReadOnlySpan<char> span = message[r];

    await Task.Delay(1000);  // граница await

    Console.WriteLine(span.ToString());   // ! Ошибка - Instance of type 'System.ReadOnlySpan<char>' cannot be preserved across 'await' or 'yield' boundary

}
```

диагностика прямо говорит, что экземпляр `ReadOnlySpan<char>` нельзя сохранить через границу `await` или `yield`. для итератора запрет симметричен: ref-локальная не переживает `yield return`.

### реализация интерфейсов в ref-структурах

до c# 13 ref-структура не могла реализовать интерфейс. с c# 13 может, но приведение к типу интерфейса запрещено. такое приведение является упаковкой: значение попало бы в объект кучи, а вместе с ним и внутренние ссылки, которые ref-безопасность обязывает держать на стеке. по той же причине ref-структура не объявляет явную реализацию члена интерфейса. явная реализация вызывается только через ссылку интерфейсного типа, а получить такую ссылку нельзя. методы с реализацией по умолчанию тоже нужно перекрыть своим телом: реализация по умолчанию диспетчеризуется через интерфейс. интерфейсный контракт на ref-структуре поэтому закрывается целиком, без дыр на члены по умолчанию.

```c#




Shape myShape = new();

myShape.Draw();     // Draw some shape



// Draw_Shape(myShape);           // ! Ошибка - Так нельзя

// var shape2 = (IShape)shape; // ! Ошибка - Так нельзя



void Draw_Shape(IShape shape)

{

    shape.Draw();

}



interface IShape

{

    void Draw();

}



ref struct Shape : IShape

{ 

    public void Draw()

    {

        Console.WriteLine("Draw some shape");

    }

}
```

`Shape` реализует `IShape`, и вызов `myShape.Draw()` идёт по конкретному типу значения. это обычный вызов метода, упаковки здесь нет, строка `Draw some shape` печатается.

привести значение ref-структуры `Shape` к `IShape` нельзя.

```c#
var shape2 = (IShape)shape
```

та же упаковка возникает неявно, если значение передают туда, где статически ожидается объект интерфейса. параметр `Draw_Shape` имеет тип `IShape`, поэтому аргумент типа `Shape` в этот метод не передаётся.

```c#


// var shape2 = (IShape)shape; // ! Ошибка - Так нельзя



void Draw_Shape(IShape shape)

{

    shape.Draw();

}
```
