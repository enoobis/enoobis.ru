поставка интерпретатора python уже содержит набор модулей. их подключают импортом и вызывают из программы. часть этих модулей разбиралась в предыдущих лекциях. помимо модулей поставки есть большой корпус пакетов, которые развивает сообщество: компании и отдельные разработчики. такие пакеты тоже подключают импортом, но в поставку интерпретатора они не входят и ставятся отдельно.

установка и удаление пакетов выполняются менеджером пакетов. для python таких программ несколько, среди них pip, conda, pixi и uv. дальше рабочим инструментом выбран pip: это штатный менеджер поставки cpython, самый распространённый в повседневной работе, и в типичной установке он уже присутствует.

pip загружает дистрибутивы из pypi (python package index), основного публичного индекса пакетов python. на момент написания исходного текста в индексе было более 600000 проектов. индекс открыт по адресу [https://pypi.org/](https://pypi.org/). через веб-интерфейс находят проект, описание, историю версий и связанные файлы.

перед работой проверяют, что pip установлен. при установленной копии python менеджер обычно уже есть. проверка выполняется в терминале или в командной строке:

```bash
pip --version
```

при успехе команда печатает версию менеджера, каталог его установки и версию интерпретатора, с которым этот pip связан:

```bash


eugene@Eugene:~$ pip --version

pip 24.0 from /usr/lib/python3/dist-packages/pip (python 3.12)

eugene@Eugene:~$
```

строка `pip 24.0 from /usr/lib/python3/dist-packages/pip (python 3.12)` читается так: версия менеджера 24.0, каталог установки, интерпретатор python 3.12. каталог `dist-packages` на debian и ubuntu обычен для пакетов дистрибутива.

если команда `pip` оболочке неизвестна, та сообщает, что исполняемый файл не найден. в командной строке windows текст такой:

```bash


"pip" не является внутренней или внешней командой, исполняемой программой или пакетным файлом
```

тогда pip разворачивают модулем `ensurepip` из стандартной библиотеки. модуль кладёт в установку ту копию pip, которая приложена к данному интерпретатору (pep 453):

```bash
python -m ensurepip --upgrade
```

если pip уже стоит и нужна более новая версия самого менеджера, её ставят из индекса той же командой установки:

```bash
python -m pip install --upgrade pip
```

вызов `python -m pip` запускает модуль pip у того интерпретатора, который выбран именем `python`. при нескольких копиях python на `PATH` короткая команда `pip` может указывать на другую копию. форма `python -m pip` эту неоднозначность снимает.

### установка виртуальной среды

на linux, где пакеты ос ведутся своим менеджером (apt на ubuntu и debian, аналоги на других дистрибутивах), пакеты python через pip ставят в виртуальную среду. на современных выпусках ubuntu и debian к этому добавляется правило pip: системный интерпретатор помечен как внешне управляемый (pep 668), и запись в системный префикс отклоняется. каталог среды и каталог пакетов apt при этом различны, поэтому обновление ос не затирает дистрибутивы, поставленные в среду.

на windows установка в общий `site-packages` выбранного интерпретатора допустима. для работы с пакетами виртуальная среда и там остаётся рекомендуемой.

виртуальная среда (модуль `venv`, pep 405) даёт проекту собственный каталог `site-packages` и собственные команды `python` и `pip`. пакеты среды видны процессам её интерпретатора и в системную установку не попадают.

без среды пакеты, поставленные pip на windows, оказываются в одной установке интерпретатора. у этого интерпретатора один набор версий. если после первого приложения выходит новая версия нужного пакета, второму проекту нужна новая версия, а первому прежняя. общая установка оставляет два выхода: обновить первый проект под новую версию или оставить второй проект на старой. обновление требует отдельной работы, потому что обратная совместимость версий пакета не гарантирована. отказ от новой версии лишает второй проект исправлений и изменений интерфейса, которые в ней появились. отдельная среда на проект разводит эти наборы версий.

модуль `venv` входит в обычную поставку cpython. на части систем linux его выносят в отдельный пакет дистрибутива, и модуля может не быть. тогда в ос ставят пакет `python3-venv`. на ubuntu и debian:

```bash
sudo apt install python3-venv
```

создание среды начинают с каталога проекта: его выбирают и переходят в него в консоли или в командной строке. затем среде передают имя каталога:

```bash
python3 -m venv myvenv
```

аргумент модуля `venv` и есть имя каталога. в этом примере имя `myvenv`. обязательного соглашения об имени нет. в проектах часто берут `.venv` или `venv`.

после команды в текущем каталоге появляется подкаталог `myvenv`:

```bash


eugene@Eugene:/python/enoobis$  python3 -m venv myvenv

eugene@Eugene:/python/enoobis$  ls -l myvenv

total 2

drwxrwxrwx 1 root root 528 Mar  8 14:56 bin

drwxrwxrwx 1 root root   0 Mar  8 14:56 include

drwxrwxrwx 1 root root 152 Mar  8 14:56 lib

lrwxrwxrwx 1 root root   3 Mar  8 14:56 lib64 -> lib

-rwxrwxrwx 1 root root 192 Mar  8 14:56 pyvenv.cfg

eugene@Eugene:/eugene/python/enoobis$
```

листинг снят на linux. видны каталоги `bin`, `include` и `lib`, ссылка `lib64` на `lib` и файл `pyvenv.cfg`. в `bin` лежат интерпретатор и сценарии активации, в `lib` оказывается `site-packages`. `pyvenv.cfg` хранит путь к базовому интерпретатору и номер версии: стандартная библиотека остаётся в базовой установке, среда добавляет свои сценарии и свой каталог пакетов. на windows место `bin` занимает каталог `Scripts`.

### активация виртуальной среды

пока среда не активирована, имена `python` и `pip` ищутся по системному `PATH` и попадают в базовую установку. активация меняет поиск в текущем сеансе оболочки: сценарий ставит каталог `bin` или `Scripts` среды в начало `PATH` и запоминает прежнее окружение, чтобы его можно было вернуть. с проектом работают при включённой связанной среде. новый сеанс оболочки активацию не наследует, её выполняют снова.

ниже включается среда `myvenv` из текущего каталога. порядок зависит от ос и от оболочки. на windows командная строка и powershell берут разные сценарии:

- активация в windows в командной строке. если ос windows, в каталоге `myvenv/Scripts/` лежит файл `activate.bat`. он включает виртуальную среду. вызов из командной строки windows:

```bash
myvenv\Scripts\activate.bat
```

- активация в windows в powershell. в том же каталоге `myvenv/Scripts/` лежит `Activate.ps1`. файл тоже включает среду, но рассчитан только на powershell. по умолчанию политика выполнения powershell сценарии запрещает, поэтому до активации текущему пользователю задают политику `RemoteSigned`: локальные сценарии разрешены, а загруженные из сети должны быть подписаны. область `CurrentUser` ограничивает эту политику учётной записью, из которой идёт работа. для активации выполняют две команды:

```bash


Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

myvenv\Scripts\Activate.ps1
```

- активация в linux и macos. оболочка читает сценарий `activate` командой `source`, чтобы присваивания `PATH` прошли в текущем процессе. запуск файла отдельным процессом изменил бы окружение дочернего процесса и не затронул бы текущую оболочку:

```bash
source myvenv/bin/activate
```

после активации слева от текущего пути приглашение показывает имя среды в круглых скобках:

```bash


(myvenv) eugene@Eugene:/python/enoobis$
```

пример целиком в командной строке windows. сначала создаётся среда, затем вызывается `activate.bat`, и приглашение получает префикс `(myvenv)`:

```bash


C:\eugene\python\ enoobis>python -m venv myvenv



C:\eugene\python\ enoobis>myvenv\Scripts\activate.bat



(myvenv) C:\eugene\python\ enoobis>
```

пример целиком в консоли ubuntu. среду создают через `python3 -m venv`, включают через `source`:

```bash


eugene@Eugene:/python/enoobis$ python3 -m venv myvenv

eugene@Eugene:/python/enoobis$ source myvenv/bin/activate

(myvenv) eugene@Eugene:/python/enoobis$
```

#### деактивация виртуальной среды

по окончании работы среду выключают. команду `deactivate` в сеанс добавляет сценарий активации. она возвращает прежний `PATH`, и имена `python` и `pip` снова разрешаются в базовую установку:

```bash
deactivate
```

### управление пакетами с помощью pip

#### установка пакетов

дистрибутив из индекса ставят командой `pip install`. на место слова `название_пакета` подставляют имя проекта на pypi:

```bash
pip install название_пакета
```

дальше ставится matplotlib, пакет построения графиков. команду выполняют после активации среды. иначе пакет попадёт в ту установку, на которую указывает текущая команда `pip`:

```bash
pip install matplotlib
```

установку проверяют отдельным процессом интерпретатора: модуль импортируют и печатают атрибут `__version__` пакета:

```bash
python -c "import matplotlib; print(matplotlib.__version__)"
```

#### удаление пакета

дистрибутив удаляют из текущей среды командой `pip uninstall`. на место `имя_пакета` подставляют имя проекта:

```bash
pip uninstall имя_пакета
```

команда снимает названный пакет. зависимости, поставленные вместе с ним, сами при этом не удаляются. их снимают отдельными вызовами, если они больше не нужны.

### использование установленных пакетов

установленный matplotlib ниже вызывается из короткой программы. программа строит помесячные показатели популярности языка python по рейтингу tiobe за 2022 год. в текущем каталоге создают файл `app.py`:

```python


import matplotlib.pyplot as plt     # импортируем функциональность модуля pyplot из пакета matplotlib



months = ["Jan", "Feb", "Mar", "Apr", "May", "Jun", "Jul", "Aug", "Sep", "Oct", "Nov", "Dec"]

rates = [13.58,  15.33, 14.26, 13.92, 12.74, 12.2, 13.44, 15.63, 15.74, 17.08, 17.18, 16.66]



# метка по оси X

plt.xlabel("month")

# метка по оси Y

plt.ylabel("rate")



plt.plot(months, rates)

plt.show()
```

фрагмент дан как демонстрация импорта, поэтому разбор короткий. список `months` хранит сокращённые английские названия месяцев, список `rates` хранит показатели популярности. порядок в обоих списках общий: элемент с одним индексом относится к одному месяцу.

`xlabel()` задаёт подпись оси x, `ylabel()` задаёт подпись оси y. в `plot()` передают два списка: по оси x список `months`, по оси y список `rates`. функция принимает набор значений и строит по ним график. `show()` выводит график в окне просмотра бэкенда по умолчанию и держит это окно, пока его не закроют.

если среда была выключена командой `deactivate` или в этом сеансе ещё не включалась, перед запуском её активируют. затем скрипт выполняют интерпретатором среды:

```bash
(myvenv) eugene@Eugene:/python/enoobis$ python3 app.py
```

pip ставит пакеты python из индекса pypi в ту установку интерпретатора, на которую указывает текущая команда. виртуальная среда держит эти пакеты в отдельном `site-packages` проекта. дополнительные библиотеки, в том числе matplotlib, тогда не меняют системную установку. зависимости проекта изолированы и не конфликтуют с другими проектами и с библиотеками ос.
