модуль `sched` из стандартной библиотеки планирует вызовы на заданный момент. он нужен там, где действие надо выполнить с задержкой или через заданные интервалы, без отдельного потока на каждую задачу и без внешнего планировщика операционной системы.

в основе модуля очередь событий. событие - отложенный вызов функции с заданными аргументами. планировщик следит за временем функцией времени (time function) и ждёт следующего события функцией задержки (delay function). пока `run` не вызван, очередь только накапливается: постановка события сама по себе функцию не вызывает.

### класс scheduler

основной класс модуля - `scheduler`. он задаёт общий интерфейс планирования. конструктор принимает две функции:

```python
class sched.scheduler(timefunc=time.monotonic, delayfunc=time.sleep)
```

- `timefunc`: функция без аргументов, возвращает число. единица этого числа произвольная, лишь бы одна и та же шкала использовалась и для «сейчас», и для момента события. по умолчанию берётся `time.monotonic`. монотонные часы не идут назад и не сдвигаются при коррекции системного времени, поэтому долгий процесс не теряет и не повторяет события из-за шага ntp. значение `time.monotonic` - секунды от произвольной точки, его нельзя сравнивать с показаниями `time.time`.

- `delayfunc`: приостанавливает выполнение на заданное число единиц времени. вызывается с одним аргументом, совместимым с тем, что возвращает `timefunc`, и держит вызывающий поток указанное число этих единиц. после каждого события `delayfunc` вызывается ещё и с аргументом 0, чтобы в многопоточной программе другие потоки успели получить управление. у стандартного `time.sleep` даже нулевой аргумент отпускает gil.

объект задаётся так:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)
```

здесь обычная пара `time.time` и `time.sleep`. её хватает для коротких сценариев, где задержка считается по стенным часам. `time.time` возвращает секунды unix-времени и может прыгнуть, если системные часы поправят. `time.sleep` ждёт примерно указанное число секунд. единица `delay` совпадает с единицей `timefunc`: при этой паре аргумент 3 означает три секунды. минута в той же шкале была бы числом 60.

### планирование событий

у очереди два способа добавить событие.

- `enter(delay, priority, action, arguments, kwargs)` ставит событие через задержку. параметры: `delay` - через сколько единиц времени выполнить событие.

- `priority`: числовой приоритет. если время двух событий совпало, раньше выполняется то, у которого число меньше.

- `action`: вызываемая функция.

- `arguments`: кортеж позиционных аргументов функции.

- `kwargs`: словарь именованных аргументов.

выполнить событие значит выполнить вызов `action(*arguments, **kwargs)`. в стандартной библиотеке позиционный кортеж называется `argument`, в единственном числе. вызов без этого аргумента подставляет пустой кортеж. один позиционный аргумент записывают кортежем из одного элемента: запятая после значения обязательна, одни скобки кортеж не создают.

при равном времени и равном приоритете раньше стоит событие, которое поставили раньше. очередь упорядочена тройкой (время, приоритет, порядковый номер постановки), поэтому `enter` не перебирает список линейно при каждой вставке.

- `enterabs(time, priority, action, arguments, kwargs)` ставит событие на абсолютное время. `time` - момент выполнения, число в той же шкале, что возвращает `timefunc`, переданная конструктору. остальные параметры те же, что у `enter()`. задержка от «сейчас» здесь не считается: момент задан сразу, и сдвиг часов виден планировщику только через выбранную `timefunc`.

оба метода возвращают объект события. он нужен, чтобы снять событие с очереди до того, как `run` до него дойдёт.

### запуск событий

поставленные события запускает `run`:

```python


scheduler.run(blocking=True)
```

метод ждёт ближайшее событие через `delayfunc`, выполняет его и повторяет цикл, пока очередь не опустеет. при `blocking=True`, это значение по умолчанию, вызов не возвращается раньше. при `blocking=False` выполняются только уже наступившие события. если в очереди остаётся будущее событие, метод возвращает задержку до него: разность момента события и текущего показания `timefunc`. пустая очередь даёт возврат `None`. если `action` поднимает исключение, оно выходит из `run`. событие к этому моменту уже снято с очереди и повторно не ставится, состояние очереди остаётся согласованным, отдельного перехватчика ошибок у планировщика нет. если обработка одного события заняла больше времени, чем оставалось до следующего, планировщик отстаёт: просроченное событие остаётся в очереди и выполняется, как только цикл снова до него доходит.

### пример использования

один вызов одной функции:

```python


import sched

import time



def print_message():

    print("Hello enoobis.ru!")



# создаем scheduler

s = sched.scheduler(time.time, time.sleep)

print("Начало планирования...")



# планируем выполнение через 3 минуты

s.enter(3, 1, print_message)



# запускаем выполнение

s.run()



print("Планирование завершено.")
```

`s.enter()` ставит `print_message` с задержкой 3. комментарий в примере говорит о трёх минутах. при паре `time.time` и `time.sleep` единица задержки - секунда, поэтому пауза равна трём секундам. минута в этой шкале была бы числом 60. `s.run()` запускает цикл: планировщик ждёт срок и вызывает `print_message` без аргументов. после возврата из `run` очередь пуста, выполняется следующий оператор модуля.

несколько сообщений с разными задержками:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)



def print_message(message):

    print(f"[{time.strftime("%H:%M:%S", time.localtime())}] - {message}")



print("Начало планирования...")



s.enter(3, 1, print_message, ("Первое сообщение (через 3 секунды)",))

s.enter(5, 1, print_message, ("Второе сообщение (через 5 секунд)",))

s.enter(5, 2, print_message, ("Третье сообщение (через 5 секунд, но с более низким приоритетом)",))



# Событие с приоритетом 1 будет выполнено раньше, чем событие с приоритетом 2, если время совпадает.



s.run()

print("Планирование завершено.")
```

ожидаемый вывод:

```bash


Начало планирования...

[07:20:03] - Первое сообщение (через 3 секунды)

[07:20:05] - Второе сообщение (через 5 секунд)

[07:20:05] - Третье сообщение (через 5 секунд, но с более низким приоритетом)

Планирование завершено.
```

два последних события поставлены с одной задержкой 5 и разными приоритетами. число 1 меньше числа 2, поэтому второе сообщение печатается раньше третьего, хотя срок у них один. текст в скобках у третьего сообщения прямо называет более низкий приоритет. метка времени в строке берётся из `time.localtime` через `time.strftime`. это показание локальных стенных часов в момент вызова. задержку планировщик мерил своей `timefunc`.

### повторяющиеся задачи

встроенного повтора у `sched` нет. следующее событие ставят из самой вызываемой функции:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)



def repeat_task():

    print(f"[{time.strftime("%H:%M:%S", time.localtime())}] - Hello enoobis.ru")

    # Планируем следующий вызов этой же функции

    s.enter(3, 1, repeat_task)



print("Начало повторяющейся задачи...")

s.enter(3, 1, repeat_task)



s.run()
```

`repeat_task` в конце снова вызывает `s.enter` для себя, и выполнение продолжается с тем же интервалом. в тексте примера интервал назван тремя минутами. с `time.time` аргумент 3 по-прежнему означает три секунды: отсчёт начинается в момент постановки, то есть уже после печати строки, поэтому к паузе добавляется время самого вызова. сеанс завершают стандартными средствами оболочки, сочетаниями ctrl+z и ctrl+c. в unix ctrl+c доставляет sigint, интерпретатор получает `KeyboardInterrupt` и процесс завершается. ctrl+z доставляет sigtstp и только приостанавливает задание, не уничтожая его. на windows прерывание сеанса в консоли тоже даёт ctrl+c.

тот же повтор записывают циклом снаружи планировщика:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)



def repeat_task():

    print(f"[{time.strftime("%H:%M:%S", time.localtime())}] - Hello enoobis.ru")



print("Начало повторяющейся задачи...")



while True:

    s.enter(3, 1, repeat_task)

    s.run()
```

каждая итерация кладёт в пустую очередь одно событие и вызывает `run`. `run` возвращается, когда событие выполнено, и цикл ставит следующее. интервал снова считается от момента постановки.

число повторов можно ограничить. ниже задача выполняется пять раз:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)



def repeat_task():

    print(f"[{time.strftime("%H:%M:%S", time.localtime())}] - Hello enoobis.ru")



print("Начало повторяющейся задачи...")



count = 5   # 5 раз выполняем задачу



while count:

    s.enter(3, 1, repeat_task)

    s.run()

    count -= 1
```

счётчик `count` стартует с 5. пока он ненулевой, тело цикла ставит событие, дожидается его в `run` и уменьшает счётчик на единицу. после пятого возврата из `run` цикл кончается, процесс не остаётся висеть в ожидании.

### отмена событий

событие снимается методом `cancel(event)`. объект, который вернули `enter` или `enterabs`, передаётся в `cancel`:

```python


import sched

import time



s = sched.scheduler(time.time, time.sleep)



def my_task():

    print("Эта задача будет отменена.")



def cancel_task(event):

    s.cancel(event)

    print("Задача успешно отменена.")



event_to_cancel = s.enter(5, 1, my_task)

s.enter(2, 1, cancel_task, (event_to_cancel,))



s.run()
```

`my_task` не выполнится: `cancel_task` поставлен на более ранний срок, задержку 2 против 5, и снимает первое событие до его времени. если передать в `cancel` объект, которого уже нет в очереди, метод поднимает `ValueError`. после отмены `run` этого вызова в очереди не видит.

### преимущества и недостатки

преимущества:

- простота: интерфейс короткий. постановка, запуск и отмена покрываются методами одного объекта, без отдельного описания задач и без конфигурационного файла.

- изолированность: очередь живёт в одном потоке, отдельная синхронизация между событиями не нужна. они и так исполняются по очереди на том потоке, который вызвал `run`.

- гибкость: у каждого события свои задержка и приоритет, абсолютное время задаётся через `enterabs`, повтор собирается из обычного `enter`.

- устойчивость к сбоям времени: конструктор по умолчанию берёт `time.monotonic`, и долгая задача не сдвигается из-за коррекции системных часов. примеры этого раздела передают `time.time` явно, поэтому берут стенные часы. монотонные часы конструктора по умолчанию в этих примерах не используются.

недостатки:

- блокировка: `run()` при `blocking=True` не отпускает текущий поток, пока очередь не опустеет. для асинхронного приложения, где тот же поток должен обслуживать другие источники событий, такой вызов не подходит. обходной путь внутри самого модуля - `blocking=False` и внешний цикл, который сам решает, когда вернуться к очереди.

- точность: фактический момент определяется `delayfunc`, в примерах это `time.sleep`. сон в операционной системе не гарантирует пробуждение ровно через заданный интервал, для задач с жёстким сроком этой точности мало. долгий `action` дополнительно отодвигает всё, что стоит в очереди следом.

- ограниченная функциональность: ни пула потоков, ни политики повтора после исключения в модуле нет. исключение просто выходит из `run`. там, где нужны параллельные задачи, расписание по календарю и изоляция сбоев, берут уже другой механизм, не очередь `sched`.
