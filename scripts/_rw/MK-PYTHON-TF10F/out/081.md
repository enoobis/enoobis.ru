тип `Pipe` из пакета `multiprocessing` задаёт канал между двумя концами соединения:

```python
multiprocessing.Pipe(duplex=True)
```

вызов возвращает пару объектов соединения `(conn1, conn2)`. оба объекта имеют тип `Connection` и представляют два конца одного канала операционной системы. процессы к этому моменту ещё не созданы: концы позже передают аргументами в `Process`, и уже процессы обмениваются данными. при двунаправленном канале оба конца и отправляют, и принимают. в терминологии модуля первый конец, `conn1`, считается родительским, второй, `conn2`, дочерним.

конструктор принимает необязательный параметр `duplex`. значение `True`, оно же значение по умолчанию, создаёт двунаправленный канал. значение `False` создаёт однонаправленный канал: `conn1` используется только для приёма, `conn2` только для отправки. однонаправленный канал ближе к классическому неименованному каналу ос, где у каждого конца одно направление. двунаправленный на unix обычно опирается на пару сокетов.

у класса `Connection` для обмена между концами есть следующий набор методов:

- `send(obj)`: отправляет объект на другой конец соединения. для получения на той стороне вызывают `recv()`. объект должен поддерживать сериализацию, то есть быть пригодным для `pickle` (быть "picklable"). при попытке отправить очень большой сериализованный объект, примерно от 32 мб и более, в зависимости от ос, возникает исключение `ValueError`. ограничение задаёт способ передачи сообщения через канал ос. от языкового типа объекта оно не зависит.
- `recv()`: возвращает объект, отправленный с другого конца методом `send()`. вызов блокирует выполнение, пока данные не появятся. если данных больше нет и противоположный конец закрыт, возникает исключение `EOFError`.
- `close()`: закрывает соединение. тот же метод вызывается автоматически при сборке мусора объекта соединения. после закрытия конца попытка чтения на другой стороне при пустом буфере завершается `EOFError`.
- `poll([timeout])`: возвращает признак того, доступны ли данные для чтения. без аргумента метод возвращает признак сразу, процесс при этом не блокируется. числовой `timeout` задаёт наибольшее время ожидания в секундах. значение `None` означает ожидание без предела.
- `send_bytes(buf[, offset[, size]])`: отправляет байтовые данные из объекта, который поддерживает протокол буфера (bytes-like object). если указан `offset`, данные читаются из `buf` начиная с этой позиции. если указан `size`, из `buf` читается именно столько байтов. очень большой буфер, примерно от 32 мб и более, в зависимости от ос, снова приводит к `ValueError`.
- `recv_bytes([maxlength])`: возвращает сообщение из байтов, отправленное с другого конца. вызов блокируется, пока данные не появятся. если данных больше нет и противоположный конец закрыт, возникает `EOFError`. если указан `maxlength` и длина сообщения больше этого значения, возникает `OSError`, после чего чтение из соединения становится невозможным: слишком длинное сообщение не отбрасывается тихо, канал для дальнейшего приёма уже непригоден.
- `recv_bytes_into(buf[, offset])`: записывает в буфер `buf` байтовое сообщение с другого конца и возвращает число байтов в сообщении. вызов блокируется, пока данные не появятся. если данных больше нет и противоположный конец закрыт, возникает `EOFError`.

основными в типичном обмене объектами python остаются `send()` и `recv()`. `send()` сериализует объект модулем `pickle` и пишет байты в канал. `recv()` читает байты и восстанавливает объект. пара методов `send_bytes` и `recv_bytes` обходится без `pickle` и передаёт уже готовый буфер, что уместно для двоичных протоколов.

сначала канал без отдельных процессов: оба конца находятся в одном интерпретаторе, и видна только семантика очереди сообщений.

```python
from multiprocessing import Pipe

a, b = Pipe()

a.send([1, "hello", True])      # отправляем в канал

data = b.recv()     # получаем данные из канала

print(data)     # [1, 'hello', True]
```

канал создаётся между объектами `a` и `b`. объект `a` отправляет список из трёх элементов, объект `b` принимает его. тем же порядком сообщений отправляют и несколько значений подряд. канал сохраняет порядок: сообщения стоят в очереди байтов.

```python
from multiprocessing import Pipe

a, b = Pipe()

a.send([1, "hello", True])
a.send("World")

data = b.recv()
print(data)     # [1, "hello", True]
data = b.recv()
print(data)     # "World"
```

два вызова `send` ставят в канал сначала список, затем строку `"World"`. два вызова `recv` снимают их в том же порядке.

канал между двумя процессами строится так: родитель создаёт пару концов, один конец передаёт в дочерний `Process`, другой оставляет себе.

```python
from multiprocessing import Process, Pipe

# функция, которая запускается во втором процессе
def send_to_parent(conn):
    conn.send("Hello, parent")
    conn.close()    # закрываем канал

if __name__ == "__main__":
    parent_conn, child_conn = Pipe() 
    # второй процесс вызывает функцию send_to_parent
    child_process = Process(target=send_to_parent, args=(child_conn,))
    child_process.start()

    message = parent_conn.recv()    # получаем данные от второго процесса
    print("Child sent:", message)   # Child sent: Hello, parent
    child_process.join()
```

дочерний процесс исполняет `send_to_parent` и получает конец `child_conn`. через этот конец функция отправляет данные:

```python
conn.send("Hello, parent")
```

на родительском конце то же сообщение читается так:

```python
message = parent_conn.recv()
```

после отправки потомок закрывает свой конец вызовом `close()`, родитель печатает строку `Child sent: Hello, parent` и дожидается потомка через `join()`.

данные на одном конце повреждаются, если два процесса или два потока одновременно читают из этого конца или одновременно пишут в него. у конца `Connection` нет внутренней блокировки на параллельный доступ. протокол канала предполагает одного читателя и одного писателя на каждый конец. очередь `Queue` как раз добавляет блокировки и служебный поток поверх канала. там, где такой дисциплины нет, берут `Queue`, а `Pipe` оставляют для явного протокола из двух участников.

### дуплексные каналы

в предыдущем примере данные шли от потомка к родителю в одну сторону. при `duplex=True`, значении по умолчанию, концы обмениваются сообщениями в обе стороны. ниже один процесс отправляет число, второй возвращает его квадрат:

```python
from multiprocessing import Process, Pipe

# функция, которая запускается во втором процессе
def conn1_func(conn):
    n = 5
    conn.send(n)            # посылаем число
    square_n = conn.recv()  # получаем из квадрат числа
    conn.close()            # закрываем канал
    print(f"Квадрат числа {n} равен {square_n}")

def conn2_func(conn):
    n = conn.recv()     # получаем из канала число
    conn.send(n*n)      # посылаем обратно квадрат числа

if __name__ == "__main__":
    conn1, conn2 = Pipe() 

    # определяем и запускаем два процесса для каждой из сторон канала
    conn1_process = Process(target=conn1_func, args=(conn1,))
    conn2_process = Process(target=conn2_func, args=(conn2,))

    conn1_process.start()
    conn2_process.start()

    conn1_process.join()
    conn2_process.join()
```

для каждого конца создаётся свой процесс: `conn1_process` и `conn2_process`. первый процесс посылает по каналу число `5`. второй читает его, вычисляет квадрат `n * n` и отправляет результат обратно. первый процесс, получив ответ, закрывает свой конец и печатает результат. второй конец в `conn2_func` явно не закрывается: процесс просто завершается, и соединение этого конца закрывается при завершении процесса. вывод:

```bash
Квадрат числа 5 равен 25
```
