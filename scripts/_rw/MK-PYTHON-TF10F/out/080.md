### обмен данными между процессами через queue (очередь)

адресные пространства процессов изолированы, поэтому присваивание общей переменной, допустимое для потоков одного процесса, между процессами не видно. обмен идёт через специальные объекты межпроцессного взаимодействия. один из них, очередь `multiprocessing.Queue`, конструируется так:

```python
multiprocessing.Queue([maxsize])
```

необязательный аргумент `maxsize` задаёт максимальную длину очереди. значение по умолчанию `0` означает отсутствие предела. перед помещением в очередь объект сериализуется модулем `pickle`, поэтому передаваемое значение должно быть сериализуемым: изоляция процессов не позволяет передать живую ссылку на объект другого интерпретатора. внутри реализация опирается на канал и блокировки, а в процессе, который первым кладёт элемент, поднимается служебный поток, переносящий объекты из буфера в канал.

основные методы:

- `empty()`: возвращает `True`, если очередь пуста, и `False` в противном случае. из-за параллельного исполнения процессов результат не является абсолютно надёжным. между проверкой и следующим вызовом другой процесс может успеть положить или забрать элемент.
- `full()`: возвращает `True`, если очередь заполнена, и `False` в противном случае. по той же причине, что и у `empty()`, результат не является абсолютно надёжным. `put(obj[, block[, timeout]])`: помещает объект `obj` в очередь. если необязательный аргумент `block` равен `True` (значение по умолчанию), а `timeout` равен `None` (значение по умолчанию), то при заполненной очереди вызов блокируется, пока не освободится место. при `block=False` и отсутствии места возникает исключение, при конечном `timeout` ожидание ограничено этим сроком.
- `get([block[, timeout]])`: извлекает и возвращает элемент из очереди. если необязательный аргумент `block` равен `True` (значение по умолчанию), а `timeout` равен `None` (значение по умолчанию), то при пустой очереди вызов блокируется до появления элемента.

пример передачи результатов из дочернего процесса в родительский:

```python


from multiprocessing import Process, Queue



# возводим числа в куб

def cubes(numbers, queue):

    for num in numbers:

        queue.put(num ** 3) # Отправляем данные в очередь

        

if __name__ == "__main__":

    numbers_list = [1, 2, 3]

    data_queue = Queue()    



    # Передаем очередь как аргумент в процесс

    proc = Process(target=cubes, args=(numbers_list, data_queue))

    proc.start()

    proc.join()



    # Извлекаем данные из очереди в главном процессе

    while not data_queue.empty():

        print(f"Получено из процесса cubes: {data_queue.get()}")
```

действие процесса сосредоточено в функции `cubes`. она принимает набор чисел `numbers` и очередь `queue`, перебирает набор и отправляет кубы вызовом `queue.put(num ** 3)`.

в блоке `__main__` очередь создаётся в родителе и передаётся потомку аргументом. при передаче потомок подключается к той же очереди: канал и буфер общие для обоих процессов. после `join()` родитель забирает элементы вызовом `data_queue.get()`, пока `empty()` сообщает о непустой очереди. вывод:

```bash


Получено из процесса cubes: 1

Получено из процесса cubes: 8

Получено из процесса cubes: 27
```

протокол обмена может быть двусторонним. процесс одновременно читает внешние данные из одной очереди и отправляет результаты в другую:

```python


from multiprocessing import Process, Queue



# возводим числа в куб

def cubes(inputs: Queue, outputs: Queue):

    # Извлекаем данные из входной очереди inputs

    while True:

        n = inputs.get()

        if not n: break

        outputs.put(n ** 3) # Отправляем данные в очередь

        

if __name__ == "__main__":



    inputs = Queue()

    outputs = Queue()



    input_values = [1, 2, 3, 4, 5, 0]



    # передаем данные из списка во входную очередь - inputs

    for i in input_values:

        inputs.put(i)

    # Передаем очередь как аргумент в процесс

    proc = Process(target=cubes, args=(inputs, outputs))

    proc.start()

    proc.join()



    # Извлекаем данные из очереди в главном процессе

    for n in input_values:

        if not n: break

        print(f"{n}: {outputs.get()}")
```

в главном процессе создаются две очереди: `inputs` для входящих чисел и `outputs` для результатов. в `inputs` последовательно помещаются числа от 1 до 5. последнее значение, `0`, служит признаком конца. ноль выбран потому, что проверка `if not n` считает его ложным. такое соглашение закрывает ноль как полезную нагрузку: встретив `0`, функция завершает цикл и не отправляет куб этого маркера.

затем запускается процесс `proc` с функцией `cubes`. аргументами передаются обе очереди. функция в цикле извлекает числа из `inputs`, возводит их в куб и кладёт результат в `outputs`. цикл заканчивается на маркере `0`. пустая очередь при блокирующем `get` остановила бы процесс в ожидании следующего элемента, даже если все полезные числа уже обработаны.

главный процесс вызывает `proc.join()` и не читает `outputs`, пока `proc` полностью не завершится. после этого он в том же порядке, что и `input_values`, достаёт значения из `outputs` и печатает их, останавливаясь на том же маркере `0`.

```bash


1: 1

2: 8

3: 27

4: 64

5: 125
```

### передача сложных объектов между процессами

сложный объект, например экземпляр пользовательского класса, разделяют между процессами через менеджер. базовый класс такого менеджера, `multiprocessing.managers.BaseManager`, даёт стандартный способ открыть доступ к пользовательскому типу (база в памяти, составная структура, сетевое соединение) из разных процессов. каждый процесс при обычной передаче аргумента получил бы собственную копию, восстановленную из `pickle`, и дальнейшие мутации копий расходились бы. менеджер оставляет один экземпляр в отдельном процессе и раздаёт остальным замещающие объекты.

при нескольких процессах python у каждого процесса собственная память. если обычный объект, например экземпляр пользовательского класса, передать в дочерний процесс аргументом `Process`, интерпретатор сериализует его через `pickle` и в потомке появится копия. изменения этой копии родитель не наблюдает. передача идёт по значению через сериализацию.

чтобы несколько процессов работали с одним и тем же сложным объектом, используют менеджер. класс `BaseManager` превращает экземпляр произвольного класса в общий ресурс.

порядок работы такой:

- `BaseManager` запускает отдельный управляющий процесс, сервер менеджера.
- в этом процессе создаётся реальный экземпляр сложного объекта.
- остальные процессы вызывают методы через прокси-объекты, то есть через клиентов менеджера.
- вызов метода у прокси отправляет серверу запрос. сервер выполняет операцию над реальным объектом и возвращает результат, снова через сериализацию.

практический пример: класс `Inventory` изображает склад и хранит товары вместе с количеством. несколько независимых процессов добавляют товары и читают остатки.

сначала определяется обычный класс. он не ссылается на процессы и не знает о менеджере:

```python


class Inventory:

    def __init__(self):

        self.items = {}



    def add_item(self, name: str, quantity: int):

        if name in self.items:

            self.items[name] += quantity

        else:

            self.items[name] = quantity

        print(f"[Склад] Добавлено: {name}, количество {quantity}")



    def get_stock(self) -> dict:

        return self.items
```

класс небольшой, но контракт его методов задаёт дальнейший протокол прокси. в конструкторе `__init__()` создаётся пустой словарь `self.items = {}`. в нём хранятся пары вида `"название_товара": количество`.

метод `add_item()` добавляет товар. параметры: `name` (название, аннотация `str`) и `quantity` (количество, аннотация `int`). двоеточия в заголовке являются аннотациями типов. интерпретатор их не проверяет во время выполнения: аннотации сохраняются в `__annotations__` и читаются человеком или внешним инструментом. на семантику метода они не влияют.

внутри метода выражение `if name in self.items` проверяет, есть ли товар в словаре. если ключ уже есть, присваивание `self.items[name] += quantity` прибавляет новое количество к старому. если ключа нет, запись создаётся присваиванием `self.items[name] = quantity`. затем метод печатает сообщение о добавлении.

метод получения остатков `get_stock` возвращает текущее содержимое словаря со всеми товарами. тип возвращаемого значения, `dict`, тоже записан аннотацией и во время выполнения не проверяется. метод возвращает сам словарь `self.items`. при обычном вызове в одном процессе вызывающий получает ссылку на тот же объект.

после определения класса его регистрируют в `BaseManager`, иначе другие процессы не смогут запросить экземпляр по имени. для этого создают подкласс менеджера, регистрируют в нём `Inventory` и запускают менеджер контекстным менеджером `with`:

```python


from multiprocessing import Process 

from multiprocessing.managers import BaseManager

import time



class Inventory:

    def __init__(self):

        self.items = {}



    def add_item(self, name: str, quantity: int):

        if name in self.items:

            self.items[name] += quantity

        else:

            self.items[name] = quantity

        print(f"[Склад] Добавлено: {name}, количество {quantity}")



    def get_stock(self) -> dict:

        return self.items





# Создаем кастомный менеджер

class CustomManager(BaseManager):

    pass



# Функция, которую будут выполнять рабочие процессы

def worker_task(shared_inventory, item_name, quantity):

    print(f"[Процесс {item_name}] Начинает работу...")

    time.sleep(1)  # Имитация работы

    # Вызываем метод через прокси-объект так же, как у обычного класса

    shared_inventory.add_item(item_name, quantity)

    print(f"[Процесс {item_name}] Завершил добавление.")

    

if __name__ == "__main__":

    # Регистрируем наш класс в менеджере под именем "Inventory"

    CustomManager.register("Inventory", Inventory)



    # Запускаем менеджер

    with CustomManager() as manager:

        # Создаем общий объект через менеджер

        # Внутри менеджера создается реальный Inventory, а нам возвращается прокси

        shared_inventory = manager.Inventory()



        # Для демонстрации создаем два процесса и передаем им наш прокси-объект

        p1 = Process(target=worker_task, args=(shared_inventory, "Яблоки", 10))

        p2 = Process(target=worker_task, args=(shared_inventory, "Бананы", 5))



        p1.start()

        p2.start()



        # Ждем завершения процессов

        p1.join()

        p2.join()



        # Проверяем финальное состояние объекта в главном процессе

        print("\n--- Финальный отчет о складе ---")

        print(shared_inventory.get_stock())
```

ход программы по шагам. сначала объявляется собственный класс менеджера без новых методов: вся настройка идёт через регистрацию на классе.

```python
class CustomManager(BaseManager):
```

в блоке `__main__` класс склада регистрируется под именем `"Inventory"`:

```python
CustomManager.register("Inventory", Inventory)
```

регистрация связывает строковое имя с вызываемым объектом, который сервер использует, чтобы создать реальный экземпляр. имя же появляется у прокси как метод-конструктор.

менеджер запускается так:

```python
with CustomManager() as manager:
```

вход в контекст вызывает `start()`: поднимается серверный процесс, открывается канал для запросов. выход из контекста останавливает сервер.

общий объект создаётся через менеджер:

```python
shared_inventory = manager.Inventory()
```

вызов `manager.Inventory()` не конструирует `Inventory` в текущем процессе. запрос уходит на сервер, реальный экземпляр живёт там, а вызывающему возвращается прокси. методы прокси вызываются тем же синтаксисом, что и методы обычного экземпляра: `shared_inventory.add_item(item_name, quantity)`.

дальше создаются два процесса, `p1` и `p2`. обоим передаётся один и тот же прокси, вместе с названием товара и количеством: яблоки в количестве 10 и бананы в количестве 5. каждый процесс в `worker_task` печатает начало работы, ждёт одну секунду (`time.sleep(1)`, имитация работы) и вызывает `add_item`. родитель дожидается обоих через `join()` и затем читает финальное состояние вызовом `shared_inventory.get_stock()` уже в главном процессе. вывод:

```bash


[Процесс Яблоки] Начинает работу...

[Процесс Бананы] Начинает работу...

[Склад] Добавлено: Яблоки, количество 10

[Процесс Яблоки] Завершил добавление.

[Склад] Добавлено: Бананы, количество 5

[Процесс Бананы] Завершил добавление.



--- Финальный отчет о складе ---

{"Яблоки": 10, "Бананы": 5}
```

оба добавления видны в одном словаре. словарь отражает состояние объекта на сервере менеджера.

при работе с `BaseManager` учитывают три ограничения:

- менеджер не делает методы процесса-сервера безопасными относительно произвольных составных операций. если два процесса одновременно вызовут метод, который меняет одно и то же поле, например `self.items["Яблоки"] += 1`, возможна гонка (race condition): потеря обновления возникает, когда чтение, изменение и запись не составляют одну неделимую операцию с точки зрения параллельных вызовов. если метод выполняет длинное вычисление или перезаписывает данные несколькими шагами, внутри метода ставят `multiprocessing.Lock` и держат его на всём критическом участке.
- прокси возвращает копию данных. ссылка на объект сервера вызывающему не передаётся. вызов `shared_inventory.get_stock()` доставляет копию словаря `items`, восстановленную из сериализованного ответа. изменение этой копии, например `stock["Груши"] = 1`, на реальном складе внутри менеджера не отражается. мутации проходят только через методы самого прокси, потому что только они исполняются на сервере.
- регистрация выполняется до старта сервера. вызов `CustomManager.register` ставят раньше `manager.start()` и раньше входа в контекст `with CustomManager()`. после запуска сервера класс уже зафиксирован в том процессе, и поздняя регистрация в родителе до него не доходит.
