в потоках нередко есть разделяемые ресурсы, общие для всей программы: общие переменные, файлы и другие объекты. когда несколько потоков одновременно меняют одну и ту же переменную или одну структуру данных, возникает состояние гонки (race condition): итог зависит от того, в каком порядке планировщик операционной системы чередует потоки, а этот порядок не фиксирован. взаимное исключение для такой ситуации в python даёт примитивная блокировка, мьютекс. вызов `threading.Lock()` возвращает её объект. имя `Lock` в модуле `threading` является фабричной функцией: конкретная реализация выбирается по платформе, семантика объекта остаётся одной. как только поток захватил блокировку, следующие попытки захвата останавливают вызывающий поток, пока блокировку не освободят.

объект блокировки находится в одном из двух состояний: захвачено (locked) или свободно (unlocked). сразу после создания состояние свободно.

у объекта два основных метода, `acquire()` и `release()`. если блокировка свободна, `acquire()` переводит её в состояние захвачено и сразу завершается. если блокировка уже захвачена, `acquire()` останавливает поток до тех пор, пока вызов `release()` в другом потоке не переведёт её в состояние свободно. после этого тот же `acquire()` снова переводит её в состояние захвачено и завершается. блокирующий вызов без ограничения по времени при успешном захвате возвращает `True`. метод `release()` вызывают только при захваченной блокировке: он переводит её в состояние свободно и сразу завершается. попытка освободить свободную блокировку возбуждает исключение `RuntimeError`. у примитивной блокировки нет потока-владельца, и `release()` вправе вызвать любой поток программы. повторный `acquire()` из потока, который уже держит блокировку и ещё не дошёл до своего `release()`, снова переходит в ожидание: примитив не реентерабелен, и если больше некому вызвать `release()`, этот поток так и остаётся ждать.

если в ожидании перехода в состояние свободно методом `acquire()` остановлено несколько потоков, после `release()` исполнение продолжит только один из них. какой именно поток продолжит работу, не определено и может зависеть от реализации. справедливой очереди ожидания спецификация этого примитива не задаёт.

в cpython байткод в каждый момент исполняет один поток: интерпретатор держит глобальную блокировку `GIL`. гонка на общей переменной при этом сохраняется. запись `x += 1` раскладывается на несколько операций байткода: чтение значения, сложение и сохранение результата. между этими операциями поток может быть переключён. вызов `time.sleep` на время ожидания отпускает `GIL`, поэтому чередование в программах ниже наблюдается регулярно.

### пример состояния гонки

блокировка закрывает гонку, поэтому сначала фиксируется сама проблема. берётся функционал банковского счёта, с которого два потока одновременно списывают деньги. оба считывают один баланс, уменьшают его и записывают обратно. операционная система переключает потоки в случайный момент, и один поток может затереть изменения другого. ту же потерю обновления показывает программа на общей переменной:

```python
import threading
import time

x = 0  # общий ресурс

threads = []    # список потоков

def increase_x(): 
    global x
    x = 1    # устанавливаем новое значение для общего ресурса
    thread_name = threading.current_thread().name   # имя текущего потока
    for _ in range(1, 4):
        print(f"{thread_name}: {x}")
        x += 1              # изменение общего ресурса
        time.sleep(0.5)     # имитация работы - полминуты


# запускаем три потока
for i in range(1, 4):
    my_thread = threading.Thread(target=increase_x, name=f"Поток {i}")
    threads.append(my_thread)
    my_thread.start()           # запускаем потоки
 
# ожидаем завершения потоков
for my_thread in threads:
    my_thread.join()
```

здесь запускаются три потока. каждый вызывает функцию `increase_x()` и работает с общей глобальной переменной `x`. по тексту функции ожидается, что каждый поток выведет значения `x` от 1 до 3. на исполнении происходит переключение между потоками, и значение `x` становится непредсказуемым. один из возможных выводов консоли:

```bash
Поток 1: 1
Поток 2: 1
Поток 3: 1
Поток 2: 2
Поток 1: 2
Поток 3: 3
Поток 2: 5
Поток 1: 6
Поток 3: 7
```

от запуска к запуску этот вывод может различаться. в приведённых строках нет трёх отдельных последовательностей 1, 2, 3: общая переменная уходит к 5, 6 и 7, потому что приращения разных потоков складываются, а присваивание `x = 1` в одном потоке затирает уже накопленное значение. разделяемым ресурсом в программе служит обычная переменная. та же гонка возникает, если общий ресурс является файлом, сокетом для отправки по сети или любым другим изменяемым объектом.

решение состоит в том, чтобы синхронизировать потоки и ограничить доступ к разделяемым ресурсам на время их использования одним потоком. для этого python предоставляет `Lock` (замок, блокировка). порядок работы такой:

- поток перед изменением переменной блокирует доступ к ней методом `acquire()`.

- если другой поток тоже пытается изменить данные, он видит блокировку и ждёт, пока её снимут.

- первый поток меняет данные и выполняет разблокировку методом `release()`.

применение `Lock` к той же программе:

```python
import threading
import time

x = 0  # общий ресурс

x_lock = threading.Lock() # Создаем объект блокировки

threads = []    # список потоков

def increase_x(): 
    global x
    thread_name = threading.current_thread().name   # имя текущего потока

    x_lock.acquire()    # Блокируем доступ для других потоков
    try:
        x = 1    # устанавливаем новое значение для общего ресурса
        for _ in range(1, 4):

            print(f"{thread_name}: {x}")
            x += 1      # изменение общего ресурса
            time.sleep(0.5)     # имитация работы
    finally:
        x_lock.release()      # обязательно разблокируем, даже если произошла ошибка

# запускаем три потока
for i in range(1, 4):
    my_thread = threading.Thread(target=increase_x, name=f"Поток {i}")
    threads.append(my_thread)
    my_thread.start()           # запускаем потоки
 
# ожидаем завершения потоков
for my_thread in threads:
    my_thread.join()
```

для блокировки применяется объект `x_lock`, полученный вызовом `threading.Lock()`. когда исполнение функции `increase_x()` в потоке доходит до `x_lock.acquire()`, объект `x_lock` переходит в состояние захвачено. на время этого захвата, вплоть до `x_lock.release()`, последующий код исполняет только один поток: остальные, дошедшие до того же `acquire()`, ждут. после `x_lock.release()` объект `x_lock` освобождается и становится доступным для других потоков. если внутри критической секции возникает ошибка, `release()` всё равно выполняется: вызов стоит в ветке `finally`. взаимное исключение действует для потоков, которые захватывают этот же `x_lock`. поток, который меняет `x` без `acquire()`, снова создаёт гонку.

при такой синхронизации консольный вывод упорядочен. каждый поток печатает 1, 2 и 3 подряд, и только потом в критическую секцию входит следующий:

```bash
Поток 1: 1
Поток 1: 2
Поток 1: 3
Поток 2: 1
Поток 2: 2
Поток 2: 3
Поток 3: 1
Поток 3: 2
Поток 3: 3
```

какой поток войдёт первым, по-прежнему зависит от того, кто раньше выполнит `acquire()`. внутри одного захвата строки одного потока идут подряд, потому что `time.sleep(0.5)` в этом листинге стоит внутри захваченной блокировки и остальные потоки ждут её освобождения.

### альтернативный способ через with

чтобы не писать конструкцию `try...finally` и не забыть вызов `release()`, протокол блокировки записывают менеджером контекста `with`. пропущенный `release()` оставляет ожидающие в `acquire()` потоки остановленными. если основной поток ждёт их через `join()`, программа останавливается и не завершается. менеджер `with` при входе в блок вызывает `acquire()`, при выходе вызывает `release()`, в том числе когда из блока вышло исключение:

```python
import threading
import time

x = 0  # общий ресурс

x_lock = threading.Lock() # Создаем объект блокировки

threads = []    # список потоков

def increase_x(): 
    global x
    thread_name = threading.current_thread().name   # имя текущего потока

    # Менеджер with сам вызовет acquire() и release()
    with x_lock:
        x = 1    # устанавливаем новое значение для общего ресурса
        for _ in range(1, 4):
            print(f"{thread_name}: {x}")
            x += 1      # изменение общего ресурса
            time.sleep(0.5)     # имитация работы

# запускаем три потока
for i in range(1, 4):
    my_thread = threading.Thread(target=increase_x, name=f"Поток {i}")
    threads.append(my_thread)
    my_thread.start()           # запускаем потоки
 
# ожидаем завершения потоков
for my_thread in threads:
    my_thread.join()
```

запись `with x_lock` держит ту же критическую секцию общей переменной `x`, что пара `acquire()` и `release()` в предыдущей программе. тело блока по-прежнему монопольно на время захвата.

блокировки обеспечивают безопасность данных при обращении к разделяемому ресурсу, и за это приходится платить скоростью. пока один поток держит `Lock`, остальные, которым нужен тот же объект, простаивают. блокировку держат как можно меньшее время: на непосредственное изменение общей переменной или на обновление общего ресурса. весь тяжёлый код в `with` не оборачивают. скачивание файла из сети и его запись внутри критической секции заставляют остальные потоки ждать этот ввод-вывод, и программа работает медленно, как в один поток.
