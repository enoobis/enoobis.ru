в многопоточном программировании на языке java одна из самых частых проблем это состояние гонки (race condition): несколько потоков одновременно читают и изменяют одни и те же данные. классический пример, простой счётчик:

```java


public class Program {

 

    public static void main(String[] args) throws InterruptedException{

         

        int numThreads = 1000;          // количество потоков

        int incrementsPerThread = 1000; // количество итреаций в каждом потоке



        Counter counter = new Counter();

 

        Thread[] threads = new Thread[numThreads];

        for (int i = 0; i < numThreads; i++){

             

            threads[i] = new Thread(() ->{ 



                for (int j = 0; j < incrementsPerThread; j++) {

                    counter.increment();

                }

                

            });

            threads[i].start();

        }

        // небольшая задержка в 1 секунду, чтобы потоки успели поработать

        Thread.sleep(1000);



        // ожидаем завершения всех потоков

        for (int i = 0; i < numThreads; i++){

            threads[i].join();

        }



        // проверяем значение счетчика

        System.out.println("Counter: " + counter.getCounter());

    }

}



class Counter{



    private volatile long counter = 0;



    long getCounter() { return counter; }

    void increment() { counter++;  }  //  НЕ АТОМАРНАЯ ОПЕРАЦИЯ!

}
```

в программе класс `Counter`, условный счётчик. в нём есть переменная `counter`:

```java
private volatile long counter = 0;
```

чтобы потоки видели изменения этой переменной, она определена с ключевым словом `volatile`. в методе `increment()` значение увеличивается на 1:

```java
void increment() { counter++;  }
```

в методе `main` класс используется через один общий объект:

```java
Counter counter = new Counter();
```

далее создаётся массив из 1000 потоков. каждый поток 1000 раз выполняет метод `increment()` у объекта `Counter`:

```java


Thread[] threads = new Thread[numThreads];



for (int i = 0; i < numThreads; i++){

             

    threads[i] = new Thread(() ->{ 



        for (int j = 0; j < incrementsPerThread; j++) {

            counter.increment();

        }       

    });

    threads[i].start();

}
```

после завершения потоков выводится финальное значение счётчика. перед печатью главный поток дожидается всех через `join`:

```java
System.out.println("Counter: " + counter.getCounter());
```

если запустить 1000 потоков и каждый 1000 раз увеличит счётчик на единицу, разумно ожидать финальное значение 1000 * 1000 = 1 000 000. на деле результат может быть таким:

```bash


Counter: 944695
```

а может быть и таким:

```bash


Counter: 870973
```

а может быть и совсем другим. результат недетерминирован и с большой вероятностью отличается от ожидаемого 1 000 000 в меньшую сторону: совпадение возможно только если потоки ни разу не прочитают поле вперемешку. операция инкремента в методе `increment()` состоит из трёх шагов:

- чтение текущего значения поля `counter`

- увеличение прочитанного значения на 1

- запись нового значения обратно в `counter`

если два и более потоков выполняют инкремент одновременно, они могут считать одно и то же значение и записать один результат. один инкремент теряется.

для решения можно взять блок или метод с оператором `synchronized` либо блокировку `ReentrantLock`. оба способа представляют блокирующий механизм. если поток а держит блокировку, поток б и следующие вынуждены остановиться и ждать. в системе с высокой нагрузкой это даёт простои потоков, частые переключения контекста и резкое падение производительности.

### атомарность и пакет java.util.concurrent.atomic

для той же задачи язык java предоставляет классы пакета `java.util.concurrent.atomic`: `AtomicInteger`, `AtomicBoolean`, `AtomicReference`, `AtomicLong` и другие. эти классы опираются на машинную инструкцию compare-and-swap. процессор сравнивает ячейку с ожидаемым значением и заменяет её только при совпадении, без отдельной блокировки операционной системы. операции над одиночными переменными, которые дают эти классы, неблокирующие и потокобезопасные (thread-safe). неудачное сравнение повторяется с уже обновлённым значением, и поток не встаёт в очередь монитора.

применение видно на `AtomicLong`, обёртке над значением типа `long` с атомарными методами изменения. объект создаётся одним из конструкторов:

```java


AtomicLong()

AtomicLong(long initialValue)
```

первая версия инициализирует объект числом 0. второй конструктор принимает начальное значение для `AtomicLong`.

чтение и запись по видимости устроены как у `volatile long`:

- `long get()`: возвращает текущее значение, аналогично чтению `volatile long`

- `void set(long newValue)`: устанавливает новое значение, аналогично записи в `volatile long`

класс также даёт атомарные операции, в них и состоит его назначение:

- `long incrementAndGet()`: атомарно увеличивает на 1 и возвращает новое значение, префиксный инкремент `++i`

- `long getAndIncrement()`: атомарно увеличивает на 1 и возвращает старое значение, постфиксный инкремент `i++`

- `long decrementAndGet()`: атомарно уменьшает на 1 и возвращает новое значение, `--i`

- `long getAndDecrement()`: атомарно уменьшает на 1 и возвращает старое значение, `i--`

- `long addAndGet(long delta)`: атомарно добавляет `delta` и возвращает новое значение, `i += delta`

- `long getAndAdd(long delta)`: атомарно добавляет `delta` и возвращает старое значение

- `boolean compareAndSet(long expect, long update)`: пытается установить значение `update`, только если текущее значение равно `expect`. возвращает `true` в случае успеха. это и есть compare-and-swap, на котором собраны остальные обновления

для атомарного счётчика предыдущий пример меняется так:

```java


import java.util.concurrent.atomic.AtomicLong;



public class Program {

 

    public static void main(String[] args) throws InterruptedException{

         

        int numThreads = 1000;

        int incrementsPerThread = 1000;



        Counter counter = new Counter();

 

        Thread[] threads = new Thread[numThreads];

        for (int i = 0; i < numThreads; i++){

             

            threads[i] = new Thread(() ->{ 



                for (int j = 0; j < incrementsPerThread; j++) {

                    counter.increment();

                }

            });

            threads[i].start();

        }

        // небольшая задержка, чтобы потоки успели поработать

        Thread.sleep(1000);



        // ожидаем завершения всех потоков

        for (int i = 0; i < numThreads; i++){

            threads[i].join();

        }



        // проверяем значение счетчика

        System.out.println("Counter: " + counter.getCounter());

    }

}



class Counter{

    // Правильный, потокобезопасный счетчик

    private AtomicLong counter = new AtomicLong(0);



    long getCounter() { return counter.get(); }

    void increment() { counter.getAndIncrement();  }   //  АТОМАРНАЯ ОПЕРАЦИЯ!

}
```

здесь изменён только класс `Counter`. вместо типа `long` у переменной тип `AtomicLong`. объект создаётся конструктором, в который передаётся начальное значение:

```java
AtomicLong counter = new AtomicLong(0);
```

по умолчанию, при аргументе 0, переменная `counter` равна 0.

в методе `getCounter()` метод `get()` возвращает текущее значение счётчика:

```java
long getCounter() { return counter.get(); }
```

в методе `increment()` вызов `getAndIncrement()` увеличивает значение счётчика на 1:

```java
void increment() { counter.getAndIncrement();  }
```

при запуске потоков метод `increment` вызывается по-прежнему, а внутри выполняется атомарная операция:

```java


for (int i = 0; i < numThreads; i++){

             

    threads[i] = new Thread(() ->{ 



        for (int j = 0; j < incrementsPerThread; j++) {

            counter.increment();  // Выполняем атомарную операцию

        }

    });

    threads[i].start();

}
```

операция остаётся атомарной, даже если несколько потоков подряд вызовут `increment()`. потерянное обновление из трёх отдельных шагов здесь не возникает: compare-and-swap повторяется, пока в ячейку не ляжет прибавление к последнему записанному значению.

консольный вывод детерминирован и равен тому значению, которое и требуется:

```bash


Counter: 1000000
```

`AtomicLong` даёт корректный результат, тогда как `volatile long` теряет инкременты из-за состояния гонки. видимость записи и атомарность прибавления единицы это разные гарантии.

### longadder

атомарные типы, в том числе `AtomicLong`, используют для счётчиков производительности и для генерации идентификаторов. при очень большом числе потоков, которые обращаются к одной и той же атомарной переменной, производительность снижается: повторные compare-and-swap сталкиваются на одной кэш-линии. для роста производительности в этом профиле есть классы `LongAdder` и `LongAccumulator`.

`LongAdder` рассчитан на сценарий чистого подсчёта, когда точное значение не нужно знать на каждом шаге, а важен итоговый результат, сумма всех прибавлений. это частая ситуация: сумму не читают до завершения всей работы. выигрыш по производительности тогда может быть существенным.

под капотом `LongAdder` хранит не одно значение, а массив ячеек. общая сумма ячеек и есть текущее значение. каждый поток работает со своей ячейкой, коллизии возникают реже. при вызове `sum()` значения ячеек складываются. такой обход не даёт атомарный снимок на фоне параллельных `add`: прибавление, которое идёт одновременно с суммированием, может в эту сумму не попасть. поэтому класс берут ради итога, а не ради постоянного точного чтения.

методы класса `LongAdder`:

- `void add(long x)`: добавляет заданное значение

- `void decrement()`: эквивалентно `add(-1)`

- `double doubleValue()`: возвращает `sum()` как значение типа `double` после расширяющего преобразования

- `float floatValue()`: возвращает `sum()` как значение типа `float` после расширяющего преобразования

- `void increment()`: эквивалентно `add(1)`

- `int intValue()`: возвращает `sum()` как значение типа `int` после сужающего преобразования

- `long longValue()`: эквивалентно `sum()`

- `void reset()`: сбрасывает накопленное состояние, оставляя сумму равной нулю

- `long sum()`: возвращает текущую сумму

- `long sumThenReset()`: эквивалентно `sum()`, за которым следует `reset()`

в примере выше промежуточное значение после каждого инкремента не требовалось, поэтому `AtomicLong` заменяется на `LongAdder`:

```java


import java.util.concurrent.atomic.LongAdder;



public class Program {

 

    public static void main(String[] args) throws InterruptedException{

         

        int numThreads = 1000;

        int incrementsPerThread = 1000;



        Counter counter = new Counter();

 

        Thread[] threads = new Thread[numThreads];

        for (int i = 0; i < numThreads; i++){

             

            threads[i] = new Thread(() ->{ 



                for (int j = 0; j < incrementsPerThread; j++) {

                    counter.increment();

                }

            });

            threads[i].start();

        }

        // небольшая задержка, чтобы потоки успели поработать

        Thread.sleep(1000);



        // ожидаем завершения всех потоков

        for (int i = 0; i < numThreads; i++){

            threads[i].join();

        }



        // проверяем значение счетчика

        System.out.println("Counter: " + counter.getCounter());

    }

}



class Counter{



    private LongAdder counter = new LongAdder();



    long getCounter() { return counter.longValue(); }   // возвращаем сумму всех значений (инкрементов) потоков

    void increment() { counter.increment();  }   //  увеличиваем на 1

}
```

по каркасу это та же программа. для счётчика вместо `AtomicLong` применяется `LongAdder`. метод `longValue()` возвращает значение счётчика, по сути сумму значений всех потоков. метод `increment()` увеличивает накопленное значение на 1, и каждый поток делает это без общей блокировки.

консольный вывод снова детерминирован и равен ожидаемому:

```bash


Counter: 1000000
```

после `join` всех потоков параллельных прибавлений уже нет, и сумма равна 1 000 000. посередине работы читать `sum()` как мгновенно точное значение нельзя: одновременные `increment()` могут попасть в обход ячеек только частично.
