семафор задаёт ещё одно средство ограничить доступ к ресурсу. в java он представлен классом `Semaphore` из пакета `java.util.concurrent`.

для управления доступом семафор использует счётчик разрешений. если значение больше нуля, поток получает доступ, и счётчик уменьшается на единицу. после окончания работы с ресурсом поток освобождает семафор, счётчик увеличивается на единицу. если счётчик равен нулю, поток блокируется и ждёт разрешения.

количество разрешений задают конструкторы класса `Semaphore`:

```java


Semaphore(int permits)

Semaphore(int permits, boolean fair)
```

параметр `permits` указывает число допустимых разрешений для доступа к ресурсу. параметр `fair` во втором конструкторе задаёт очередность получения доступа. при значении `true` разрешения предоставляются ожидающим потокам в том порядке, в каком они запрашивали доступ. при значении `false` разрешения предоставляются в неопределённом порядке: забрать разрешение может и поток, подошедший к семафору позже. очередь в порядке запроса снижает голодание за счёт учёта ожидающих.

разрешение у семафора получают методом `acquire()` в двух формах:

```java


void acquire() throws InterruptedException

void acquire(int permits) throws InterruptedException
```

для одного разрешения применяется первая форма, для нескольких разрешений сразу применяется вторая. второй вызов возвращается, только когда доступно всё запрошенное количество. пока поток разрешение не получил, он блокируется. обе формы объявляют `InterruptedException`: прерывание выводит поток из ожидания.

после работы с ресурсом разрешение освобождают методом `release()`:

```java


void release()

void release(int permits)
```

первый вариант освобождает одно разрешение, второй вариант освобождает количество разрешений, указанное в `permits`. семафор не запоминает, какой поток брал разрешение. `release()` может вызвать любой поток, и счётчик просто вырастет. освободить монитор `synchronized` может только тот поток, который его захватил.

семафор с одним разрешением в роли двоичного ограничителя общего счётчика:

```java


import java.util.concurrent.Semaphore;



public class Program {



    public static void main(String[] args) {

        

        Semaphore sem = new Semaphore(1); // 1 разрешение

        CommonResource res = new CommonResource();

        new Thread(new CountThread(res, sem, "CountThread 1")).start();

        new Thread(new CountThread(res, sem, "CountThread 2")).start();

        new Thread(new CountThread(res, sem, "CountThread 3")).start();

    }

}

class CommonResource{

    

    int x=0;  

}



class CountThread implements Runnable{



    CommonResource res;

    Semaphore sem;

    String name;

    CountThread(CommonResource res, Semaphore sem, String name){

        this.res=res;

        this.sem=sem;

        this.name=name;

    }

     

    public void run(){

        

        try{

            System.out.println(name + " ожидает разрешение");

            sem.acquire();

            res.x=1;

            for (int i = 1; i < 5; i++){

                System.out.println(this.name + ": " + res.x);

                res.x++;

                Thread.sleep(100);

            }

        }

        catch(InterruptedException e){System.out.println(e.getMessage());}

        System.out.println(name + " освобождает разрешение");

        sem.release();

    }

}
```

здесь общий ресурс `CommonResource` с полем `x`, которое изменяет каждый поток. потоки представлены классом `CountThread`: он получает семафор, ресурс и имя и выполняет действия над полем. в основном классе семафор создаётся как `new Semaphore(1)`, затем три потока запускаются. при одном разрешении секция выполняется по одному потоку. возможный вывод:

```consoletext

CountThread 1: 2

CountThread 1: 3

CountThread 1 освобождает разрешение

CountThread 3: 1

CountThread 3: 2

```

в этом `run()` вызов `release()` стоит после `catch`, а не рядом с успешным `acquire()`. если `acquire()` завершился `InterruptedException`, разрешение взято не было, однако `release()` всё равно увеличит счётчик, и разрешений станет больше, чем задано в конструкторе.

семафор применяют там, где доступ нужно ограничить по числу потоков, а не закрыть для всех, кроме одного. классическая задача: обедающие философы. философов пять, одновременно за столом могут сидеть не больше двух. нужно, чтобы все пообедали и при этом не возникло взаимной блокировки в борьбе за тарелку и вилку. в программе семафор ограничивает число сидящих, отдельные вилки не моделируются:

```java


import java.util.concurrent.Semaphore;



public class Program {



    public static void main(String[] args) {

        

        Semaphore sem = new Semaphore(2);

		for(int i=1;i<6;i++)

			new Philosopher(sem,i).start();

    }

}

// класс философа

class Philosopher extends Thread 

{

    Semaphore sem; // семафор. ограничивающий число философов

    // кол-во приемов пищи

    int num = 0;

    // условный номер философа

    int id;

    // в качестве параметров конструктора передаем идентификатор философа и семафор

    Philosopher(Semaphore sem, int id)

    {

		this.sem=sem;

		this.id=id;

    }

    

    public void run()

    {

		try

		{

			while(num<3)// пока количество приемов пищи не достигнет 3

			{

				//Запрашиваем у семафора разрешение на выполнение

				sem.acquire(); 

				System.out.println ("Философ " + id+" садится за стол");

				// философ ест

				sleep(500);

				num++;

					

				System.out.println ("Философ " + id+" выходит из-за стола");

				sem.release();

			

				// философ гуляет

				sleep(500);

			}

		}

		catch(InterruptedException e)

		{

			System.out.println ("у философа " + id + " проблемы со здоровьем");

		}

    }

}
```

третий и следующие блокируются в `acquire()`, пока кто-нибудь не вызовет `release()`. каждый философ ест три раза, условие `while(num<3)`: запрос разрешения, сообщение о посадке, `sleep(500)` на еду, увеличение `num`, сообщение о выходе, `release()`, затем ещё `sleep(500)`, уже прогулка без удержанного разрешения. при прерывании печатается сообщение о проблеме со здоровьем, и `run()` завершается. взаимная блокировка здесь не собирается: поток не держит часть ресурса в ожидании другой части, а берёт одно разрешение на весь обед и возвращает его целиком.
