`Executor`, исполнитель, принимает задачи и выполняет их. исполнитель заменяет явное создание потоков в клиентском коде и отделяет отправку задачи от политики исполнения: синхронный вызов, новый поток, пул или виртуальный поток.

`Executor` является функциональным интерфейсом с одним методом `execute()`:

```java


void execute(Runnable command)
```

метод принимает задачу `Runnable` и выполняет её в некоторый момент в будущем. момент и поток выбирает реализация. простейший пример:

```java


import java.util.concurrent.*;



class TaskExecutor implements Executor{

    

    public void execute(Runnable task){

        task.run();

    }

}



class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        var executor = new TaskExecutor();

        executor.execute(() -> {

                    

            System.out.println("Executing task in " + Thread.currentThread());

        });

        System.out.println("Main thread finished...");

    }

}
```

класс `TaskExecutor` реализует `Executor`. метод `execute()` вызывает у переданной задачи `run()` прямо в вызывающем потоке.

в `main` создаётся объект этого класса, и `execute()` получает короткую задачу `Runnable`. переданная задача выполняется.

в таком запуске политика исполнения совпадает с прямым вызовом `run()` в том же методе `main`, без отдельного интерфейса. контракт `Executor` при этом не требует асинхронности. синхронное выполнение, как в примере выше, где задача отработала в потоке `main`, контракту соответствует. исключение из `run()` в этой реализации выходит в вызывающий код.

чаще задача выполняется в потоке, отличном от потока вызывающего. исполнитель можно изменить так, чтобы на каждую задачу создавался новый поток:

```java


class TaskExecutor implements Executor{

    

    public void execute(Runnable task){

        new Thread(task).start();

    }

}
```

при запуске задача выполняется в отдельном потоке:

```bash


Main thread started...

Main thread finished...

Executing task in Thread[#34,Thread-0,5,main]
```

строка `Thread[#34,Thread-0,5,main]` построена `toString()` платформенного потока: идентификатор, имя `Thread-0`, приоритет 5, группа `main`. конкретные номера зависят от запуска. исключение из `run()` в этой реализации остаётся в новом потоке и обрабатывается его обработчиком неперехваченных исключений. в код `main` оно не попадает.

реализации `Executor` часто берут на себя координацию нескольких задач. собственная реализация интерфейса нужна редко: в java уже есть готовые классы, в том числе `ThreadPoolExecutor`. он управляет выполнением через пул потоков и тем снижает накладные расходы на создание потоков под каждую задачу.

интерфейс `ExecutorService` расширяет `Executor`. он добавляет завершение работы и методы, которые создают `Future` для слежения за одной или несколькими асинхронными задачами. через `Future` появляются результат и отмена, которых у `execute()` нет: `execute()` возвращает `void`. `ThreadPoolExecutor` реализует `ExecutorService`, а через него и `Executor`. дальше разбирается применение `ExecutorService`.

#### создание исполнителя

исполнителей создают статическими методами класса `Executors`. большинство этих методов собирает пул потоков. пул сокращает расходы на платформенные потоки. создание платформенного потока дорого: у него есть стек и соответствующий поток операционной системы. повторное использование уже созданных потоков дешевле создания новых. пул хранит свободные потоки, готовые принять задачу. когда нужно выполнить `Runnable` или `Callable`, из пула берётся один поток. после задачи поток не завершается, а возвращается в пул и обслуживает следующий запрос.

часть фабрик:

- `Executors.newCachedThreadPool()` создаёт пул, который заводит новые потоки по мере необходимости и повторно использует ранее созданные, когда они свободны. бездействующие потоки сохраняются в течение 60 секунд

- `Executors.newFixedThreadPool()` создаёт пул из фиксированного количества потоков. бездействующие потоки сохраняются неограниченное время, пока пул не остановлен. если отправленных задач больше, чем свободных потоков, лишние задачи помещаются в очередь и запускаются после завершения других

- `Executors.newSingleThreadExecutor()` создаёт `Executor` (фактически пул из одного потока) с одним рабочим потоком, который последовательно выполняет отправленные задачи

- `Executors.newVirtualThreadPerTaskExecutor()` создаёт `Executor`, который запускает каждую задачу в новом виртуальном потоке

у `newFixedThreadPool` есть обязательный аргумент размера пула. очередь этой фабрики не ограничена: при устойчивом превышении скорости поступления над скоростью исполнения очередь растёт. `newSingleThreadExecutor` гарантирует последовательное исполнение и один активный поток. перенастроить его на большее число потоков нельзя. `newFixedThreadPool` с размером 1 такую перенастройку допускает, если ссылку привести к `ThreadPoolExecutor`.

`newCachedThreadPool` рассчитан на большое число коротких задач: свободный поток берётся из кэша, а если свободного нет, создаётся новый. поток, простоявший 60 секунд, завершается и удаляется из кэша. потоки `newCachedThreadPool`, `newFixedThreadPool` и `newSingleThreadExecutor` демонами не являются. пока такая задача выполняется, jvm не завершает процесс.

`newVirtualThreadPerTaskExecutor` появился в java 21 вместе со стабильными виртуальными потоками. виртуальный поток не занимает платформенный поток на всё время задачи: на время блокировки носитель может исполнять другой виртуальный поток. число виртуальных потоков этой фабрикой не ограничено, отдельный пул платформенных потоков под них не собирается. виртуальные потоки являются демонами. удержание процесса до конца задач обеспечивает закрытие исполнителя. статус демона процесс не удерживает.

все перечисленные методы возвращают объекты классов, реализующих `ExecutorService`. `ExecutorService` расширяет `Executor`.

### отправка задачи исполнителю

для отправки `Runnable` или `Callable` в `ExecutorService` служат перегрузки `submit()`:

```java


Future<T> submit(Callable<T> task)

Future<?> submit(Runnable task)

Future<T> submit(Runnable task, T result)
```

вызов `submit()` передаёт задачу исполнителю, и тот планирует её выполнение. `execute()` возвращает `void`. `submit()` возвращает `Future`, через который получают результат или отменяют задачу.

вторая перегрузка `submit` возвращает `Future<?>`. его `get()` блокирует вызывающий поток до завершения задачи и затем возвращает `null`, потому что `Runnable` сам значения не производит.

третья перегрузка возвращает `Future<T>`. после завершения задачи `get()` возвращает объект, переданный вторым аргументом. этот аргумент и есть заранее известный результат, аналогично конструктору `FutureTask` для `Runnable`.

первая перегрузка принимает `Callable<T>`. `get()` возвращает значение, которое вычислил `call()`, либо завершается `ExecutionException`, если `call()` выбросил исключение.

### завершение исполнителя

после работы исполнителя ресурсы освобождают методом `close()`:

```java
void close()
```

закрытый исполнитель не принимает новых задач. `close()` блокирует вызывающий поток, пока все уже отправленные задачи не завершатся. если поток, вызывающий `close`, прерывают во время ожидания, отправленные задачи отменяются: поведение совпадает с `shutdownNow()`, исполняемые задачи прерываются, задачи из очереди не запускаются, ожидание продолжается, а статус прерывания перед возвратом восстанавливается. метод входит в `ExecutorService` с java 19, когда интерфейс стал `AutoCloseable`.

неявный вызов `close()` даёт конструкция `try-with-resources`:

```java


try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {



    ...............



    Future<V> f = submit(myCallable);



    .......................

} // здесь вызывается метод executor.close()
```

общий порядок применения `Executor` к задаче:

- одним из статических методов класса `Executors` (`newCachedThreadPool`, `newFixedThreadPool` и другие) создаётся объект `ExecutorService`

- у объекта `ExecutorService` для отправки задач `Callable` или `Runnable` вызывается `submit()`

- `submit()` возвращает `Future`. возвращённый объект сохраняют, чтобы запрашивать состояние задач, получать результат или отменять выполнение

- когда новые задачи больше не отправляются, у объекта `ExecutorService` вызывается `close()`, и исполнитель завершает работу

пример с виртуальными потоками:

```java


import java.util.concurrent.*;



class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {



            // запускаем 5 задач в виртуальных потоках

            for (int i = 0; i < 5; i++) {



                int taskNumber = i;



                executor.submit(() -> {

                    try{

                        Thread.sleep(1000);

                    }

                    catch(Exception ex) { 

                        System.out.println(ex.getMessage());

                    }

                    System.out.println("Executing task " + taskNumber + " in " + Thread.currentThread());

                });

            }

        } // executor.close() вызывается автоматически



        System.out.println("Main thread finished...");

    }

}
```

здесь `ExecutorService` создаёт новый виртуальный поток на каждую задачу `Runnable`:

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
```

через `submit()` на выполнение передаётся задача в виде лямбда-выражения:

```java
executor.submit(() -> {
```

для имитации работы каждая задача останавливается на 1 секунду. возвращённые `Future` в примере не сохраняются: ни результат, ни отмена через них не читаются. блок `try` заканчивается вызовом `close()`, и этот вызов ждёт все пять задач. поэтому строка `Main thread finished...` печатается после сообщений задач, хотя сам `submit()` не блокируется на `sleep` внутри лямбды. виртуальные потоки демоны, и без `close()` jvm могла бы завершить процесс раньше их окончания. консольный вывод имеет вид:

```bash


Main thread started...

Executing task 2 in VirtualThread[#39]/runnable@ForkJoinPool-1-worker-2

Executing task 3 in VirtualThread[#42]/runnable@ForkJoinPool-1-worker-5

Executing task 1 in VirtualThread[#37]/runnable@ForkJoinPool-1-worker-1

Executing task 0 in VirtualThread[#35]/runnable@ForkJoinPool-1-worker-4

Executing task 4 in VirtualThread[#46]/runnable@ForkJoinPool-1-worker-3

Main thread finished...
```

фрагмент `VirtualThread[#39]/runnable@ForkJoinPool-1-worker-2` показывает виртуальный поток и носитель из пула `ForkJoinPool`, на котором виртуальный поток был смонтирован в момент печати. номера и порядок пяти строк от запуска к запуску не фиксированы: задачи идут параллельно.
