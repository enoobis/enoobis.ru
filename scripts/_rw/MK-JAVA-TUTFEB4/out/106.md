модификатор `volatile` задаёт синхронизацию доступа к полю экземпляра без блокировки. при выполнении поток может кэшировать значение переменной, а компилятор и процессор могут переупорядочивать инструкции ради оптимизации, пока однопоточный результат сохраняется. если поле пишет один поток, а читает другой, кэша и перестановки уже достаточно, чтобы запись осталась невидимой. `volatile` как раз закрывает эту дыру. при таком объявлении компилятор и виртуальная машина учитывают, что поле может одновременно обновлять другой поток. при компиляции вставляется код, который гарантирует: изменение `volatile`-переменной в одном потоке видно любому другому потоку, читающему эту переменную.

основная проблема, которую решает `volatile`, это проблема видимости. по модели памяти java (java memory model, jmm) обычная запись не обязана быть сразу видна другому потоку. в ранней формулировке модели у каждого потока была собственная рабочая память. на процессоре ту же роль играют кэш и регистры: поток может изменить локальную копию, а другие потоки ещё читают прежнее значение из общей памяти или из своего кэша. в действующей спецификации тот же разрыв выражен отношением happens-before. без синхронизирующего действия чужое чтение не обязано увидеть запись.

простой пример с флагом остановки:

```java


public class Program {

 

    public static void main(String[] args) throws InterruptedException{

         

        Worker worker = new Worker();

        

        // Создаем "Поток А" и запускаем его. Он вызовет worker.run()

        Thread workerThread = new Thread(worker);

        workerThread.start(); // <-- Здесь запускается run()



        // Даем "Потоку А" немного времени, чтобы он вошел в цикл while(true)

        Thread.sleep(1000); // Ждем 1 секунду



        // "Поток Б" (главный поток) вызывает stop()

        worker.stop(); // <-- Здесь вызывается stop()



        // Ждем завершения "Потока А"

        // Если флаг running не был volatile, join() может ждать вечно!

        workerThread.join(2000); // Ждем до 2 секунд



        if (workerThread.isAlive()) {

            System.out.println("--- РЕЗУЛЬТАТ: Поток А все еще работает! ---");

            System.out.println("Поток А не увидел изменение running = false.");

            System.exit(1); // Завершаем программу, так как поток "завис"

        } else {

            System.out.println("--- РЕЗУЛЬТАТ: Поток А  успешно завершился. ---");

        }

    }

}



class Worker implements Runnable {



    // Флаг НЕ volatile

    private boolean running = true;



    @Override

    public void run() {

        

        // Этот код выполняется в "Потоке А"

        System.out.println("Поток А: Начинаю работу...");

        while (running) {

            // Здесь может быть некоторая работа

            

            // JIT-компилятор с высокой вероятностью "закэширует" переменную running

            // в регистре процессора, так как она не меняется внутри цикла.

        }

        // Эта строка может никогда не выполниться

        System.out.println("Поток А: Работа остановлена.");

    }



    public void stop() {

        // Этот код выполняется в "Потоке Б" (главном потоке)

        System.out.println("Поток Б: Отправляю команду на остановку...");

        this.running = false;

    }

}
```

класс `Worker` представляет реализацию интерфейса `Runnable`, задачу для исполнения в потоке. в классе два метода. `run()` это реализация `Runnable`, она выполняется в дочернем потоке, поток а, пока переменная `running` равна `true`. второй метод, `stop()`, сбрасывает `running` в `false` и вызывается из главного потока, поток б. поле при этом не объявлено `volatile`.

в методе `main` создаётся объект `Worker`, и его выполнение запускается в дочернем потоке `workerThread`:

```java


Worker worker = new Worker();

        

// Создаем "Поток А" и запускаем его. Он вызовет worker.run()

Thread workerThread = new Thread(worker);

workerThread.start(); // <-- Здесь запускается run()
```

при выполнении потока `workerThread` выполняется метод `run()` класса `Worker`. так как `running` равна `true`, поток а бесконечно выполняет цикл `while`.

далее после задержки в 1 секунду у объекта `Worker` флаг `running` сбрасывается в `false`, чтобы поток а завершился, и вызов `join()` ждёт завершения `workerThread` не дольше 2 секунд:

```java


Thread.sleep(1000); // Ждем 1 секунду



// "Поток Б" (главный поток) вызывает stop()

worker.stop();



// Ждем завершения "Потока А"

// Если флаг running не был volatile, join() может ждать вечно!

workerThread.join(2000); // Ждем до 2 секунд
```

после этого поток `workerThread` по замыслу примера должен завершиться. статус проверяется методом `isAlive()`, и на консоль выводится одно из двух сообщений. если флаг не был `volatile`, `join(2000)` может вернуться по пределу ожидания, пока рабочий поток ещё жив. тогда программа сообщает, что изменение не увидено, и завершается через `System.exit(1)`:

```java


if (workerThread.isAlive()) {

    System.out.println("--- РЕЗУЛЬТАТ: Поток А все еще работает! ---");

    System.out.println("Поток А не увидел изменение running = false.");

    System.exit(1); // Завершаем программу, так как поток "завис"

} else {

    System.out.println("--- РЕЗУЛЬТАТ: Поток А  успешно завершился. ---");

}
```

запуск в таком виде может дать следующий консольный вывод:

```bash


Поток А: Начинаю работу...

Поток Б: Отправляю команду на остановку...

--- РЕЗУЛЬТАТ: Поток А все еще работает! ---

Поток А не увидел изменение running = false.
```

поток а, скорее всего, оптимизировал свой цикл. раз переменная `running` не меняется внутри цикла, повторно читать её из общей памяти для одного потока бессмысленно. jit может оставить в регистре кэшированное значение `true`, и цикл не заканчивается. строка об остановке работы не выполняется. запись `false` в потоке б при этом есть, но отношения happens-before между этой записью и чтением в потоке а нет.

исправление меняет в классе `Worker` одну строку. объявление

```java
private boolean running = true;
```

заменяется на

```java
private volatile boolean running = true;
```

с `volatile` поток а при каждой итерации цикла `while` проверяет `running` по правилам видимости, а не по копии в регистре. как только поток б запишет туда `false`, поток а это увидит и выйдет из цикла.

### семантика volatile

`volatile` предоставляет две гарантии.

- гарантия видимости (visibility). для jvm такое поле нельзя постоянно держать в копии потока. запись в `volatile`-переменную публикуется в общую память, и последующее чтение того же поля её наблюдает

- чтение `volatile`-переменной берёт значение, согласованное с этой публикацией, и отменяет ранее закэшированное

если в примере `running` объявлена как `volatile boolean running = true`, поток а при каждой проверке `while (running)` вынужден согласованно прочитать поле. как только поток б записал `false` так, что запись предшествует этому чтению, поток а видит `false` и завершает цикл.

- гарантия упорядочивания (happens-before). `volatile` предотвращает те перестановки инструкций, которые компилятор и процессор делают ради производительности и которые сломали бы этот порядок. запись в `volatile`-переменную происходит после всех предыдущих чтений и записей в коде того же потока: те действия стоят в отношении happens-before к записи

- чтение `volatile`-переменной происходит до всех последующих чтений и записей того же потока

`volatile` действует как барьер памяти. всё, что поток сделал до записи в `volatile`-переменную, видно любому потоку, который после этой записи прочитал ту же переменную.

### атомарность и volatile

`volatile` не гарантирует атомарность составной операции. классический пример со счётчиком:

```java


private volatile int counter = 0;



public void increment() {

    counter++; // ОПАСНО!

}
```

видимость отдельного чтения и отдельной записи здесь есть, но `counter++` состоит из трёх шагов. чтение: берётся текущее значение `counter` из общей памяти, раз поле `volatile`. изменение: прочитанное значение увеличивается, например с 0 до 1. запись: новое значение `counter` сохраняется в общую память. два потока, а и б, вызывают `increment()` одновременно:

- поток а читает `counter`, значение 0

- поток б читает `counter`, значение 0

- поток а изменяет свою копию на 1 и записывает 1 в `counter`

- поток б изменяет свою копию, которая всё ещё 0, на 1 и записывает 1 в `counter`

в итоге возможно некорректное значение 1 при двух прибавлениях. `volatile` не защищает от состояния гонки (race condition) на составной операции.

### когда использовать volatile

`volatile` называют облегчённым механизмом синхронизации. его применяют, когда нужно обеспечить видимость изменений переменной между потоками и при этом выполнены оба условия:

- изменение переменной не зависит от её текущего значения. под это условие не подходят `counter++` и `x = x + 1`

- запись в переменную производит только один поток, а значение считывают один или несколько других потоков

флаг `running` оба условия выполняет: главный поток только записывает `false`, рабочий поток только читает, и новое значение не вычисляется из старого.
