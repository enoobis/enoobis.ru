по умолчанию поток, созданный конструктором `Thread`, выполняется как поток платформы. его предоставляет операционная система, в которой работает виртуальная машина java. для части нагрузок этого достаточно. поток платформы дорог в создании: стек резервируется сразу, типичный размер задаётся параметром `-Xss` и составляет порядка мегабайта, плюс учётные структуры в ядре. число таких потоков, которое процесс способен держать, ограничено памятью и планировщиком. на интенсивной нагрузке это ограничение становится узким местом и ограничивает пропускную способность.

долгие операции в прикладном коде чаще всего ждут внешний ресурс: сеть, чтение и запись файлов, базу данных. на время ожидания поток платформы другой код не исполняет, хотя ядро могло бы делать другую работу. в веб-приложении, которое принимает тысячи запросов в секунду, модель «один запрос на один поток платформы» упирается в это раньше, чем в арифметическую мощность процессора. длительная операция в потоке интерфейса к тому же замораживает ввод. виртуальный поток снимает это ограничение для кода, который большую часть времени блокируется.

виртуальный поток лёгкий, планирует и монтирует его виртуальная машина java. операционная система видит только несущие потоки платформы. одному процессу их доступны миллионы: стек живёт в куче и растёт по мере вызовов, целиком при создании он не резервируется. такой поток рассчитан на задачи, которые почти всё время блокированы, то есть на ввод-вывод, файлы, базу и сетевые запросы. длительный счёт без блокировок ему не подходит. этот код всё равно занимает ядро на всё время счёта, и полезное число потоков остаётся порядка числа аппаратных контекстов.

исполнение устроено как монтирование. планировщик сажает виртуальный поток на свободный поток платформы. такой поток платформы называют несущим (carrier): он несёт виртуальный поток, пока тот исполняет код. для исполнения виртуальный поток всё равно нуждается в потоке платформы. когда код доходит до блокирующей операции jdk, которая умеет парковать виртуальный поток, машина открепляет его от носителя и сохраняет кадры продолжения (continuation) в куче на время операции, например на время чтения файла. несущий поток в это время свободен и берёт другой виртуальный поток. когда операция заканчивается, планировщик снова монтирует продолжение на свободный несущий поток, не обязательно на прежний, и код идёт дальше. потоки платформы при этом заняты исполнением. ожидание сокета или диска остаётся на откреплённом виртуальном потоке.

на запросе к веб-приложению тот же путь выглядит так. для обработки запроса запускается виртуальный поток и монтируется на поток платформы. коду нужно прочитать файл, запускается чтение, и оно может длиться долго. на это время виртуальный поток открепляется от несущего потока, в котором выполнялся. несущий чтения не ждёт: при наличии другой работы к нему монтируется другой виртуальный поток. когда файл прочитан, первый поток возобновляет обработку и для этого снова монтируется на поток платформы. небольшой пул несущих потоков, по числу близкий к числу ядер, обслуживает куда больше запросов, чем в нём потоков.

основные свойства виртуальных потоков:

- масштаб. начальный след виртуального потока в куче составляет несколько сотен байт и дальше растёт со стеком вызовов. поток платформы сразу занимает стек порядка мегабайта. поэтому допустимы миллионы виртуальных потоков без сопоставимой нагрузки на систему

- тот же стиль кода. тело остаётся последовательным `Runnable` с обычными блокирующими вызовами, через тот же api, что и у потока платформы. отдельная цепочка обратных вызовов на каждое чтение не требуется

- совместимость. виртуальный поток является экземпляром `java.lang.Thread`. код и библиотеки, которые принимают `Thread` или `Runnable`, работают с ним через тот же api

### создание виртуального потока

виртуальный поток пользуется тем же api, что и поток платформы: `start`, `join`, `interrupt`, имя, флаг демона. создать его можно двумя способами:

- статический метод `Thread.startVirtualThread(Runnable task)`. в него передаётся задача `Runnable`, метод создаёт поток и ставит его в очередь

- `Thread.ofVirtual()`. метод возвращает строитель `Thread.Builder.OfVirtual`, то есть фабрику с накопленной настройкой, и через него задают имя и момент запуска

оба способа ниже.

#### метод `Thread.startVirtualThread`

самый короткий путь передаёт `Runnable` в `Thread.startVirtualThread`:

```java
public static Thread startVirtualThread(Runnable task)
```

минимальный пример. в виртуальном потоке печатается одно сообщение:

```java


class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        Runnable task = () -> {

            System.out.println("Hello from a virtual thread");

        };



        Thread.startVirtualThread(task); // запускаем виртуальный поток



        System.out.println("Main thread finished...");

    }

}
```

прогон может показать только строки главного потока:

```bash


Main thread started...

Main thread finished...
```

по такому выводу исполнения виртуального потока не видно. виртуальные потоки по умолчанию демоны и работают в фоне. процесс завершается, когда не осталось живых потоков помимо демонов. `main` является потоком платформы и демоном не является. как только он вернулся из `main`, таких потоков не остаётся, и машина завершает работу, не дожидаясь демона. сообщение виртуального потока появляется только если планировщик успел выполнить его раньше. api тот же, что у обычного потока, поэтому на возвращённом объекте вызывают `join()` и дожидаются завершения:

```java


class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        Runnable task = () -> {

            System.out.println("Hello from a virtual thread");

        };



        var t = Thread.startVirtualThread(task); // запускаем виртуальный поток

        try{

            t.join();       // ждем завершения виртуального потока

        }

        catch(InterruptedException _){

            System.out.println("Main thread interrupted");

        }



        System.out.println("Main thread finished...");

    }

}
```

после `join` вывод стабилен:

```bash


Main thread started...

Hello from a virtual thread

Main thread finished...
```

#### метод `ofVirtual()`

`ofVirtual()` возвращает строитель виртуального потока и нужен, когда требуется имя, фабрика или запуск отдельно от создания:

```java
public static Thread.Builder.OfVirtual ofVirtual()
```

тип строителя: `Thread.Builder.OfVirtual`. у него используются такие методы:

- `Thread.Builder.OfVirtual name(String name)`: задаёт имя потока

- `Thread.Builder.OfVirtual name(String prefix, long start)`: задаёт имя как префикс плюс счётчик. счётчик начинается со значения `start`, каждый следующий поток этого строителя получает следующее число

- `Thread start(Runnable task)`: создаёт виртуальный поток, ставит его в очередь и возвращает объект `Thread`

- `Thread unstarted(Runnable task)`: создаёт поток в состоянии `NEW` и не запускает его. исполнение начинается после явного `start()` на возвращённом объекте

- `ThreadFactory factory()`: возвращает фабрику `ThreadFactory`, которая создаёт виртуальные потоки с уже накопленной настройкой строителя

пример задаёт имя и сразу запускает поток:

```java


class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        Runnable task = () -> {

            System.out.println("Hello from " + Thread.currentThread().getName());

        };



        var t = Thread.ofVirtual()

                    .name("MyTask")  // устанавливаем имя

                    .start(task);     // запускаем поток

        try{

            t.join();       // ждем завершения виртуального потока

        }

        catch(InterruptedException _){

            System.out.println("Main thread interrupted");

        }



        System.out.println("Main thread finished...");

    }

}
```

консольный вывод:

```bash


Main thread started...

Hello from MyTask

Main thread finished...
```

создание и запуск можно разнести. `unstarted` возвращает поток в состоянии `NEW`, `start()` переводит его в очередь на исполнение:

```java


class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        var t = Thread.ofVirtual()

                    .name("MyTask")  // устанавливаем имя

                    .unstarted(() -> System.out.println("Hello from " + Thread.currentThread().getName()));



        t.start();     // запускаем поток

        try{

            t.join();       // ждем завершения виртуального потока

        }

        catch(InterruptedException _){

            System.out.println("Main thread interrupted");

        }



        System.out.println("Main thread finished...");

    }

}
```

#### особенности свойств виртуального потока

для виртуального потока `isVirtual()` возвращает `true`.

имени по умолчанию нет. `getName()` возвращает пустую строку, пока имя не задано через `setName` или через строитель. несколько потоков различают по имени только если имя назначено явно.

виртуальный поток всегда демон и не удерживает машину от начала завершения. сделать его недемоническим нельзя, `isDaemon()` возвращает `true`. по этой причине в первом примере без `join` сообщение могло не появиться.

приоритет фиксирован и равен `NORM_PRIORITY`. `setPriority` эффекта не имеет. монтированием заведует планировщик виртуальной машины. приоритет потока платформы на выбор виртуального потока не влияет. чтение этих свойств:

```java


class Program{



    public static void main(String[] args) {

         

        System.out.println("Main thread started...");



        Runnable task = () -> {



            Thread t = Thread.currentThread(); // получаем текущий поток



            System.out.println("Name: " + t.getName()); // если имя не задано, то t.getName() вернет пустую строку

            System.out.println("Is Vitual: " + t.isVirtual());

            System.out.println("Is Daemon: " + t.isDaemon());

            System.out.println("Priority: " + t.getPriority());

        };



        var thread = Thread.startVirtualThread(task);



        try{

            thread.join();       // ждем завершения виртуального потока

        }

        catch(InterruptedException _){

            System.out.println("Main thread interrupted");

        }



        System.out.println("Main thread finished...");

    }

}
```

консольный вывод:

```bash


Main thread started...

Name: 

Is Vitual: true

Is Daemon: true

Priority 5

Main thread finished...
```

пустая строка после `Name:` это пустое имя. строка `Is Vitual` напечатана так, как записано в литерале формата, значение при этом истинно. приоритет равен 5.

### применимость виртуальных потоков

виртуальные потоки окупаются там, где много одновременных ожиданий:

- задачи, ограниченные вводом-выводом (i/o-bound): веб-серверы, микросервисы, работа с базами, любое большое число блокирующих чтений и записей

- высоконагруженные системы, которым нужно держать тысячи и миллионы одновременных подключений или запросов

для других нагрузок устройство иное:

- задачи, ограниченные процессором (cpu-bound): плотные вычисления, обработка больших объёмов данных в памяти. поток почти не блокируется, откреплять его негде, и преимущества виртуальных потоков здесь невелики. число рабочих потоков держат около числа ядер, для этого подходит пул потоков платформы

- долгое удержание монитора `synchronized` на jdk до 24. пока виртуальный поток находится внутри `synchronized`, он закреплён (pin) за несущим потоком: планировщик не открепляет его, и несущий простаивает вместе с ним, даже если внутри монитора поток заблокируется. другие виртуальные потоки этот несущий тогда не получают. начиная с jdk 24 (jep 491) монитор `synchronized` виртуальный поток за несущим не закрепляет. блокировки `java.util.concurrent`, которые паркуют поток через `LockSupport`, открепляют виртуальный поток ещё с jdk 21

- вызовы нативных методов (`JNI`) и foreign function. нативный кадр исполняется на стеке несущего потока. на время такого вызова виртуальный поток остаётся смонтированным, как и в случае закрепления, и несущий занят до возврата из нативного кода
