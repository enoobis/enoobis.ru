во время выполнения программы возникают ошибки, и вина разработчика для этого не обязательна. часть сбоев трудно предвидеть, а некоторые предвидеть нельзя. при передаче файла может оборваться сетевое соединение. такие ситуации называются **исключениями**: нормальный порядок инструкций прерывается, и управление передаётся обработчику либо механизму аварийного завершения.

в java для этих ситуаций есть специальная конструкция **try...catch...finally**. если исключение возникает в блоке `try`, управление переходит в блок `catch`, способный его обработать. если подходящий `catch` не найден ни в этом методе, ни у вызывающих, пользователю показывается сообщение о необработанном исключении, и дальнейшее выполнение программы останавливается. чтобы ошибка не завершала процесс аварийно, применяют блок **try..catch..finally**:

```java


try{

     

}

catch (Тип_исключения переменная){

     

}

finally{

     

}
```

при входе в **try...catch..finally** сначала выполняются инструкции блока **try**. если исключения не было, после `try` выполняется блок **finally**, и на этом конструкция завершается. блок `catch` в этом пути пропускается.

если в блоке `try` исключение всё же возникло, обычный порядок останавливается, и среда выполнения ищет блок **catch**, чей тип совместим с типом исключения. найденный блок `catch` выполняется, и после него выполняется блок `finally`.

если подходящий блок `catch` не найден, исключение не перехватывается: среда выполнения формирует сообщение, и выполнение программы прекращается. блок `finally` текущего `try` при этом всё равно выполняется, прежде чем исключение уйдёт к вызывающему методу.

### применение конструкции try..catch..finally

простейший пример:

```java


class Program{

     

	public static void main(String[] args) {

         

        int a = 5;

        int b = 0;

        int result = a / b;

        System.out.printf("Результат: %d\n", result);

    }

}
```

здесь целое делится на 0, и среда выполнения порождает исключение. на консоли появляется такая картина:

```bash


Exception in thread "main" java.lang.ArithmeticException: / by zero

	at Program.main(Program.java:7)
```

сообщение говорит, что во время выполнения возникло исключение типа `java.lang.ArithmeticException`, и добавляет краткий текст `/ by zero`. по этому тексту видно, что причина в делении на ноль. для типа `int` деление на ноль именно исключение. для `double` та же операция по ieee 754 даёт бесконечность и исключения не бросает. ниже в трассировке указано место: метод `Program.main` в файле `Program.java`, строка 7. по номеру строки проблемный участок ищут в исходном файле.

деление константы на ноль в исходном тексте искусственно: делитель известен до запуска. если делитель приходит извне, перед делением его сравнивают с нулём и тем самым не доводят программу до аварийного завершения:

```java


class Program{

     

	public static void main(String[] args) {

         

        divide(10, 2);

        divide(10, 0);

    }



    static void divide(int a, int b){



        if(b != 0) System.out.println(a / b);

        else System.out.println("Деление на ноль");

    }

}
```

не каждую исключительную ситуацию можно отсечь такой проверкой заранее: обрыв сети, ошибка ввода-вывода, отказ внешнего сервиса становятся известны только в момент операции. для них применяют `try...catch...finally`, чтобы аварийное завершение заменить обработкой:

```java


class Program{

     

	public static void main(String[] args) {

         

        divide(10, 0);

        System.out.println("Конец программы");

    }



    static void divide(int a, int b){



        try{



            int result = a / b;

            System.out.printf("Результат: %d\n", result);

        }

        catch(Throwable _){



            System.out.println("Возникло исключение!");

        }

        finally{



            System.out.println("Блок finally");

        }

    }

}
```

разбор по частям. сначала фрагмент, который потенциально порождает исключение:

```java
int result = a / b;
```

его помещают в блок `try`:

```java


try{



    int result = a / b;

    System.out.printf("Результат: %d\n", result);

}
```

если в `try` возникает исключение (при `b = 0`), обычный порядок останавливается и управление переходит к `catch`. синтаксис обработчика:

```java
catch (тип_исключения имя_переменной){



    // выполняемые инструкции при возвникновении исключения

}
```

после `catch` в скобках стоят тип исключения и имя переменной, как при объявлении локальной переменной. **если возникшее исключение совместимо с этим типом, выполняется данный блок catch.** совместимость означает, что динамический тип исключения является этим типом или его подтипом.

в примере взят самый широкий тип, под который подходит любое исключение: класс `Throwable`, корень всей иерархии.

```java


catch(Throwable _){



    System.out.println("Возникло исключение!");

}
```

обработчик `Throwable` принимает любое исключение, в том числе деление на ноль. он же принимает и ошибки `Error`, которые обычно не обрабатывают в прикладном коде. для этого примера переменная исключения не нужна и нигде не читается, поэтому вместо имени стоит прочерк `_`. безымянная переменная в `catch` стандартна с java 22. в более ранних версиях имя обязательно, даже если переменная не используется. тело `catch` только печатает диагностическое сообщение.

после `catch` идёт `finally`. он тоже печатает сообщение на консоль:

```java


finally{



    System.out.println("Блок finally");

}
```

`finally` выполняется и на нормальном пути, и после обработанного исключения, и когда исключение уходит дальше. пропускают его только при аварийной остановке самой виртуальной машины, при `System.exit` и при бесконечном цикле в `try` или `catch`.

### выполнение try..catch..finally

ниже та же конструкция разбирается на двух путях: неудачное деление и успешное. первый путь, делитель равен 0:

```java


public static void main(String[] args) {

         

    divide(10, 0);

    System.out.println("Конец программы");

}
```

делитель равен 0, деление не может завершиться нормально, и консольный вывод такой:

```bash


Возникло исключение!

Блок finally

Конец программы
```

по инструкциям ход программы выглядит так:

- `divide(10, 0);` управление переходит в метод `divide`

- `int result = a / b;` поскольку `b` равно 0, возникает `ArithmeticException`, и управление переходит в блок `catch`. инструкция печати результата не выполняется

- `System.out.println("Возникло исключение!");` обработчик завершается, управление переходит в блок `finally`

- `System.out.println("Блок finally");` блок `finally` отработал, метод `divide` закончил выполнение, управление возвращается в метод `main`

- `System.out.println("Конец программы");` последняя инструкция `main` выполнена, программа завершена

исключение перехвачено, поэтому после `divide` метод `main` продолжается. без `catch` до строки «конец программы» выполнение бы не дошло.

второй путь, делитель не равен 0:

```java


public static void main(String[] args) {

         

    divide(10, 2);

    System.out.println("Конец программы");

}
```

деление выполняется успешно, консольный вывод такой:

```bash


Результат: 5

Блок finally

Конец программы
```

по инструкциям ход программы выглядит так:

- `divide(10, 2);` управление переходит в метод `divide`

- `int result = a / b;` `b` равно 2, деление выполняется, переменная `result` получает значение 5

- `System.out.printf("Результат: %d\n", result);` блок `try` завершился без исключения, блок `catch` пропускается, управление переходит в `finally`

- `System.out.println("Блок finally");` блок `finally` отработал, метод `divide` закончил выполнение, управление возвращается в метод `main`

- `System.out.println("Конец программы");` последняя инструкция `main` выполнена, программа завершена

на обоих путях `finally` выполняется. различается только то, был ли выполнен `catch`.

### сокращённая версия конструкции try..catch..finally

в конструкции `try..catch..finally` обязателен только блок `try`. один из двух остальных можно опустить. остаётся либо `catch`, если блок `finally` не нужен, либо `finally`, если перехватывать исключение в этом методе не требуется. часто обходятся без `finally` и пишут только `try..catch`:

```java


static void divide(int a, int b){



    try{



        int result = a / b;

        System.out.printf("Результат: %d\n", result);

    }

    catch(Throwable _){



        System.out.println("Возникло исключение!");

    }

}
```

можно оставить `finally` и не писать `catch`. тогда при исключении оно не обрабатывается, блок `finally` выполняется, и программа завершается с ошибкой: исключение уходит к вызывающему, а в `main` необработанное исключение останавливает поток:

```java


static void divide(int a, int b){



    try{



        int result = a / b; 

        System.out.printf("Результат: %d\n", result);

    }

    finally{



        System.out.println("Блок finally");

    }

}
```

### возвращение результата из try..catch..finally

внутри `try..catch..finally` инструкция `return` возвращает результат из метода. пример разбора строки в число:

```java


static int parse(String s)

{

    try

    {

        return Integer.parseInt(s);

    }

    catch(Throwable _){



        System.out.println("Ошибка преобразования");

        return 0;

    }

 }
```

в блоке `try` возвращается результат `Integer.parseInt()`. метод преобразует строку в `int`. если строка не является записью целого, возникает исключение `NumberFormatException`. блок `catch` перехватывает его и возвращает 0. возвращать ли значение при ошибке и какое именно, этот фрагмент не решает: 0 одновременно является и законным результатом разбора строки `"0"`, и сигналом сбоя, поэтому вызывающий код эти два исхода не различает. в java для такой развилки есть отдельные приёмы, в том числе обёртывание результата и специальные типы исключений. здесь пример берётся только как схема передачи управления.

дальше метод `parse` вызывается, и из него читается результат:

```java


class Program{

     

	public static void main(String[] args) throws Exception {

         

        int result = parse("5"); 

        System.out.println(result);     // 5



        result = parse("t");            // Ошибка преобразования

        System.out.println(result);     // 0

    }



    static int parse(String s)

    {

        try

        {

            return Integer.parseInt(s);

        }

        catch(Throwable _){



            System.out.println("Ошибка преобразования");

            return 0;

        }

    }

}
```

строка `"5"` разбирается успешно, метод возвращает 5. строка `"t"` порождает исключение, печатается «ошибка преобразования», метод возвращает 0.

если у `try` есть блок `finally`, этот блок выполняется обязательно, в том числе после `return` в `try` или `catch`. `return` из `try` не выходит из метода мгновенно: значение откладывается, выполняется `finally`, и только потом метод завершается. если `finally` тоже содержит `return`, этот возврат подменяет отложенное значение. пример:

```java


class Program{

     

	public static void main(String[] args) throws Exception {

         

        int result = parse("5");

        System.out.println(result);        // -1



        result = parse("t");                // Ошибка преобразования 

        System.out.println(result);        // -1

    }



    static int parse(String s)

    {

        try

        {

            return Integer.parseInt(s);

        }

        catch(Throwable _){



            System.out.println("Ошибка преобразования");

            return 0;

        }

        finally{

            return -1;

        }

    }

}
```

блок `finally` возвращает -1. преобразование может пройти успешно или завершиться исключением, метод всё равно вернёт -1, потому что после `try` и `catch` обязательно выполняется `finally`, а его `return` затирает и 5, и 0. тот же `return` в `finally` подавляет и исключение, которое ещё не было перехвачено: вместо распространения исключения вызывающий получает значение из `finally`. поэтому `return` в `finally` в обычном коде не используют.

### обработка исключений и условные конструкции

создание объекта исключения включает съём трассировки стека, и это заметная по времени операция. сам вход в блок `try`, если исключения не было, устроен таблицей обработчиков в байткоде и на нормальном пути почти ничего не стоит. дорогое место появляется тогда, когда исключительная ситуация ожидаема и возникает часто: объект исключения строится снова и снова. если ситуацию можно предвидеть проверкой предусловия, её обрабатывают условной конструкцией, без `try..catch`. для деления на 0 предпочтительнее сравнить второй операнд с нулём, чем порождать `ArithmeticException` и тут же его ловить. исключение оставляют для сбоев, которые в этой точке не являются нормальной ветвью алгоритма.
