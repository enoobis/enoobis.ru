обобщения, или generics (обобщённые типы и методы), снимают жёсткую привязку класса, интерфейса и метода к одному заранее выбранному типу. один и тот же исходный текст повторно используется с разными аргументами типа. проверку совместимости при этом берёт на себя компилятор.

чтобы увидеть происхождение этого механизма, сначала разбирается задача, которая до обобщений решалась через `Object`. ниже класс для хранения данных пользователя.

```java


class Person {



    private int id;

    private String name;



    int getId(){ return id; }

    String getName(){ return name; }



    Person(int id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

класс `Person` определяет два поля: `id`, уникальный идентификатор пользователя, и `name`, имя пользователя. идентификатор задан числом: значения 1, 2, 3, 4 и далее.

для идентификатора нередко берут и строковые значения. у числового и у строкового представления есть свои плюсы и минусы. в момент написания класса ещё неизвестно, что лучше хранить в идентификаторе: строки или числа. класс могут использовать и другие разработчики со своим решением. идентификатор, например, оформляют отдельным классом.

на первый взгляд из положения выходят, объявив поле `id` типом `Object`. `Object` является корнем иерархии ссылочных типов, поэтому в такое поле помещается и строка, и число после упаковки:

```java


class Person {



    private Object id;      // универсальный идентификатор - и числа, и строки

    private String name;



    Object getId(){ return id; }

    String getName(){ return name; }



    Person(Object id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

дальше в программу передают в конструктор и числа, и строки:

```java


class Program {



    public static void main(String[] args){

        

        var tom = new Person(546, "Tom");

        tom.print();	// Person. Id: 546;  Name: Tom





        var bob = new Person("zpio9", "Bob");

        bob.print();	// Person. Id: zpio9;  Name: Bob

    } 

}



class Person {



    private Object id;      // универсальный идентификатор - и числа, и строки

    private String name;



    Object getId(){ return id; }

    String getName(){ return name; }



    Person(Object id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

по замыслу примера идентификатор принимается и числом, и строкой. решение при этом слабое: каждое сохранение и каждое чтение проходит через преобразование типов.

при передаче в конструктор значения типа `int` это значение упаковывается в `Integer`, а затем ссылка восходит к `Object`. цепочка типов: `int` -> `Integer` -> `Object`.

```java


var tom = new Person(546, "Tom");	// преобразование значения int в тип Integer и Object
```

со строкой тоже выполняется восходящее преобразование, `String` -> `Object`. оно менее критично: представление строки не меняется, меняется только статический тип ссылки.

```java
var bob = new Person("zpio9", "Bob");
```

восходящее преобразование выполняется автоматически. чтобы снова получить значение в переменной типа `int` или `String`, нужно явное нисходящее преобразование:

```java


int tomId = (int)tom.getId();		// Object -> int

String bobId = (String) bob.getId();		// Object -> String
```

вторая проблема: безопасность типов. неверное приведение не видно компилятору и срывается уже при выполнении.

```java


class Program {



    public static void main(String[] args) {

        

        var tom = new Person(546, "Tom");

        String tomId = (String)tom.getId();  // !Ошибка  - Исключение java.lang.ClassCastException

        System.out.printf("tom id: %s\n", tomId);

    } 

}
```

какой объект лежит в `id`, по статическому типу `Object` не видно. попытка прочитать числовой идентификатор как `String` даёт исключение `java.lang.ClassCastException`. исключение возникает на этапе выполнения. на этапе компиляции эта ошибка не отслеживается: приведение к `String` для ссылки типа `Object` синтаксически законно, даже если динамический тип другой.

ситуация выглядит искусственной, пока в том же тексте видно, что в конструктор передано число, и приводить его к строке нет причины. в реальной разработке фактический тип значения в `id` часто неизвестен. чтение в нужном типе тогда снова заканчивается `java.lang.ClassCastException`.

отдельная версия класса `Person` на каждый тип идентификатора проблему не снимает: реализации приходится копировать.

для этих задач в java добавлены обобщения: обобщённые типы и методы. их же называют универсальными типами и методами, по-английски generics. обобщение позволяет указать конкретный тип, с которым будет работать данный экземпляр. класс `Person` объявляется обобщённым:

```java


class Person<T> {



    private T id;  

    private String name;



    T getId(){ return id; }

    String getName(){ return name; }



    Person(T id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

угловые скобки в описании `class Person<T>` показывают, что класс обобщённый. тип `T`, заключённый в угловые скобки, будет использоваться этим классом. буква `T` не обязательна: годится другая буква или набор символов. на этапе написания кода конкретный тип ещё неизвестен, им может оказаться любой ссылочный тип. параметр `T` в угловых скобках называют универсальным параметром: на его место подставляют нужный тип.

метод `getId()` возвращает значение переменной `id`. переменная имеет тип `T`, поэтому метод тоже возвращает объект типа `T`: `T getId()`.

на место `T` подставляют, например, `Integer`: число, которым представлен номер пользователя. тем же параметром может быть `String` или любой другой ссылочный тип, класс или интерфейс.

```java


class Program {



    public static void main(String[] args){

        

        Person<Integer> tom = new Person<Integer>(546, "Tom");   // преобразование типов не нужно

        Person<String> bob = new Person<String>("abc123", "Bob"); // преобразование типов не нужно

        

        Integer tomId = tom.getId();      // преобразование типов не нужно

        String bobId = bob.getId();  // преобразование типов не нужно

        

        System.out.println(tomId);   // 546

        System.out.println(bobId);   // abc123

    } 

}



class Person<T> {



    private T id;  

    private String name;



    T getId(){ return id; }

    String getName(){ return name; }



    Person(T id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

при объявлении переменной и при создании объекта после имени класса в угловых скобках указывают, какой тип стоит на месте универсального параметра. первый объект использует `Integer`: вместо `T` подставляется `Integer`.

```java
Person<Integer> tom = new Person<Integer>(546, "Tom");
```

с точки зрения проверки типов эта подстановка даёт класс с полем типа `Integer`:

```java


class Person {



    private Integer id;  

    private String name;



    Integer getId(){ return id; }

    String getName(){ return name; }



    Person(Integer id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

так подстановку видит проверка типов. отдельный класс в байткоде под неё не порождается. java применяет стирание типов: аргумент типа после компиляции не хранится. в рантайме остаётся один класс `Person`, а там, где исходник читает значение как `Integer` или `String`, компилятор вставляет проверку приведения. отдельных классов для `Person<Integer>` и `Person<String>` нет. этим java отличается от шаблонов c++, где подстановка порождает отдельный код, и от обобщений c#, где аргумент типа сохраняется во время выполнения.

обобщения работают только с объектами и не работают с примитивными типами. допустима запись `Person<Integer>`. типы `int` и `double` в аргументе типа недопустимы, например `Person<int>` и `Person<double>`. вместо примитивов используют классы-обёртки: `Integer` вместо `int`, `Double` вместо `double` и далее по тому же правилу. литерал `546`, переданный в `Person<Integer>`, по-прежнему упаковывается в `Integer`. явного приведения идентификатора при этом уже нет.

второй объект использует тип `String`:

```java
Person<String> bob = new Person<String>("abc123", "Bob");
```

с java 7 аргумент типа в выражении `new` можно не повторять, если он выводится из типа переменной: `new Person<>(546, "Tom")`. в примерах аргумент указан явно, чтобы подстановка была видна в тексте.

передача для параметра `id` значения другого типа даёт ошибку компиляции. строка не совместима с аргументом `Integer`:

```java


Person<Integer> tom = new Person<Integer>("546", "Tom");  // ошибка компиляции
```

при чтении через `getId()` операция приведения в исходнике больше не нужна. статический тип результата уже равен аргументу типа:

```java
Integer tomId = tom.getId();      // преобразование типов не нужно
```

ручное приведение при этом уходит из исходника, и `ClassCastException` при чтении в неверном типе тоже не возникает. если типы не сходятся, компилятор сообщает об этом до запуска. программа не доходит до падения на приведении. выигрыш по времени выполнения относительно версии с `Object` невелик: после стирания проверки приведения в байткоде остаются, а упаковка примитива никуда не девается. сокращается другое: число потенциальных ошибок и объём преобразований, которые иначе пишут вручную. исходный текст больше не зависит от удачного приведения в каждом месте чтения.

### универсальный параметр как обобщённый тип

универсальный параметр сам может быть обобщённым типом. аргумент типа тогда содержит собственные угловые скобки.

```java


// класс компании

class Company<P>{



    private P ceo;  // президент компании

    P getCEO(){ return ceo; }



    Company(P ceo){



        this.ceo = ceo;

    }

}



class Person<T> {



    private T id;  

    private String name;



    T getId(){ return id; }

    String getName(){ return name; }



    Person(T id, String name)

    {

        this.id = id; 

        this.name = name;

    }

}
```

класс `Company` определяет поле `ceo`: президент компании. в это поле передаётся значение типа `Person`, уже типизированное своим аргументом.

```java


class Program {



    public static void main(String[] args){

        

        Person<Integer> tom = new Person<Integer>(546, "Tom");

        Company<Person<Integer>> melkosoft=  new Company<Person<Integer>>(tom);

        

        var ceo = melkosoft.getCEO();

        System.out.println(ceo.getId());  // 546

        System.out.println(ceo.getName());  // Tom

    } 

}
```

внешний аргумент `Company<Person<Integer>>` есть `Person<Integer>`. внутренний аргумент `Person` есть `Integer`. чтение `getCEO()` возвращает президента в том типе, который был подставлен, и `getId()` дальше даёт `Integer` без ручного приведения.

### использование нескольких универсальных параметров

у обобщения может быть несколько универсальных параметров сразу. они принимают одинаковые или различные типы.

```java






class Person<T, K> {



    private T id;  

    private K password;  

    private String name;



    T getId(){ return id; }

    K getPassword(){ return password; }

    String getName(){ return name; }



    Person(T id, String name, K pass)

    {

        this.id = id; 

        this.name = name;

        this.password = pass;

    }

}
```

класс `Person` использует два универсальных параметра. один задаёт тип идентификатора `id`, другой задаёт тип поля пароля. пароль существует в разных формах: текстовый, голосовой и других, поэтому второй параметр не фиксируют заранее. применение класса:

```c#


class Program {



    public static void main(String[] args){

        

        Person<Integer, String> tom = new Person<Integer, String>(546, "Tom", "qwerty12345");

        System.out.println(tom.getId());  // 546

        System.out.println(tom.getPassword());  // qwerty12345

    } 

}
```

объект `Person` типизирован типами `Integer` и `String`. универсальный параметр `T` есть `Integer`, параметр `K` есть `String`. порядок аргументов в угловых скобках совпадает с порядком параметров в объявлении `Person<T, K>`.

### обобщённые интерфейсы

интерфейсы, как и классы, бывают обобщёнными:

```java


public class Program{

     

	public static void main(String[] args) {

         

		Accountable<String> acc1 = new Account("1235rwr", 5000);

		Account acc2 = new Account("2373", 4300);

		System.out.println(acc1.getId());

		System.out.println(acc2.getId());

	}

}

interface Accountable<T>{

	T getId();

	int getSum();

	void setSum(int sum);

}

class Account implements Accountable<String>{

	

    private String id;

	private int sum;

	

	Account(String id, int sum){

		this.id = id;

		this.sum = sum;

	}

	

    public String getId() { return id; }

	public int getSum() { return sum; }

	public void setSum(int sum) { this.sum = sum; }

}
```

интерфейс `Accountable` задаёт базовый функционал банковского счёта: метод возврата идентификатора и методы получения и установки суммы. класс `Account` этот интерфейс реализует.

при реализации такого интерфейса есть две стратегии. в примере выше использована первая: у универсального параметра интерфейса сразу указан конкретный тип, здесь `String`, в записи `Accountable<String>`. класс, реализующий интерфейс, жёстко привязан к этому типу. второй объект `Account` в том же примере тоже хранит строковый идентификатор, но переменная `acc2` объявлена самим классом `Account`, без типа интерфейса.

вторая стратегия: класс тоже объявляют обобщённым и пробрасывают тот же универсальный параметр в интерфейс. привязка к конкретному типу откладывается до создания объекта.

```java


public class Program{

     

	public static void main(String[] args) {

         

		Account<String> acc1 = new Account<String>("1235rwr", 5000);

		Account<String> acc2 = new Account<String>("2373", 4300);

		System.out.println(acc1.getId());

		System.out.println(acc2.getId());

	}

}

interface Accountable<T>{

	T getId();

	int getSum();

	void setSum(int sum);

}

class Account<T> implements Accountable<T>{

	

    private T id;

	private int sum;

	

	Account(T id, int sum){

		this.id = id;

		this.sum = sum;

	}

	

    public T getId() { return id; }

	public int getSum() { return sum; }

	public void setSum(int sum) { this.sum = sum; }

}
```

здесь и `acc1`, и `acc2` имеют тип `Account<String>`. подстановка `String` стоит в аргументе класса, а интерфейс `Accountable<T>` получает тот же `T`. если понадобится счёт с числовым идентификатором, объявление меняется на `Account<Integer>` без новой копии класса.

### обобщённые методы

кроме обобщённых типов объявляют обобщённые методы. универсальный параметр принадлежит методу. класс `Printer` в примере обычный, параметр `T` существует только у `print`.

```java


public class Program{

     

	public static void main(String[] args) {

         

		Printer printer = new Printer();

		String[] people = {"Tom", "Alice", "Sam", "Kate", "Bob", "Helen"};

		Integer[] numbers = {23, 4, 5, 2, 13, 456, 4};

		printer.<String>print(people);

		printer.<Integer>print(numbers);

	}

}



class Printer{

	

	public <T> void print(T[] items){

		for(T item: items){

			System.out.println(item);

		}

	}

}
```

особенность обобщённого метода: универсальный параметр стоит в объявлении после всех модификаторов и перед типом возвращаемого значения.

```java
public <T> void print(T[] items)
```

внутри метода все вхождения `T` обозначают этот универсальный параметр. массив `T[]` есть массив ссылок на выбранный тип, а переменная цикла `item` имеет тот же тип. отдельного параметра у класса для этого не требуется.

при вызове перед именем метода в угловых скобках можно явно указать тип, который подставляется на место универсального параметра. такую запись называют свидетелем типа:

```java


printer.<String>print(people);

printer.<Integer>print(numbers);
```

в этом вызове, как и в большинстве вызовов, параметр типа опускают. явные свидетели `<String>` и `<Integer>` писать не обязательно. компилятору хватает информации, чтобы выбрать метод: он сопоставляет типы аргументов с обобщённым типом `T` и выводит, что в первом вызове `T` есть `String`, а во втором `T` есть `Integer`. достаточно прямого вызова:

```java


Printer printer = new Printer();

String[] people = {"Tom", "Alice", "Sam", "Kate", "Bob", "Helen"};

Integer[] numbers = {23, 4, 5, 2, 13, 456, 4};

printer.print(people);

printer.print(numbers);
```

вывод типа смотрит на аргументы вызова. массив строк задаёт `T` как `String`, массив `Integer` задаёт `T` как `Integer`. если аргументы со свидетелем не сходятся, ошибка снова обнаруживается при компиляции.

### обобщённые конструкторы

конструкторы, как и методы, бывают обобщёнными. универсальные параметры пишут в угловых скобках перед именем конструктора. параметр принадлежит конструктору: сам класс может оставаться необобщённым.

```java


public class Program{

     

	public static void main(String[] args) {

         

		Person acc1 = new Person("cid2373", 5000);

		Person acc2 = new Person(53757, 4000);

		System.out.println(acc1.getId());

		System.out.println(acc2.getId());

	}

}



class Person{

	

    private String id;

	private int sum;

	

	<T>Person(T id, int sum){

		this.id = id.toString();

		this.sum = sum;

	}

	

    public String getId() { return id; }

	public int getSum() { return sum; }

	public void setSum(int sum) { this.sum = sum; }

}
```

конструктор принимает параметр `id` типа `T`. в теле значение превращается в строку вызовом `toString()` и записывается в поле `id` типа `String`. параметр `T` нужен только на входе, чтобы принять идентификатор любого ссылочного типа. наружу класс отдаёт уже строку, поэтому у экземпляра обобщения нет: и `acc1`, и `acc2` имеют один и тот же тип `Person`. для строкового аргумента `T` выводится как `String`, для числового литерала аргумент упаковывается и `T` выводится как `Integer`.
