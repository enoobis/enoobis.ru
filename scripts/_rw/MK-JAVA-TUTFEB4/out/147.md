программу целиком можно написать на java: язык покрывает широкий круг задач, а библиотек и фреймворков на нём много. остаётся класс ситуаций, где рядом с кодом java нужен код на другом языке, чаще всего на c или c++. типичные причины две. первой программе нужен доступ к системной функции или устройству, для которых у платформы java нет готового api. второй уже есть большой проверенный и отлаженный код на другом языке, и его встраивают в программу на java, а не переписывают. ниже разобрано, как программа на java вызывает нативный код на c и c++.

начиная с java 1.1 в платформе есть отдельный api для вызова нативного кода c: **java native interface** (jni). более поздний и более компактный по связующему коду api, foreign functions and memory (ffm api), входил в jdk как preview около java 20 и стал постоянной частью платформы в java 22. jni при этом остаётся рабочим механизмом, особенно на старых версиях платформы. сначала разбираются базовые шаги jni.

связывание нативного метода с программой java через jni идёт в фиксированном порядке:

- в классе java объявляется нативный метод-обёртка над функцией c
- команда `javac -h` порождает заголовочный файл c с объявлением этой функции
- на c пишется тело нативного метода
- код c компилируется в разделяемую библиотеку
- библиотека загружается в программе на java

дальше каждый шаг разбирается отдельно. пропуск любого из них даёт одну и ту же наблюдаемую ошибку на запуске: виртуальная машина не находит реализацию нативного метода.

### определение обёртки функции на java

для функции c или c++, которую нужно вызвать, в jni объявляют метод-прокси с модификатором `native`. модификатор сообщает компилятору, что тело метода задано вне java. нативного тела в исходнике java нет: после заголовка сразу стоит точка с запятой. по форме такие объявления совпадают с объявлениями абстрактных методов, но смысл другой. абстрактный метод реализует подкласс на java, нативный метод связывает загрузчик библиотеки с символом в машинном коде. модификатор `native` допустим и у метода экземпляра, и у статического метода. у нативного метода могут быть обычные модификаторы доступа.

в качестве наглядной функции c берётся библиотечная `printf` с одним аргументом. для неё в файле `HelloNative.java` объявляется обёртка:

```java


class HelloNative {  

    public static native int printf(String str);

}
```

класс `HelloNative` содержит один нативный метод. имя метода совпадает с именем функции `printf`, но это имя на стороне java. в библиотеке символ будет другим: jni кодирует имя по классу и пакету. в примере метод объявлен статическим. экземплярный нативный метод отличался бы первым служебным параметром на стороне c: вместо класса туда пришёл бы указатель на объект-приёмник.

заголовочный файл c получается компиляцией этого класса с флагом `-h`. после флага указывается каталог, куда класть заголовки. точка означает текущий каталог:

```bash
javac -h . HelloNative.java
```

`javac` одновременно компилирует `HelloNative.class` и записывает `HelloNative.h`. сгенерированный заголовок выглядит так:

```c


/* DO NOT EDIT THIS FILE - it is machine generated */

#include <jni.h>

/* Header for class HelloNative */



#ifndef _Included_HelloNative

#define _Included_HelloNative

#ifdef __cplusplus

extern "C" {

#endif

/*

 * Class:     HelloNative

 * Method:    printf

 * Signature: (Ljava/lang/String;)I

 */

JNIEXPORT jint JNICALL Java_HelloNative_printf

  (JNIEnv *, jclass, jstring);



#ifdef __cplusplus

}

#endif

#endif
```

в файле объявлена функция `Java_HelloNative_printf`. имя длиннее, чем `printf`. в jni имена экспортируемых функций заданы правилом, а не произвольным выбором. к имени добавляется префикс `Java`, затем пакет класса, затем имя класса и имя метода, разделённые подчёркиванием. если пакет вложенный, точка в его имени заменяется на подчёркивание: пакет `com.enoobis.test` в символе выглядит как `com_enoobis_test`. схема без пакета, как в примере: `Java_` + имя класса + `_` + имя метода. в java этот метод объявлен в классе `HelloNative` как `native int printf(String s)`. комментарий `Signature: (Ljava/lang/String;)I` задаёт дескриптор jvm: один аргумент типа `String`, результат `int`. по нему видно, что перегрузка на стороне java различается уже на уровне дескриптора.

если нативный метод перегружен, короткого имени недостаточно: к символу дописываются два подчёркивания и закодированная сигнатура аргументов. автогенерация заголовка делает это сама. такой файл можно написать и вручную, ошибка в одном символе обнаружится только при загрузке или при вызове, поэтому заголовок лучше получать из `javac -h`.

стражи `_Included_HelloNative` не дают включить заголовок дважды. блок `extern "C"` закрывает соглашение об именах c++, если тот же заголовок компилируется как c++: без него компилятор c++ исказил бы имя символа, и jvm его не нашла бы. подключаемый `jni.h` вводит типы `JNIEnv`, `jclass`, `jstring`, `jint` и макросы `JNIEXPORT`, `JNICALL`.

### определение кода на c

тело функции кладётся в отдельный файл `HelloNative.c`:

```c


#include "HelloNative.h"

#include <stdio.h>



JNIEXPORT jint JNICALL Java_HelloNative_printf (JNIEnv *env, jclass cl, jstring jstr) {



    const char *cstr = (*env)->GetStringUTFChars(env, jstr, NULL);

    int numchars = printf(cstr);

    (*env)->ReleaseStringUTFChars(env, jstr, cstr);

    return numchars;

}
```

что делает каждая строка:

- `#include "HelloNative.h"` подключает сгенерированный заголовок. без этого объявления определение функции не с чем сверить, и компилятор c не увидит прототип, по которому java ожидает символ
- `#include <stdio.h>` подключает стандартный заголовок c с прототипами ввода-вывода. оттуда берётся `printf`. кавычки и угловые скобки здесь различны: кавычки ищут файл относительно текущего исходника, угловые скобки ищут его в системных путях и в каталогах `-I`
- `JNIEXPORT jint JNICALL Java_HelloNative_printf` задаёт экспортируемую функцию. `JNIEXPORT` и `JNICALL` являются макросами из `jni.h` и платформенного `jni_md.h`. они делают символ видимым динамическому загрузчику и фиксируют соглашение о вызове, которого ждёт jvm. между макросами стоит тип результата `jint`. в java ему соответствует `int`. после макросов идёт имя `Java_HelloNative_printf` и тело
- `(JNIEnv *env, jclass cl, jstring jstr)` перечисляет параметры, которых в объявлении java нет, плюс явный аргумент метода. каждый нативный метод получает `env`, указатель на таблицу функций jni: через него вызывают `GetStringUTFChars`, создают объекты java, бросают исключения. `cl` для статического метода является дескриптором класса `HelloNative`. у нестатического метода на этом месте стоит дескриптор экземпляра, его тип `jobject`. `jstr` типа `jstring` содержит ту строку, которую код java передал в `printf`. тип `jstring` обозначает ссылку на объект `String` в куче jvm. указателем `char*` он не является
- тело начинается с извлечения байтов строки: `const char *cstr = (*env)->GetStringUTFChars(env, jstr, NULL);`. строки java хранят последовательность символов utf-16. функции c вроде `printf` ждут указатель на байты, завершённые нулём. `GetStringUTFChars` отдаёт такую последовательность в modified utf-8. для текста без нулевых символов внутри и без дополнительных плоскостей юникода эти байты совпадают с обычным utf-8. третий аргумент, `NULL`, означает, что вызывающему коду не нужно знать, сделала ли виртуальная машина копию или закрепила исходную строку. указатель `cstr` действителен только до парного освобождения
- `int numchars = printf(cstr);` вызывает стандартную `printf`. строка уходит на стандартный вывод. в `numchars` сохраняется число напечатанных символов. отрицательное значение `printf` оставляет как признак ошибки вывода, и это же число вернётся в java
- `(*env)->ReleaseStringUTFChars(env, jstr, cstr);` освобождает ресурсы, занятые предыдущим вызовом. шаг обязателен. если jni выдала копию, копию нужно отдать обратно. если строка была закреплена, закрепление нужно снять, иначе сборщик мусора не сможет её переместить или освободить. сборщик работает в отдельном потоке и может пересекаться с нативным методом, поэтому конец использования строки нельзя оставить подразумеваемым: его фиксирует `ReleaseStringUTFChars`. вызов стоит в паре с `GetStringUTFChars` на каждом пути, где указатель уже получен. указатель `cstr` после освобождения использовать нельзя
- `return numchars;` возвращает число напечатанных символов в код java. тип `jint` на границе становится типом `int` объявления `native`

вызовы через `(*env)->` записывают форму для c. в c++ те же операции выглядят как методы объекта `JNIEnv`, без явной передачи `env` первым аргументом. заголовок рассчитан на обе формы за счёт макросов `jni.h`. пример написан на c, поэтому используется форма с указателем на таблицу функций.

### компиляция библиотеки на c

есть заголовок и файл c. дальше нативный код собирается в динамически загружаемую библиотеку. конкретные флаги зависят от компилятора и от операционной системы. ниже два распространённых варианта: gcc на linux и visual c++ на windows.

при компиляторе gcc на linux команда такая:

```bash


gcc -fPIC -I $JAVA_HOME/include -I $JAVA_HOME/include/linux -shared -o libHelloNative.so HelloNative.c
```

переменная окружения `JAVA_HOME` должна указывать на каталог установки jdk. путь `$JAVA_HOME/include` ведёт к заголовкам, без которых библиотека c не соберётся. среди них `jni.h`, подключённый из `HelloNative.h`. второй каталог, `$JAVA_HOME/include/linux`, содержит платформенный `jni_md.h`: там раскрываются `jint`, `JNIEXPORT` и `JNICALL` для данной ос и архитектуры. флаг `-I` добавляет каталог в поиск заголовков, `-fPIC` порождает позиционно независимый код, без которого разделяемую библиотеку на linux обычно не собрать, `-shared` просит именно разделяемую библиотеку, а не исполняемый файл, `-o` задаёт имя результата.

если `JAVA_HOME` не задана и заводить её не требуется, в команду подставляют конкретный путь к заголовкам. при установке jdk в каталог `/usr/java/jdk-25` команда принимает вид:

```bash


gcc -fPIC -I /usr/java/jdk-25/include -I /usr/java/jdk-25/include/linux -shared -o libHelloNative.so HelloNative.c
```

после успешного выполнения в текущем каталоге появляется `libHelloNative.so`. имя библиотеки для java равно `HelloNative`, без префикса `lib` и без расширения `.so`. префикс и расширение добавляет уже соглашение linux, а `System.loadLibrary` принимает короткое имя.

если ос windows, а компилятор visual c++ от microsoft, команда другая:

```bash


cl -I %JAVA_HOME%\include -I %JAVA_HOME%\include\win32 -LD HelloNative.c -FeHelloNative.dll
```

`%JAVA_HOME%\include` и `%JAVA_HOME%\include\win32` играют ту же роль, что каталоги `include` и `include/linux` на linux: общие объявления jni и платформенный `jni_md.h`. флаг `-LD` собирает динамическую библиотеку, `-Fe` задаёт имя выходного файла. в текущем каталоге появляется `HelloNative.dll`. короткое имя библиотеки для `System.loadLibrary` снова `HelloNative`, уже без расширения `.dll`.

ошибка на этом шаге обычно означает, что компилятор не нашёл `jni.h` либо не совпала разрядность jdk и компилятора. заголовки должны принадлежать той же установке jdk, которой программу потом запустят.

### определение кода java

чтобы виртуальная машина подгрузила библиотеку, в программу добавляют вызов `System.loadLibrary`. аргумент задаёт короткое имя библиотеки, без префикса и без расширения. загрузку привязывают к инициализации класса статическим блоком: инициализация класса происходит до выполнения его кода, который может вызвать нативный метод, и повторно статический блок не выполняется.

в текущем каталоге файл `Program.java`:

```java


class Program {

  

    public static void main(String[] args) {

        

        HelloNative.printf("Hello enoobis.ru\n");    

    }



    static {  

        System.loadLibrary("HelloNative");

    }

}
```

статический блок записан в `Program`, а не в `HelloNative`. класс `Program` инициализируется перед входом в `main`, поэтому `loadLibrary` выполняется раньше `HelloNative.printf`. поиск файла идёт по `java.library.path` и по правилам ос: на linux к короткому имени добавляются `lib` и `.so`, на windows добавляется `.dll`. если файл не найден или в нём нет символа `Java_HelloNative_printf`, возникает `UnsatisfiedLinkError`. несовпадение сигнатуры, которое не поймал заголовок, проявляется той же ошибкой уже в момент вызова.

в каталоге проекта после всех шагов лежат:

- `HelloNative.java`: класс с нативным методом-обёрткой функции c
- `HelloNative.class`: скомпилированный класс
- `HelloNative.h`: заголовок, сгенерированный `javac -h`
- `HelloNative.c`: реализация функции из заголовка
- `libHelloNative.so` или `HelloNative.dll`: скомпилированная библиотека, в зависимости от ос
- `Program.java`: основной файл программы, загрузка библиотеки и вызов

### запуск программы

программа на java компилируется обычной командой:

```bash
javac Program.java
```

этой команде нативный доступ сам по себе не нужен: `javac` только проверяет объявление `native` и не открывает библиотеку. библиотека участвует на запуске.

запуск требует дополнительной опции виртуальной машины, которая разрешает нативный доступ. на актуальных jdk jni и ffm относятся к ограниченным операциям: без явного разрешения машина отказывается их выполнять или печатает предупреждение. если код лежит вне именованного модуля, в безымянном модуле, запуск выглядит так:

```bash
java --enable-native-access=ALL-UNNAMED ...
```

`ALL-UNNAMED` обозначает весь безымянный модуль, то есть классы, запущенные с classpath. классы именованного модуля в эту пометку не входят. многоточие в записи команды занимает место остальных аргументов, в рабочем запуске вместо него стоит имя главного класса.

в модульной программе перечисляют модули, которым нативный доступ разрешён. модуль, которого нет в списке, вызов нативного метода не получит:

```bash
java --enable-native-access=module1, module2 ...
```

на linux текущий каталог сам по себе в путь поиска библиотек не входит. его добавляют в `LD_LIBRARY_PATH`, чтобы динамический загрузчик ос увидел `libHelloNative.so`:

```bash
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
```

точка обозначает текущий каталог, прежнее значение переменной сохраняется после двоеточия. переменная принадлежит окружению процесса и читается загрузчиком ос. тот же каталог можно передать свойством java, которое читает уже `System.loadLibrary`:

```bash
java --enable-native-access=ALL-UNNAMED -Djava.library.path=. Program
```

`-Djava.library.path=.` задаёт путь поиска библиотек для этой виртуальной машины, не меняя окружение оболочки. `--enable-native-access=ALL-UNNAMED` по-прежнему разрешает нативный вызов. имя `Program` обозначает главный класс.

прогон на linux выглядит так:

```bash


eugene@Eugene:/workspace/java/test$ java --enable-native-access=ALL-UNNAMED -Djava.library.path=. Program

Hello enoobis.ru

eugene@Eugene:/workspace/java/test$
```

`printf` из библиотеки печатает `Hello enoobis.ru` и перевод строки. управление возвращается в `main`, и процесс завершается. число символов, которое вернула нативная функция, в этом `main` не используется: обёртка объявлена как `int`, но результат вызова отброшен. сам факт печати подтверждает, что символ найден, строка java преобразована в байты c и освобождение буфера в `HelloNative.c` отработало до возврата.
