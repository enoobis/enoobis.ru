java позволяет объявлять обобщенные типы и методы с параметрами типа, однако на уровне виртуальной машины отдельных обобщенных типов и методов нет: каждый объект принадлежит обычному классу. при компиляции параметры типа удаляются. параметр без границы заменяется на `Object`, параметр с границей заменяется на тип этой границы. процесс называется type erasure (стирание типов).

стирание выбрано при появлении обобщений в java 5 так, чтобы новый байткод оставался совместим с библиотеками, скомпилированными до обобщений. все инстанцирования одного обобщенного класса разделяют один класс времени выполнения, а сведения об аргументе типа в представление объекта не входят. нарушение этого инварианта в обход компилятора (так называемое загрязнение кучи, heap pollution) на jvm выглядит как обычная ссылка, и ошибка проявляется позже, в приведении, которое компилятор вставил при стирании.

пример обобщенного класса:

```java

class Person<T>{

    private T id;
    private String name;

    T getId(){ return id; }
    String getName() { return name; }

    Person(T id, String name){

        this.id = id;
        this.name = name;
    }
}
```

у параметра `T` границы нет, поэтому стирание подставляет `Object`. класс после стирания выглядит так:

```java

class Person{

    private Object id;
    private String name;

    Object getId(){ return id; }
    String getName() { return name; }

    Person(Object id, String name){

        this.id = id;
        this.name = name;
    }
}
```

поле `id`, результат `getId()` и первый параметр конструктора меняют тип с `T` на `Object`. поле `name` имеет конкретный тип `String`, и стирание его не меняет.

конкретный аргумент типа в исходной программе на результат стирания не влияет:

```java

Person tom = new Person<Integer>(456, "Tom");
Person bob = new Person<String>("qwert", "Bob");
```

для обоих объектов класс времени выполнения один и тот же, `Person`. параметр `T` в обоих случаях стерт до `Object`. значение `456` упаковано в `Integer` и хранится как `Object`, строка `"qwert"` хранится как `String`, то есть тоже как `Object`. различить `Person<Integer>` и `Person<String>` операцией `instanceof` или вызовом `getClass()` нельзя: аргумент типа в представлении jvm отсутствует, и оба выражения дают класс `Person`.

если результат метода или поле, тип которых задан параметром, присваивается внешней переменной, компилятор вставляет приведение к аргументу типа. фрагмент:

```java

var tom = new Person<Integer>(456, "Tom");
int tomId = tom.getId();
System.out.println(tomId);
```

в байткоде этот фрагмент соответствует схеме:

```java

var tom = new Person(456, "Tom");
int tomId = (int) tom.getId();
System.out.println(tomId);
```

`getId()` после стирания возвращает `Object`. компилятор вставляет приведение к аргументу типа, здесь к `Integer`. для примитивного `int` приведение идет к оболочке `Integer`, после чего значение распаковывается в `int`. проверку выполняет инструкция `checkcast` уже во время выполнения. запись `(int)` в листинге показывает место этой вставки в упрощенном виде: в исходном тексте после стирания привести `Object` сразу к `int` нельзя, распаковка следует за приведением к оболочке. если фактический объект не является `Integer`, `checkcast` завершается `ClassCastException`. при обычной компиляции обобщенного кода такая ситуация означает, что инвариант типа был нарушен раньше.

### параметры типа с ограничениями

следующий пример задает границу параметра.

```java

class Message{
 
    private String text; // текст сообщения
    String getText(){ return text; }
 
    Message(String text)
    {
        this.text = text;
    }
}

class Messenger<T extends Message> {
 
    private T message;
    T getMessage() { return this.message; }
 
    Messenger(T message) { this.message = message;  }
 
    void send() {
        System.out.println("Отправляется сообщение: " + message.getText());
    }
}
```

класс `Messenger` параметризован типом `T` с границей `Message`. внутри класса `T` стирается не до `Object`, а до границы `Message`:

```java

class Messenger {
 
    private Message message;
    Message getMessage() { return this.message; }
 
    Messenger(Message message) { this.message = message;  }
 
    void send() {
        System.out.println("Отправляется сообщение: " + message.getText());
    }
}
```

поле, результат `getMessage()` и параметр конструктора получают тип `Message`. вызов `message.getText()` после стирания остается вызовом метода `Message` и отдельного приведения не требует: граница уже совпадает с типом, у которого этот метод объявлен.

если границ несколько, параметр заменяется типом первой границы.

```java

class Messenger<T extends Message & Printable> {
 
    void sendMessage(T message){
 
        message.print();
    }
}
interface Printable{
 
    void print();
}
 
class Message{
 
    private String text; // текст сообщения
    String getText(){ return text; }
 
    Message(String text){

        this.text = text;
    }
}
```

в классе `Messenger` параметр `T` должен быть подтипом пересечения `Message` и `Printable`: класс аргумента наследует `Message` и реализует `Printable`. для виртуальной машины класс после стирания устроен так:

```java

class Messenger {
 
    void sendMessage(Message message){
 
        ((Printable)message).print();
    }
}
```

параметр `T` заменен первой границей, типом `Message`. вызов `print()` принадлежит второй границе, интерфейсу `Printable`, поэтому компилятор вставляет приведение аргумента к `Printable` и только затем вызывает `print()`. порядок границ в заголовке определяет и тип стирания, и то, какие вызовы получат приведение. поменять границы местами нельзя без смены класса стирания: первой должна стоять классовая граница, если она есть, потому что стирание обязано дать один класс или интерфейс, к которому приводится параметр в байткоде.
