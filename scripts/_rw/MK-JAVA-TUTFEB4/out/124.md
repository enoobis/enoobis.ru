кроме последовательных потоков stream api поддерживает параллельные потоки. распараллеливание потоков позволяет задействовать несколько ядер процессора, если целевая машина многоядерная, и тем самым может повысить производительность и ускорить вычисления. утверждение, что применение параллельных потоков на многоядерных машинах однозначно повысит производительность, из устройства конвейера не следует. в каждом конкретном случае надо проверять и тестировать: у разбиения и сборки есть собственная стоимость.

чтобы сделать обычный последовательный поток параллельным, надо вызвать у объекта `Stream` метод `parallel`. кроме того, можно использовать метод `parallelStream()` интерфейса `Collection` для создания параллельного потока из коллекции.

если рабочая машина не является многоядерной, поток будет выполняться как последовательный. параллельные потоки исполняются на общем пуле `ForkJoinPool.commonPool()`. его параллелизм равен `Runtime.availableProcessors() - 1`. при одном процессоре рабочих потоков у пула нет, и конвейер выполняется в вызывающем потоке.

применение параллельных потоков во многих случаях аналогично последовательному. произведение чисел:

```java


import java.util.Optional;

import java.util.stream.Stream;



public class Program {

 

    public static void main(String[] args) {

		

		Stream<Integer> numbersStream = Stream.of(1, 2, 3, 4, 5, 6);

		Optional<Integer> result = numbersStream.parallel().reduce((x,y)-> x*y);

		System.out.println(result.get()); // 720

	}

}
```

`parallel()` переводит поток в параллельный режим, `reduce` перемножает элементы. результат равен 720, как у последовательного произведения тех же чисел. это возможно, потому что умножение ассоциативно.

ещё один пример:

```java


import java.util.Arrays;

import java.util.List;





public class Program {



    public static void main(String[] args) {



        List<String> people = Arrays.asList("Tom","Bob", "Sam", "Kate", "Tim");



        System.out.println("Последовательный поток");

        people.stream().filter(p->p.length()==3).forEach(System.out::println);



        System.out.println("\nПараллельный поток");

        people.parallelStream().filter(p->p.length()==3).forEach(System.out::println);

    }

}
```

сначала для списка `people` создаётся поток, и над ним выполняется ряд операций в последовательном режиме. в частности, в списке находятся строки, длина которых равна 3, и они выводятся на консоль. все операции с потоком производятся над элементами списка в том порядке, в котором элементы идут в списке: `Tom`, `Bob`, `Sam`, `Kate`, `Tim`. длина 3 есть у `Tom`, `Bob`, `Sam` и `Tim`. у `Kate` длина 4, строка отсекается.

затем с помощью метода `people.parallelStream()` для списка создаётся параллельный поток. применяются те же операции, однако теперь порядок, в котором над элементами списка производятся операции, не детерминирован.

консольный вывод:

```consoletext


Последовательный поток

Tom

Bob

Sam

Tim



Параллельный поток

Sam

Tim

Bob

Tom
```

в случае с параллельным потоком вывод недетерминирован и может отличаться. повторный запуск может дать другую перестановку. `forEach` в параллельном режиме порядок встречи не сохраняет.

не все функции можно без ущерба для точности вычисления перенести с последовательных потоков на параллельные. прежде всего такие функции должны быть без сохранения состояния и ассоциативными, то есть при выполнении слева направо давать тот же результат, что и при выполнении справа налево, как в случае с произведением чисел.

```java


Stream<Integer> numbersStream = Stream.of(1, 2, 3, 4, 5, 6);

Integer result = numbersStream.parallel().reduce(1, (x,y)->x * y);

System.out.println(result);
```

фактически здесь происходит перемножение чисел от начального значения 1. при этом нет разницы между `1 * 2 * 3 * 4 * (5 * 6)` и `5 * 6 * 1 * (2 * 3) * 4`. скобки можно расставить любым образом, последовательность чисел можно разместить в любом порядке, и всё равно получится один и тот же результат. данная операция является ассоциативной и поэтому может быть распараллелена. вычитание ассоциативным не является: `(1 - 2) - 3` и `1 - (2 - 3)` дают разные числа, и параллельное `reduce` с вычитанием не обязано повторить последовательный результат.

кроме ассоциативности спецификация требует, чтобы операции не сохраняли состояние и не вмешивались в источник. лямбда, которая пишет во внешнюю переменную или меняет коллекцию, по которой идёт поток, делает результат неопределённым. стадии могут исполняться в другом порядке и на других потоках, а источник читает сплитератор.

### вопросы производительности в параллельных операциях

фактически применение параллельных потоков сводится к тому, что данные в потоке будут разделены на части, каждая часть обрабатывается на отдельном ядре процессора, и в конце эти части соединяются, и над ними выполняются финальные операции. на производительность в параллельных потоках влияют такие критерии:

- размер данных. чем больше данных, тем сложнее сначала разделять данные, а потом их соединять. на малом наборе эта стоимость легко перекрывает выигрыш от нескольких ядер. на большом наборе работа над элементами начинает преобладать.

- количество ядер процессора. теоретически, чем больше ядер в компьютере, тем быстрее программа будет работать. если на машине одно ядро, нет смысла применять параллельные потоки: дополнительного процессора, на который можно отдать часть, нет.

- чем проще структура данных, с которой работает поток, тем быстрее будут происходить операции. данные из `ArrayList` легко использовать, так как структура данной коллекции предполагает последовательность несвязанных данных и обращение по индексу. сплитератор делит такой список по диапазону индексов за постоянное время. коллекция типа `LinkedList` не лучший вариант, так как в последовательном списке все элементы связаны с предыдущими и последующими. чтобы отрезать часть, список надо пройти, и такое разбиение само по себе дорого.

- над данными примитивных типов операции будут производиться быстрее, чем над объектами классов. `IntStream`, `LongStream` и `DoubleStream` не упаковывают значение в `Integer`, `Long` и `Double` на каждом шаге.

### упорядоченность в параллельных потоках

как правило, элементы передаются в поток в том же порядке, в котором они определены в источнике данных. список этот порядок задаёт, `HashSet` не задаёт. при работе с параллельными потоками система сохраняет порядок следования элементов упорядоченного источника там, где операция этот порядок обещает. исключение составляет метод `forEach()`, который может выводить элементы в произвольном порядке. чтобы сохранить порядок следования, необходимо применять метод `forEachOrdered`:

```java


phones.parallelStream()

    .sorted()

    .forEachOrdered(s->System.out.println(s));
```

`sorted()` задаёт порядок элементов, `forEachOrdered` соблюдает этот порядок при печати.

сохранение порядка в параллельных потоках увеличивает издержки при выполнении: части приходится собирать обратно в исходной последовательности. если порядок не важен, его сохранение можно отключить и тем самым увеличить производительность, использовав метод `unordered`:

```java


phones.parallelStream()

    .sorted()

	.unordered()

    .forEach(s->System.out.println(s));
```

`unordered()` помечает поток как неупорядоченный. последующие операции получают право работать без сборки в прежнем порядке. `forEach` печатает элементы в том порядке, в каком они приходят из частей. вызов `sorted()` перед `unordered()` по-прежнему сортирует данные на своей стадии. снятое обязательство относится к тому, должен ли потребитель после `unordered()` уважать порядок этой сортировки.
