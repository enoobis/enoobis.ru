для управления доступом к общему ресурсу рядом с оператором `synchronized` используют блокировки. их функциональность собрана в пакете `java.util.concurrent.locks`.

сначала поток пытается получить доступ к общему ресурсу. если ресурс свободен, на него накладывается блокировка. после завершения работы блокировка снимается. если ресурс занят и блокировка уже наложена, поток ожидает, пока её не снимут.

классы блокировок реализуют интерфейс `Lock`. интерфейс определяет методы:

- `void lock()`: ожидает, пока не будет получена блокировка. прерывание это ожидание не прекращает

- `void lockInterruptibly() throws InterruptedException`: ожидает блокировку, если поток не прерван. прерывание выводит поток из ожидания

- `boolean tryLock()`: пытается получить блокировку без ожидания. если блокировка получена, возвращает `true`. если не получена, возвращает `false`. метод `lock()` в той же ситуации ждал бы освобождения

- `void unlock()`: снимает блокировку

- `Condition newCondition()`: возвращает объект `Condition`, связанный с текущей блокировкой

организация блокировки проста: для получения вызывается `lock()`, после окончания работы с общими ресурсами вызывается `unlock()`, и блокировка снимается.

объект `Condition` позволяет управлять ожиданием логического условия. поток, вставший на условие, атомарно отпускает связанный `Lock`: иначе поток, который должен изменить условие и послать сигнал, сам не вошёл бы в секцию.

как правило для работы с блокировками используется класс `ReentrantLock` из пакета `java.util.concurrent.locks`. класс реализует интерфейс `Lock`. реентерабельность означает повторный захват владельцем: счётчик захватов растёт на каждом `lock()` этого потока и уменьшается на `unlock()`. другой поток входит, когда счётчик доходит до нуля.

для примера взят код из темы про оператор `synchronized` и переписан с использованием `ReentrantLock`:

```java


import java.util.concurrent.locks.ReentrantLock;



public class Program {

 

    public static void main(String[] args) {

         

        CommonResource commonResource= new CommonResource();

        ReentrantLock locker = new ReentrantLock(); // создаем заглушку

        for (int i = 1; i < 6; i++){

             

            new Thread(new CountThread(commonResource, locker), "Thread "+ i).start();

        }

    }

}

 

class CommonResource{

     

    int x=0;

}

 

class CountThread implements Runnable{

 

    CommonResource res;

    ReentrantLock locker;

    CountThread(CommonResource res, ReentrantLock lock){

        this.res=res;

        locker = lock;

    }

    public void run(){

        

		locker.lock(); // устанавливаем блокировку

        try{

            res.x=1;

            for (int i = 1; i < 5; i++){

                System.out.printf("%s %d \n", Thread.currentThread().getName(), res.x);

                res.x++;

                Thread.sleep(100);

            }

        }

        catch(InterruptedException e){

            System.out.println(e.getMessage());

        }

        finally{

            locker.unlock(); // снимаем блокировку

        }

    }

}
```

здесь также используется общий ресурс `CommonResource`, для управления которым создаётся пять потоков. блокировка одна на всех, она создаётся в `main` и передаётся в `CountThread`. в исходном разборе этот объект назван заглушкой. на входе в критическую секцию поток устанавливает её вызовом:

```java
locker.lock();
```

после этого только один поток имеет доступ к критической секции, которую образует блок `try`. остальные потоки ожидают снятия блокировки внутри своего `lock()`. в секции поле обнуляется в единицу, печатается и увеличивается, между шагами стоит `Thread.sleep(100)`. в блоке `finally`, после окончания основной работы потока, блокировка снимается:

```java


finally{

    locker.unlock(); // снимаем блокировку

}
```

снятие делается обязательно в `finally`. при возникновении ошибки иначе все остальные потоки окажутся заблокированными навсегда: владелец уже не дойдёт до `unlock()`. сам `lock()` стоит до `try`. если захват не состоялся, `finally` не выполняется. `unlock()` без владения бросает `IllegalMonitorStateException`.

консольный вывод аналогичен синхронизированному варианту. порядок имён потоков выбирает планировщик, числа одного потока идут от 1 до 4 подряд:

```bash


Thread 4 1 

Thread 4 2 

Thread 4 3 

Thread 4 4 

Thread 3 1 

Thread 3 2 

Thread 3 3 

Thread 3 4 

Thread 2 1 

Thread 2 2 

Thread 2 3 

Thread 2 4 

Thread 1 1 

Thread 1 2 

Thread 1 3 

Thread 1 4 

Thread 5 1 

Thread 5 2 

Thread 5 3 

Thread 5 4
```

поток держит `locker` на всё время цикла, включая паузу, поэтому инкременты разных потоков не перемешиваются.
