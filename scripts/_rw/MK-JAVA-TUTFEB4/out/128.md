нередко программа состоит не из одного модуля, а из нескольких, и при их связывании действуют отдельные правила.

### экспорт

для своей работы модулю могут понадобиться пакеты другого модуля. пакеты, объявленные внутри модуля, сами по себе другим модулям не доступны. модуль перечисляет открытые пакеты директивой `exports`. в объявлении `java.base`, модуля с базовой функциональностью платформы, в репозитории openjdk на [github](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/module-info.java) видны такие строки:
```java

module java.base {

    exports java.io;
    exports java.lang;
    exports java.lang.annotation;
    exports java.lang.classfile;
...................................
    exports java.util;
.........................
```
модуль `java.base` открывает пакеты `java.io`, `java.util` и `java.lang`. при экспорте пакета за границей модуля видны его открытые и защищённые типы, с модификаторами `public` и `protected`, и такие же члены этих типов. `protected` сохраняет обычное правило языка: член доступен из подкласса. произвольный код читающего модуля к такому члену не допускается. пакеты, которые директива `exports` не назвала, снаружи скрыты. и компилятор, и виртуальная машина отвергают обращение к ним из другого модуля.

#### квалифицированный экспорт

помимо обычного `exports` в дескрипторе `java.base` есть строки такого вида:
```java

exports jdk.internal.javac to
    java.compiler,
    jdk.compiler;
```
конструкция `exports ... to` задаёт квалифицированный экспорт (qualified export). доступ к пакету получают только перечисленные модули, здесь `java.compiler` и `jdk.compiler`. остальные модули этот пакет не читают, даже если зависят от `java.base`. так платформа отдаёт внутренний пакет только тем модулям jdk, которым он нужен для реализации, и не включает его в контракт прикладного кода.

### импорт модуля

модуль подключается директивой `import`, в той же роли, в какой импортируют пакет или отдельный тип:
```java
import module java.base;
```
директива равносильна импорту всех экспортируемых пакетов модуля `java.base`. пример:
```java

import module java.base;

class Program {
    
    static void main(String[] args) {

        List<String> people = new ArrayList<String>();
        people.add("Tom");
        people.add("Bob");
        people.add("Sam");
        System.out.println(people);     // [Tom, Bob, Sam]
    }
}
```
типы `List` и `ArrayList` по отдельности не импортируются, пакет `java.util` в файле тоже не назван. импорт модуля открывает экспортируемые типы, а эти классы лежат в пакете `java.util` данного модуля.

до java 25 оболочка jshell подключала фиксированный набор пакетов. с java 25 она импортирует модуль `java.base`, и функциональность этого модуля доступна в оболочке без дополнительного импорта. в компактных программах, которые запускаются одним исходным файлом, модуль `java.base` импортируется автоматически.

когда импортируется несколько модулей, растёт вероятность конфликта имён: одноимённые типы могут прийти из разных модулей или из разных пакетов одного модуля. в такой ситуации однозначнее обычный импорт пакета или отдельного типа.

### пример взаимодействия модулей

проект имеет такую структуру:

![взаимодействие модулей в java](/uploads/course-lectures/724cda24c966eb21d3559fd3f2b17ae51cfd0d0c.png)

здесь два модуля, `demo` и `operations`. каждый лежит в своём одноимённом каталоге.

в каталоге `operations/com/enoobis/factorial` находится файл `Factorial.java`:
```java

package com.enoobis.factorial;

public class Factorial{
	
	public static int calculate(int n){
		if (n < 1) return -1;
        int result = 1;
        while (n > 1) result *= n--;
        return result;
	}
}
```
класс `Factorial` вычисляет факториал и принадлежит пакету `com.enoobis.factorial`. при `n < 1` метод возвращает `-1`, иначе накапливает произведение от `n` вниз до `2`.

чтобы класс был доступен другим модулям, пакет нужно экспортировать. по умолчанию все пакеты модуля снаружи невидимы. экспорт задаётся директивой `exports` в дескрипторе модуля.

в каталоге `operations` лежит файл `module-info.java`:
```java

module operations {
    exports com.enoobis.factorial;
}
```
дескриптор задаёт модулю имя `operations`. директива `exports` экспортирует пакет `com.enoobis.factorial`. после этого другие модули, которые читают `operations`, могут обращаться к классу `Factorial`.

модуль `demo` описывается своим файлом `module-info.java`:
```java

module demo {
    requires operations;
}
```
директива `requires` объявляет, что модуль `demo` зависит от модуля `operations` и читает его экспортированные пакеты. одной директивы `exports` в `operations` недостаточно: без `requires` модуль `demo` этот пакет не читает. нужны обе стороны отношения.

в каталоге `demo/com/enoobis/hello/` создаётся файл `Hello.java`:
```java

package com.enoobis.hello;

import com.enoobis.factorial.Factorial;

public class Hello{
	
	public static void main(String[] args){
		
		int a = 5;
		int b = Factorial.calculate(a);
		System.out.printf("Factorial of %d is equal to %d \n", a, b);
	}
}
```
класс `Factorial` импортируется из пакета `com.enoobis.factorial`, и для числа `5` вычисляется факториал.

в консоли выполняется переход в корневой каталог, где лежат оба модуля, и первым компилируется модуль `operations`:
```bash

javac -d appmodules/operations operations/module-info.java operations/com/enoobis/factorial/Factorial.java
```
параметр `-d` задаёт каталог скомпилированного модуля: `appmodules/operations`. если каталога ещё нет, он создаётся. в этот каталог попадают и `module-info.class`, и классы пакетов: на выходе модуль является каталогом с классами.

вторым компилируется модуль `demo`, он использует первый:
```bash

javac -p appmodules -d appmodules/demo demo/module-info.java demo/com/enoobis/hello/Hello.java
```
параметр `-p` является сокращением `--module-path` и указывает, где искать требуемые модули. здесь это каталог `appmodules`, в который уже помещён скомпилированный модуль `operations`. без этого пути компилятор не разрешит директиву `requires operations`.

параметр `-d`, как и в предыдущей команде, задаёт выходной каталог скомпилированного модуля, каталог `appmodules/demo`.

когда оба модуля скомпилированы, запускается модуль `demo`:
```bash

java -p appmodules -m demo/com.enoobis.hello.Hello
```
в команде запуска параметр `-p` снова указывает каталог, где лежат оба скомпилированных модуля, а `-m` выбирает главный класс в форме `demo/com.enoobis.hello.Hello`. на консоль выводится факториал числа:
```bash

eugene@Eugene:/java$ javac -d appmodules/operations operations/module-info.java operations/com/enoobis/factorial/Factorial.java
eugene@Eugene:/java$ javac -p appmodules -d appmodules/demo demo/module-info.java demo/com/enoobis/hello/Hello.java
eugene@Eugene:/java$ java -p appmodules -m demo/com.enoobis.hello.Hello
Factorial of 5 is equal to 120 
eugene@Eugene:/java$
```
