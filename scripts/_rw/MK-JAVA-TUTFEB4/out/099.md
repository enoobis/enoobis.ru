при обращении нескольких потоков к одному ресурсу, который существует вне потока, результат зависит от чередования их шагов планировщиком. таким ресурсом бывает поле объекта или файл. одновременные обращения делают итог невыводимым из одного только текста программы. фрагмент ниже запускает пять потоков на общем счётчике.

```java


public class Program {



    public static void main(String[] args) {

        

        CommonResource commonResource= new CommonResource();



        for (int i = 1; i < 6; i++){

            

            new Thread(new CountThread(commonResource), "Thread "+ i).start();

        }

    }

}



class CommonResource{

    

    int x = 0;

}



class CountThread implements Runnable{



    CommonResource res;



    CountThread(CommonResource res){

        this.res = res;

    }



    public void run(){

		res.x = 1;



        for (int i = 1; i < 5; i++){



			System.out.printf("%s %d \n", Thread.currentThread().getName(), res.x);

			res.x++;



            try{

				Thread.sleep(100);

            }

            catch(InterruptedException _){}

        }

    }

}
```

класс `CommonResource` задаёт общий ресурс: одно целочисленное поле `x`. класс `CountThread` реализует `Runnable`, хранит ссылку на этот ресурс и в цикле увеличивает `x` на единицу. перед циклом поток записывает в поле единицу:

```java
res.x=1;
```

цикл записан как `for (int i = 1; i < 5; i++)`: четыре итерации, на каждой печатается текущее `x`, затем выполняется инкремент. изолированный поток напечатал бы 1, 2, 3, 4. в исходном разборе ожидаемым как раз называют это значение 4, последнюю напечатанную величину. к выходу из цикла само поле уже равно 5, потому что печать стоит до инкремента.

в `main` создаётся один экземпляр `CommonResource` и пять потоков с именами от `Thread 1` до `Thread 5`. если бы потоки не мешали друг другу, каждый прошёл бы последовательность от 1 до 4. наблюдаемый вывод другой:

```bash


Thread 1 1 

Thread 2 1 

Thread 3 1 

Thread 5 1 

Thread 4 1 

Thread 5 6 

Thread 2 6 

Thread 1 6 

Thread 3 6 

Thread 4 6 

Thread 4 11 

Thread 2 11 

Thread 5 11 

Thread 3 11 

Thread 1 11 

Thread 4 16 

Thread 1 16 

Thread 3 16 

Thread 5 16 

Thread 2 16
```

пока один поток не закончил работу с полем `res.x`, то же поле читает и пишет другой. конкуренцию двух и более потоков за один ресурс называют состоянием гонки (race condition). операция `res.x++` состоит из чтения, сложения и записи. между этими шагами планировщик может переключить поток, и второй прочитает то же число, которое первый ещё не записал обратно. если несколько потоков так меняют баланс счёта, гонка нарушает целостность данных.

секции, которые нельзя выполнять одновременно, синхронизируют. механизм языка для этого: ключевое слово `synchronized`. им помечают блок или метод.

## synchronized-блоки

синхронизированный блок: участок кода, войти в который в один момент времени может только один поток. форма записи:

```java


synchronized (obj)

{

    // критическая секция

}
```

после `synchronized` в скобках стоит объект-заглушка: `synchronized(obj)`. монитор есть у объекта некоторого класса и отсутствует у значения примитивного типа, поэтому в скобки ставят ссылку, а не примитив. в фигурных скобках лежит критическая секция.

с каждым объектом в java связан монитор, внутренний замок этого объекта. он и есть средство управления доступом. когда выполнение доходит до `synchronized`, поток захватывает монитор. на время захвата тело блока выполняет только он. монитор реентерабелен: повторный вход того же потока не ставит его в ожидание самого себя. при выходе из блока монитор освобождается, в том числе если выход произошёл из-за исключения. освобождённый монитор захватывает один из ожидающих, остальные продолжают ждать. кто войдёт следующим, взаимное исключение не фиксирует.

тот же пример, где критическая секция закрыта монитором общего ресурса:

```java


public class Program {

 

    public static void main(String[] args) {

         

        CommonResource commonResource= new CommonResource();

        for (int i = 1; i < 6; i++){

             

            new Thread(new CountThread(commonResource), "Thread "+ i).start();

        }

    }

}

 

class CommonResource{

     

    int x=0;

}

 

class CountThread implements Runnable{

 

    CommonResource res;



    CountThread(CommonResource res){ this.res = res; }



    public void run(){



        synchronized(res){  // определяем синхронизированный блок



            // до конца блок идет критическая секция

            res.x = 1;



            for (int i = 1; i < 5; i++){

                System.out.printf("%s %d \n", Thread.currentThread().getName(), res.x);



                res.x++;



                try{

                    Thread.sleep(100);

                }

                catch(InterruptedException _){}

            }

        }

    }

}
```

одномоментный доступ нужен участку, который меняет общий ресурс `res`. этот участок оформляют синхронизированным блоком:

```java


synchronized(res){  // определяем синхронизированный блок



    res.x = 1;



    for (int i = 1; i < 5; i++){

        System.out.printf("%s %d \n", Thread.currentThread().getName(), res.x);



        res.x++;



        try{

            Thread.sleep(100);

        }

        catch(InterruptedException _){}

        }

    }

}
```

поток, первым дошедший до блока, захватывает `res` и выполняет секцию до конца. вызов `Thread.sleep(100)` монитор не отпускает, пауза тоже идёт при исключительном владении, и остальные потоки всё это время стоят на входе в `synchronized`. когда первый поток выходит из блока, `res` освобождается и достаётся любому из ожидавших. остальные снова ждут. так секция проходит у всех пяти потоков. печать становится упорядоченной: поток целиком выводит 1, 2, 3, 4, и только потом ресурс отдают следующему.

пустой обработчик `InterruptedException` с именем `_` отбрасывает прерывание. само исключение снимает статус прерывания потока, и учебный пример на это никак не отвечает.

```bash


Thread 1 1 

Thread 1 2

Thread 1 3

Thread 1 4

Thread 3 1 

Thread 3 2

Thread 3 3

Thread 3 4

Thread 5 1 

Thread 5 2

Thread 5 3

Thread 5 4

Thread 4 1 

Thread 4 2

Thread 4 3

Thread 4 4

Thread 2 1 

Thread 2 2

Thread 2 3

Thread 2 4
```

## синхронизированные методы

`synchronized` у метода задаёт ту же монополию, что и у блока: в один момент времени метод выполняет поток, захвативший монитор. у метода экземпляра монитором служит получатель вызова, `this`. в программе ниже синхронизирована операция над общим ресурсом.

```java


public class Program {

 

    public static void main(String[] args) {

         

        CommonResource commonResource= new CommonResource();

        for (int i = 1; i < 6; i++){

             

            new Thread(new CountThread(commonResource), "Thread "+ i).start();

        }

    }

}

 

class CommonResource{

     

    int x;

    synchronized void increment(){  // синхронизированный метод



        x = 1;

        for (int i = 1; i < 5; i++){

            System.out.printf("%s %d \n", Thread.currentThread().getName(), x);

            x++;

            try{

                Thread.sleep(100);

            }

            catch(InterruptedException _){}

        }

    }

}

 

class CountThread implements Runnable{

 

    CommonResource res;

    CountThread(CommonResource res){



        this.res = res;

    }

     

    public void run(){

        res.increment();

    }

}
```

результат совпадает с вариантом на блоке `synchronized`. в работу входит монитор объекта `CommonResource`, общего для всех потоков. синхронизированным объявлен метод `increment()` класса `CommonResource`. метод `run()` класса `CountThread` оставлен без `synchronized`, потому что отдельный объект каждого потока не защитил бы общее поле `x`. первый поток, вошедший в `increment()`, захватывает монитор `CommonResource` и держит его до возврата из метода, вместе с паузой `sleep`. остальные вызовы `increment()` на том же экземпляре ждут освобождения. у статического метода монитором был бы объект `Class`. здесь метод экземплярный, поэтому закрывается именно общий ресурс.
