вызов кода c из программы java через **jni** работает и в последних версиях java. путь при этом длинный: отдельный заголовок, файл на c, сборка разделяемой библиотеки и загрузка её по короткому имени. в последних версиях платформы для доступа к внешним функциям и к памяти вне кучи добавлен **foreign functions and memory api** (**ffm**). раньше эта работа шла под именем project panama. с java 14 api был экспериментальным, в java 22 он вышел из preview и стал постоянной частью платформы. предполагается, что со временем ffm займёт место jni в новом коде: объявление `native` и ручная сборка библиотеки-обёртки для уже загруженной функции c больше не обязательны.

для примера снова берётся библиотечная функция `printf` из стандартной библиотеки c. отдельный файл на c не пишется. вся программа находится в `Program.java`:

```java


import java.lang.invoke.*;

import java.lang.foreign.*;



public class Program {



    public static void main(String[] args) throws Throwable {



        Linker linker = Linker.nativeLinker();

        MethodHandle printf = linker.downcallHandle(

            linker.defaultLookup().findOrThrow("printf"),  // получаем функцию printf

            FunctionDescriptor.of(ValueLayout.JAVA_INT, ValueLayout.ADDRESS));



        try (Arena arena = Arena.ofConfined()) {

            MemorySegment str = arena.allocateFrom("Hello enoobis.ru\n");

            int result = (int) printf.invoke(str);  // получаем результат из нативной функции

            System.out.printf("Напечатано символов %d\n", result);

        }

    }

}
```

разбор идёт по порядку выполнения `main`. сначала создаётся **линкер**, связка с нативными функциями текущей машины:

```java


Linker linker = Linker.nativeLinker();
```

`Linker.nativeLinker()` возвращает линкер для abi той операционной системы и той архитектуры, на которой запущена виртуальная машина. abi фиксирует соглашение о вызове и раскладку типов c: в каких регистрах лежит указатель, как выравнивается `int`, кто снимает аргументы со стека. один и тот же исходник java за счёт этого вызывает `printf` и на linux, и на windows, а конкретная раскладка выбирается в момент запуска, не во время компиляции `Program`.

дальше строится дескриптор вызываемой функции, объект `MethodHandle`:

```java


MethodHandle printf = linker.downcallHandle(...)
```

`MethodHandle` здесь задаёт типизированную точку вызова нативной функции. java вызывает её как метод, без объявления `native` и без сгенерированного заголовка. имя `downcallHandle` фиксирует направление: вызов идёт из java вниз, в машинный код. обратное направление, когда нативный код вызывает метод java, устроено отдельно и этим методом не задаётся.

`linker.downcallHandle` в примере получает два аргумента:

- дескриптор внешней функции, то есть адрес символа. адрес ищется цепочкой вызовов. `linker.defaultLookup()` смотрит символы стандартных библиотек c, которые загрузчик уже отобразил в процесс. произвольная разделяемая библиотека в этот поиск не входит: для неё есть отдельный lookup по имени файла. `findOrThrow("printf")` запрашивает символ с именем `printf` и бросает исключение, если его нет. короткое имя здесь имя символа c, а не схема `Java_класс_метод`, как в jni

```java
linker.defaultLookup().findOrThrow("printf")
```

- описание сигнатуры. его передают вторым аргументом, чтобы линкер знал, что положить в регистры и что считать результатом. в примере `printf` описана как функция с результатом `int` и одним аргументом-указателем. `ValueLayout.JAVA_INT` соответствует результату `int`, `ValueLayout.ADDRESS` соответствует указателю, на стороне c это `char*`. носитель адреса на стороне java: `MemorySegment`. объект `String` в этот аргумент не кладут

```java


FunctionDescriptor.of(ValueLayout.JAVA_INT, ValueLayout.ADDRESS)
```

у `printf` после форматной строки в языке c идут вариативные аргументы. для вызова с такими аргументами у `downcallHandle` есть опция `Linker.Option.firstVariadicArg`: она помечает, с какого индекса аргументы вариативны, потому что abi часто передаёт их иначе, чем фиксированные. в этом примере дополнительных аргументов нет, в функцию уходит только адрес строки, и дескриптор ограничивается одним `ADDRESS`.

следующий шаг выделяет память под строку, которую функция получит аргументом:

```java


try (Arena arena = Arena.ofConfined()) {

       MemorySegment str = arena.allocateFrom("Hello enoobis.ru\n");
```

нативная функция не принимает объекты java. `String` лежит в куче, сборщик мусора вправе переместить его, и стабильного адреса у объекта нет. байты для c размещают в памяти вне кучи, которую виртуальная машина не перемещает:

- `Arena.ofConfined()` создаёт ограниченную арену. сегменты, выделенные в ней, принадлежат потоку, который арену создал. закрытие блока `try` закрывает арену, потому что `Arena` реализует `AutoCloseable`, и память отдаётся обратно. явного `free` в тексте нет, утечка при выходе из блока не возникает даже если `invoke` бросит исключение
- `arena.allocateFrom("...")` выделяет сегмент, копирует в него байты строки java в кодировке utf-8 и дописывает нулевой байт `\0`, чтобы последовательность была строкой c. результат имеет тип `MemorySegment` и является безопасной ссылкой на этот сегмент: адрес, длина и привязка к арене. исходный объект `String` при этом не закрепляется, в нативную память уходит копия

сам вызов и чтение результата:

```java


int result = (int) printf.invoke(str);
```

`printf.invoke(str)` выполняет нативную функцию и передаёт ей адрес сегмента. `invoke` объявлен с результатом `Object`, фактический носитель `JAVA_INT` является упакованным `int`, приведение достаёт значение. это число символов, которое вернула `printf`, та же величина, что в jni лежала в `numchars`.

сводный порядок работы программы:

- поиск. `defaultLookup` находит `printf` среди символов стандартных библиотек, уже загруженных в процесс
- выделение памяти. арена резервирует блок вне кучи java и кладёт туда байты строки вместе с завершающим нулём
- выполнение. `invoke` вызывает нативную функцию и передаёт адрес этого блока как единственный аргумент
- освобождение. по выходе из `try` арена закрывается, и память строки освобождается сразу, не дожидаясь сборки мусора

как и для jni, запуск передаёт виртуальной машине разрешение на нативный доступ. без модулей программа запускается так:

```bash
java --enable-native-access=ALL-UNNAMED ...
```

в модульной программе перечисляют все модули, для которых нативный доступ разрешён:

```bash
java --enable-native-access=module1, module2 ...
```

`ALL-UNNAMED` покрывает безымянный модуль. именованный модуль без этой опции до `downcallHandle` не допускается: ограниченной операцией здесь является и поиск символа, и сам вызов. отдельная библиотека и `LD_LIBRARY_PATH` в этом примере не нужны, символ `printf` уже есть в стандартной библиотеке c.

прогон:

```bash


eugene@Eugene:/workspace/java/test$ javac Program.java

eugene@Eugene:/workspace/java/test$ java --enable-native-access=ALL-UNNAMED Program

Hello enoobis.ru

Напечатано символов 18

eugene@Eugene:/workspace/java/test$
```

сначала `javac` компилирует `Program.java`. затем `java` с разрешением нативного доступа выполняет `main`. нативная `printf` печатает `Hello enoobis.ru` и перевод строки. следующая строка уже от `System.out.printf`: в неё подставлено значение `result`. число 18 складывается из 17 байт текста `Hello enoobis.ru` и перевода строки. нулевой терминатор в это число не входит: `printf` его не печатает, он только завершает строку c в сегменте.
