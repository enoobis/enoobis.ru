### класс throwable

базовый класс всех исключений в java называется `Throwable`. чтобы в одном блоке `catch` принять любое исключение и любую ошибку, в качестве типа указывают его. более узкие обработчики ставят на подтипы, если реакция зависит от вида сбоя.

у класса есть несколько базовых методов. основные:

- `String getMessage()`: возвращает строку подробного сообщения об исключении, ту, что была передана при создании объекта

- `StackTraceElement[] getStackTrace()`: возвращает снимок трассировки стека, тот же набор кадров, который печатает `printStackTrace()`

- `void printStackTrace()`: выводит трассировку стека в стандартный поток ошибок, то есть в `System.err`

эти методы читают информацию об исключении уже после перехвата:

```java


class Program{

     

	public static void main(String[] args) {

         

        try{

            // для эмуляции ошибки делим число на 0

            System.out.println(5 / 0);

        }

        catch(Throwable ex){



            // выводим сообщение об ошибке

            System.out.println("Error: " + ex.getMessage());

            // выводим трасировку стека

            ex.printStackTrace();

        }

    }

}
```

исключение в блоке `try` порождается делением числа на 0. в `catch` объявлена переменная `ex` типа `Throwable`. на консоль отдельно выводятся сообщение об ошибке и трассировка стека. трассировка сама содержит это сообщение, поэтому текст `/ by zero` появляется дважды. консольный вывод:

```bash


Error: / by zero

java.lang.ArithmeticException: / by zero

	at Program.main(Program.java:7)
```

трассировка показывает фактический динамический тип и место возникновения. в выводе исключение имеет тип `java.lang.ArithmeticException`, то есть тип исключений арифметических операций, хотя перехват записан по супертипу `Throwable`. сама ошибка возникла на строке 7 файла `Program.java` в методе `Program.main`. кадр `at Program.main(Program.java:7)` связывает исключение с конкретной инструкцией исходного текста.

### классификация ошибок

от `Throwable` наследуются два класса: `Error` и `Exception`. все остальные типы исключений являются производными от этих двух. третьей ветви у корня нет.

класс `Error` описывает внутренние ошибки исполняющей среды java: нехватку памяти, сбой в самой виртуальной машине, несовместимость байткода. у программы почти нет осмысленной реакции на такую ошибку, кроме как сообщить пользователю и попытаться завершиться аккуратно. встречаются эти ситуации редко, и ловить `Error` в прикладном `catch` обычно не стремятся: состояние среды уже может быть непригодно для продолжения.

собственно исключения наследуют класс `Exception`. среди них выделяется `RuntimeException`. классы, унаследованные от `Error` и от `RuntimeException`, называются **непроверяемыми исключениями** (unchecked exceptions). компилятор не требует, чтобы такой тип был перехвачен или объявлен в `throws`. непроверяемое исключение часто оказывается следствием ошибки в коде: неверное приведение типа, выход за границу массива, разыменование пустой ссылки.

некоторые классы непроверяемых исключений:

- `ArithmeticException`: целочисленное деление на ноль и другие недопустимые арифметические операции над целыми

- `IndexOutOfBoundsException`: индекс вне допустимого диапазона. у массива это уточняется подклассом `ArrayIndexOutOfBoundsException`, у строки подклассом `StringIndexOutOfBoundsException`

- `IllegalArgumentException`: в метод передан аргумент, который контракт метода запрещает

- `NullPointerException`: операция над пустой ссылкой, у которой нужен объект

- `NumberFormatException`: строка не разбирается в число. этот класс является подклассом `IllegalArgumentException`, поэтому тоже непроверяемый

все остальные классы, производные от `Exception` и при этом не производные от `RuntimeException`, называются проверяемыми исключениями (checked exceptions). компилятор требует обработать их в `try..catch` или перечислить в секции `throws` метода. проверяемость задана статически, по положению класса в иерархии, а не по тексту сообщения.

некоторые классы проверяемых исключений:

- `CloneNotSupportedException`: у объекта вызван `clone()`, а его класс не реализует интерфейс `Cloneable`

- `InterruptedException`: поток ожидания прерван другим потоком через `interrupt()`. проверяемость здесь заставляет вызывающий код явно решить, восстанавливать ли флаг прерывания и как завершать ожидание

- `ClassNotFoundException`: загрузчик классов не нашёл класс по имени, обычно при рефлексивной загрузке

вместо общего типа `Throwable` перехватывают конкретный тип. при делении на 0 порождается `ArithmeticException`. обработчик этого типа:

```java


class Program{

     

	public static void main(String[] args) {

         

        try{

            // для эмуляции ошибки делим число на 0

            System.out.println(5 / 0);

        }

        catch(ArithmeticException ex){



            // выводим сообщение об ошибке

            System.out.println("Error: " + e.getMessage());

            // выводим трасировку стека

            e.printStackTrace();

        }

    }

}
```

во фрагменте параметр объявлен как `ex`, а в теле используется имя `e`. в таком виде текст не компилируется: имени `e` в области видимости нет. вызовы относятся к пойманному объекту, то есть по смыслу это `ex.getMessage()` и `ex.printStackTrace()`.

### обработка нескольких исключений

на одном участке кода возникают исключения разных типов. обработчик `Throwable` или `Exception` покрывает их все одной ветвью. если реакция должна зависеть от типа, для каждого типа добавляют свой блок `catch`:

```java


class Program{

     

	public static void main(String[] args) {

         

        printNumber(0);     // По индексу 0 число 1

        printNumber(10);    // Выход за пределы массива

        printNumber(3);     // Ошибка преобразования из строки в число

    }



    static void printNumber(int index){



        String[] data = {"1", "a", "2", "b", "3", "c"};



        try{

            // пытаемся преобразовать значение массива по индексу в число

            int result =Integer.parseInt(data[index]);

            System.out.printf("По индексу %d число %d\n", index, result);

        }

        catch(ArrayIndexOutOfBoundsException _){

                    

            System.out.println("Выход за пределы массива");

        }

        catch(NumberFormatException _){

                    

            System.out.println("Ошибка преобразования из строки в число");

        }

    }

}
```

основные действия собраны в методе `printNumber()`. метод получает индекс и пытается разобрать элемент массива `data` по этому индексу как целое число. развитие ситуации идёт по одному из трёх путей:

- по переданному индексу в массиве лежит число, записанное строкой. `Integer.parseInt` завершается успешно, и метод печатает индекс и значение. для индекса 0 это строка `"1"` и число 1

- переданный индекс лежит вне допустимого диапазона `0 .. data.length - 1`. обращение `data[index]` порождает `ArrayIndexOutOfBoundsException`. для вызова с индексом 10 массив из шести элементов этого индекса не содержит

- индекс действителен, но строка по нему не является записью числа. `Integer.parseInt` порождает `NumberFormatException`. для индекса 3 в массиве стоит `"b"`

последние два пути перехватываются двумя блоками `catch`:

```java


catch(ArrayIndexOutOfBoundsException _){

                    

    System.out.println("Выход за пределы массива");

}

catch(NumberFormatException _){

                    

    System.out.println("Ошибка преобразования из строки в число");

}
```

исключение попадает в тот блок `catch`, с типом которого оно совместимо, и дальнейшие блоки этой конструкции уже не проверяются. первый подходящий обработчик и есть выбранный. поэтому два разных сообщения, «выход за пределы массива» и «ошибка преобразования из строки в число», не смешиваются.

так обработка разных типов разводится по разным ветвям. заводить отдельный `catch` на каждый тип стандартной библиотеки при этом не требуется. для типов со специальной реакцией пишут свои блоки, а для всех остальных один блок более общего типа, `Throwable` или `Exception`. с java 7 несколько несвязанных типов можно перечислить и в одном обработчике, формой `catch (A | B ex)`, если реакция на них общая. пример с общим хвостом:

```java


class Program{

     

	public static void main(String[] args) {

         

        printNumber(0);     // По индексу 0 число 1

        printNumber(10);    // Выход за пределы массива

        printNumber(3);     // For input string: "b"

    }



    static void printNumber(int index){



        String[] data = {"1", "a", "2", "b", "3", "c"};



        try{

            // пытаемся преобразовать значение массива по индексу в число

            int result =Integer.parseInt(data[index]);

            System.out.printf("По индексу %d число %d\n", index, result);

        }

        catch(ArrayIndexOutOfBoundsException _){  // обрабатываем выход за границы массива

                    

            System.out.println("Выход за пределы массива");

        }

        catch(Exception ex){        // обрабатываем все остальные типы исключений

                    

            System.out.println(ex.getMessage());    // выводим сообщение об исключении

            ex.printStackTrace();

        }

    }

}
```

отдельно обрабатывается `ArrayIndexOutOfBoundsException`, то есть выход за границы массива. все прочие исключения этого участка, включая `NumberFormatException`, принимает второй блок с типом `Exception`. для индекса 3 на консоль попадает сообщение исключения, у `NumberFormatException` это текст вида `For input string: "b"`, и следом трассировка стека.

блоки `catch` для более конкретных, производных типов (`ArrayIndexOutOfBoundsException`) располагают первыми, а блоки для более общих, базовых типов (`Exception`, `Throwable`) в конце, как в примере выше. компилятор отвергает обратный порядок: после `catch (Exception ...)` блок `catch (ArrayIndexOutOfBoundsException ...)` недостижим, потому что `ArrayIndexOutOfBoundsException` уже является `Exception` и был бы поглощён общим обработчиком.
