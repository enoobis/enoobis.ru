объект `Future` хранит результат асинхронной задачи. метод `get()` блокирует текущий поток, пока результат не станет доступен. класс `CompletableFuture` реализует `Future` и даёт другой способ получить результат: функцию обратного вызова, которая вызывается с результатом, когда он готов. `CompletableFuture` можно завершить явно, установив значение и статус методами `complete` и `completeExceptionally`. до этого вызова объект, созданный конструктором, остаётся незавершённым.

кроме того, `CompletableFuture` реализует `CompletionStage`. этап представляет звено асинхронного вычисления: действие или новое значение выполняются после завершения предыдущего этапа. цепочка этапов близка к `promise` в ряде языков, в том числе в javascript. каждый вызов `thenApply`, `thenAccept` и родственных методов возвращает новый этап, зависимый от предыдущего.

### создание completablefuture

объект `CompletableFuture` создаётся конструктором без параметров:

```java
CompletableFuture<Integer> future = new CompletableFuture<Integer>();
```

класс `CompletableFuture` обобщённый, параметр типа задаёт тип результата. в фрагменте выше результат асинхронной задачи имеет тип `Integer`.

после конструктора этап можно завершить явно. класс также содержит фабрики, которые сразу связывают объект с асинхронной задачей. одна из них, статический метод `supplyAsync`:

```java


static <U> CompletableFuture<U> supplyAsync(Supplier<U> supplier)

static <U> CompletableFuture<U> supplyAsync(Supplier<U> supplier, Executor executor)
```

у метода две перегрузки. обе возвращают новый `CompletableFuture`. первым аргументом обе принимают `Supplier`, и он описывает выполняемое действие. интерфейс функциональный, единственный метод `get()` возвращает значение:

```java


interface Supplier<T>{

    T get();

}
```

результат `get()` становится результатом этапа. дальнейшая обработка задаётся отдельными методами продолжения, обратными вызовами.

перегрузки различаются тем, кто исполняет задачу. во второй вторым аргументом передаётся `Executor`, и задачу выполняет он. в первой задаче достаётся поток из `ForkJoinPool.commonPool()`, если параллелизм этого пула не меньше 2. при меньшем параллелизме на задачу создаётся новый поток. `ForkJoinPool` является специализированным пулом для параллельных подзадач с кражей работы. общий пул выбирают, когда отдельная политика исполнения не нужна. свой `Executor` передают, когда нужен контроль над потоками, очередью и временем жизни.

простейшее вычисление факториала:

```java


int number = 5;  // исходное число для вычисления факториала



CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {

 

    // если число меньше 1, генерируем исключение

    if(number < 1) throw new RuntimeException("Number must be greater than 0");



    int n = 1;

    int result = 1;

    while(n <= number) result *= n++; 

    return result;  // возвращаем результат задачи

});
```

в `CompletableFuture.supplyAsync()` объект `Supplier` передан неявно, лямбда-выражением. лямбда читает внешнюю переменную `number`, считает факториал и возвращает результат. это значение и есть результат `Supplier.get()`, а затем и результат этапа. тот же объект `Supplier` можно объявить явно:

```java


int number = 5;  // исходное число для вычисления факториала



Supplier<Integer> task = () -> {

 

    // если число меньше 1, генерируем исключение

    if(number < 1) throw new RuntimeException("Number must be greater than 0");



    int n = 1;

    int result = 1;

    while(n <= number) result *= n++;

    return result;  // возвращаем результат задачи

};

CompletableFuture<Integer> future = CompletableFuture.supplyAsync(task);
```

метод `get()` у `Supplier` не объявляет проверяемых исключений. лямбда, переданная в `supplyAsync`, может выбросить только непроверяемое исключение. поэтому при недопустимом числе в примере используется `RuntimeException`. `Supplier.get()` проверяемых исключений не объявляет. у `Callable.call()` такое исключение в сигнатуре есть.

### добавление обратного вызова

после создания `CompletableFuture` и установки задачи регистрируют обратный вызов на завершение этапа. у класса большой набор таких методов. несколько из них:

- `CompletableFuture<Void> thenAccept(Consumer<? super T> action)` применяет к результату действие. метод `accept` у `Consumer` не возвращает значения, а сам `thenAccept` возвращает новый этап `CompletableFuture<Void>`

- `CompletableFuture<U> thenApply(Function<? super T, ? extends U> fn)` применяет функцию к результату и передаёт её значение следующему этапу

- `CompletableFuture<Void> thenRun(Runnable action)` запускает `Runnable`. этот `Runnable` результат предыдущего этапа не получает. полезного значения у нового этапа нет, метод возвращает `CompletableFuture<Void>`

- `CompletableFuture<U> thenCompose(Function<? super T, ? extends CompletionStage<U>> fn)` вызывает функцию для результата и подставляет возвращённый этап вместо вложенного будущего. функция возвращает `CompletionStage`, и именно его результат становится результатом цепочки

если передать в `thenApply` функцию, которая сама возвращает `CompletableFuture`, тип результата станет вложенным. `thenCompose` стыкует зависимую асинхронную задачу плоско, без этой вложенности.

в примере используется `thenAccept()`. аргумент имеет тип `Consumer`. у интерфейса метод `accept()` принимает одно значение:

```java
void accept(T t)
```

обратный вызов принимает значение типа результата и ничего не возвращает.

пример с факториалом:

```java


import java.util.concurrent.*;

import java.util.function.Supplier;

 

class Program{

 

    public static void main(String[] args) throws Exception{

          

        System.out.println("Main thread started...");

 

        int number = 5;  // исходное число для вычисления факториала

       

        // определяем задачу, которая вычисляет факториал

        Supplier<Integer> task = () -> {



            if(number < 1) throw new RuntimeException("Number must be greater than 0");

            int n = 1;

            int result = 1;

            while(n <= number) {



                result *= n++;

            }

            return result;  // возвращаем результат задачи

        };

 

        CompletableFuture<Integer> future = CompletableFuture.supplyAsync(task);



        // передаем в thenAccept обратный вызов

        future.thenAccept(result -> System.out.printf("factorial of %d is %d\n", number, result));



        // future.thenAccept - не блокирует основной поток 

        // и одновременно мы можем выполнять в основном потоке некоторую работу 

        System.out.println("Main thread works...");

 

        Thread.sleep(2000);



        System.out.println("Main thread finished...");

    }

}
```

регистрация обратного вызова:

```java
future.thenAccept(result -> System.out.printf("factorial of %d is %d\n", number, result));
```

параметр `result` является результатом асинхронной задачи, вычисленным факториалом. тело лямбды печатает его. вызов `thenAccept` возвращает управление сразу после регистрации и не ждёт колбэк.

по этапам программа идёт так:

- `System.out.println("Main thread started...")` основной поток `main` запускается и выводит это сообщение

- `CompletableFuture future = CompletableFuture.supplyAsync(task);` передаёт ранее определённую задачу `task` (вычисление факториала) в общий пул потоков, по умолчанию `ForkJoinPool.commonPool()`. задача начинает выполняться параллельно в другом потоке

- `future.thenAccept(result -> System.out.printf("factorial of %d is %d\n", number, result))` регистрирует обратный вызов. в исходном тексте программы зарегистрирован `thenAccept`. `thenAcceptAsync` поставил бы колбэк в пул отдельной задачей. колбэк не выполняется немедленно. он ждёт, пока `task` завершится и вернёт результат. если к моменту регистрации задача уже завершена, колбэк выполняется в потоке, вызвавшем `thenAccept`. иначе его выполняет поток, завершивший задачу

- `System.out.println("Main thread works...")` основной поток не ждёт завершения `task` и сразу продолжает работу. в примере для этой паузы печатается сообщение

- выполнение задачи. в это время `main` либо печатает `Main thread works...`, либо уже спит. параллельный поток считает факториал 5, то есть 120. на это уходят доли миллисекунды

- выполнение колбэка. сразу после завершения `task` запускается обратный вызов, зарегистрированный `thenAccept`, обычно в том же потоке пула, и выводит `factorial of 5 is 120`

- `Thread.sleep(2000);` основной поток спит 2000 мс. к этому моменту колбэк обычно уже выполнен и результат напечатан

- `System.out.println("Main thread finished...")` через 2 секунды основной поток просыпается, выводит сообщение, и программа завершается

наиболее вероятный порядок вывода:

```bash


Main thread started...

Main thread works...

factorial of 5 is 120

Main thread finished...
```

результат обрабатывается, как только он доступен, и `main` на `get()` не блокируется. точка ожидания в этом примере одна: `Thread.sleep(2000)`.

потоки, которые `CompletableFuture` берёт по умолчанию из `ForkJoinPool.commonPool()`, являются потоками-демонами, фоновыми потоками. jvm не ждёт их завершения. процесс жив, пока жив хотя бы один поток, не являющийся демоном. в программе выше такой поток один, поток метода `main`. если убрать `Thread.sleep`, поток `main` быстро выполнит `supplyAsync()` и `thenAccept()`, напечатает `Main thread works...` и `Main thread finished...` и завершится.

как только `main` завершается и других потоков, не являющихся демонами, не остаётся, jvm останавливает процесс. асинхронная задача и колбэк в `thenAccept()` могут не успеть выполниться. именно `Thread.sleep(2000)` удерживает основной поток живым и даёт задаче время завершиться и напечатать результат. оговорка к этому правилу: если параллелизм общего пула меньше 2, что бывает при одном или двух аппаратных потоках, `supplyAsync` без явного исполнителя создаёт на задачу отдельный поток через `new Thread`. такой поток демоном не является, и процесс дождётся задачи без паузы в `main`. на типичной машине с большим числом ядер используется общий пул, и пауза нужна.

вместо паузы в `main` можно явно задать `Executor`, который выполняет задачи:

```java


import java.util.concurrent.*;

import java.util.function.Supplier;

 

class Program{

 

    public static void main(String[] args) throws Exception{

          

        System.out.println("Main thread started...");

 

        int number = 5;  // исходное число для вычисления факториала

       

        // определяем задачу, которая вычисляет факториал

        Supplier<Integer> task = () -> {



            if(number < 1) throw new RuntimeException("Number must be greater than 0");

            int n = 1;

            int result = 1;

            while(n <= number)  result *= n++; 



            // имитируем долгую работу

            try {Thread.sleep(2000);}

            catch(InterruptedException _){}



            return result;  // возвращаем результат задачи

        };



        // определяем объект Executor, который будет выполнять задачу

        ExecutorService executor = Executors.newCachedThreadPool();

        CompletableFuture<Integer> future = CompletableFuture.supplyAsync(task, executor);

        future.thenAccept(result -> System.out.printf("factorial of %d is %d\n", number, result));



        // future.thenAccept - не блокирует основной поток 

        // и одновременно мы можем выполнять в основном потоке некоторую работу 

        System.out.println("Main thread works...");

        System.out.println("Main thread finished...");

        // закрываем исполнителя

        executor.close();  

    }

}
```

действия те же. пауза убрана из основного потока и перенесена в задачу факториала, чтобы задача заканчивалась после сообщений метода `main`.

добавлено создание `Executor`, он передаётся в `supplyAsync()`:

```java


ExecutorService executor = Executors.newCachedThreadPool();

CompletableFuture<Integer> future = CompletableFuture.supplyAsync(task, executor);
```

созданный `Executor` берёт платформенный поток из кэширующего пула. этот же пул выполняет и задачу факториала, и колбэк, который печатает результат: `thenAccept` без собственного исполнителя запускает продолжение в потоке, завершившем предыдущий этап. пауза в две секунды стоит внутри поставщика, поэтому к моменту `thenAccept` этап ещё не завершён и колбэк не попадает в `main`.

наиболее вероятный консольный вывод:

```bash


Main thread started...

Main thread works...

Main thread finished...

factorial of 5 is 120
```

из-за двухсекундной паузы внутри асинхронной задачи печать факториала оказывается после строки `Main thread finished...` в методе `main`. эта строка стоит до `executor.close()`. `close()` блокирует `main`, пока пул не остановится, поэтому процесс не завершается раньше колбэка. потоки `newCachedThreadPool` демонами не являются. в первом примере ту же роль удержания процесса выполнял `Thread.sleep` в `main`, потому что потоки общего `ForkJoinPool` демоны и сами процесс не держат.

### создание цепочки обратных вызовов

те же методы ставят обратные вызовы на обработку результата. продолжение может обрабатывать результат предыдущего продолжения. для преобразования значения служит `thenApply()`:

```java
<U> CompletableFuture<U> thenApply(Function<? super T, ? extends R> fn)
```

параметр метода имеет тип `Function`: функция принимает объект типа `T` и возвращает объект типа `R`, то есть переводит результат типа `T` в объект типа `R`. точнее, обратный вызов соответствует методу `apply()` интерфейса `Function`:

```java
R apply(T t)
```

во фрагменте сигнатуры результат функции обозначен как `R`, а параметр типа самого `thenApply` назван `U`. по контракту библиотеки тип значения функции и есть тип результата нового `CompletableFuture`.

после факториала значение увеличивается в два раза. факториал числа 5 равен 120, удвоенное значение равно 240.

```java


import java.util.concurrent.*;

import java.util.function.Supplier;

import java.util.function.Function;

import java.util.function.Consumer;

 

class Program{

 

    public static void main(String[] args) throws Exception{

          

        System.out.println("Main thread started...");

 

        int number = 5;  // исходное число для вычисления факториала

       

        // определяем задачу, которая вычисляет факториал

        Supplier<Integer> factorialTask = () -> {



            if(number < 1) throw new RuntimeException("Number must be greater than 0");

            int n = 1;

            int result = 1;

            while(n <= number)  result *= n++; 

            return result; 

        };

        // определяем задачу, которая увеличивает в два раза

        Function<Integer, Integer> doubleTask = result ->  result * 2;

        // определяем задачу, которая выводит на консоль конечный результат

        Consumer<Integer> printTask = result -> System.out.printf("Final result: %d\n", result);



        // определяем объект Executor, который будет выполнять задачи

        ExecutorService executor = Executors.newCachedThreadPool();

        // определяем коллбеки

        CompletableFuture

                .supplyAsync(factorialTask, executor)

                .thenApply(doubleTask)

                .thenAccept(printTask);



        System.out.println("Main thread works...");

        System.out.println("Main thread finished...");

        

        executor.close();  // закрываем исполнителя

    }

}
```

связывание этапов задаётся цепочкой:

```java


CompletableFuture

    .supplyAsync(factorialTask, executor)

    .thenApply(doubleTask)

    .thenAccept(printTask);
```

по шагам:

- `supplyAsync(factorialTask, executor)` задаёт асинхронную задачу, которая выполняется. это `factorialTask`, вычисление факториала. задача имеет тип `Supplier` и возвращает значение типа `Integer`

- `thenApply(doubleTask)` применяет к результату предыдущей задачи, вычислению факториала, функцию `doubleTask`. эта задача имеет тип `Function`. функция получает `Integer`, факториал числа и результат `factorialTask`, и возвращает `Integer`, удвоенное значение факториала

- `thenAccept(printTask)` применяет к результату предыдущей задачи, результату `doubleTask`, функцию `printTask` типа `Consumer`. задача получает `Integer` и ничего не возвращает, фактически `void`, и печатает результат на консоль

консольный вывод программы:

```bash


Main thread started...

Main thread works...

Main thread finished...

Final result: 240
```

`close()` снова удерживает процесс до конца цепочки. порядок строк зависит от того, успеет ли пул допечатать результат раньше двух сообщений `main`. в приведённой трассе паузы внутри факториала нет, но планировщик может отложить печать `Final result: 240` до строк `main`, как в этом выводе.
